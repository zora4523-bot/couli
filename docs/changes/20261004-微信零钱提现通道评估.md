# 影响评估：提现增加「微信零钱」收款方式

- 日期：2026-10-04
- 类型：00 §8 第 ② 类。改变已确认决定 D12（打款通道：企业支付宝 + 本人银行卡），新增一条资金通道。以下 §0–§9 是批准时的评估原文；写回落点见 §10。
- 状态：已批准并写回（2026-10-04）。
- 批准：2026-10-04 负责人在对话中选「全部按推荐」（微-01～微-06 均选 A）。
- 起因：2026-10-04 负责人在对话中提出提现要能打到微信零钱。
- 范围：只评估提现。App 内购买会员用微信支付是向用户收款，属于新增业务范围，另写评估，本文不涉及。
- 依据：08 `07_WDR`（BR-WDR-01～32）、`06_FUND`（BR-FUND-13、14）、`10_ID`（BR-ID-04）；00 §3.1 D10、D12；09 5_X §5.5（微信开放平台核对）；微信支付官方文档（§1.1）。

## 0. 结论

1. 能做，但微信的转账和支付宝不是一个模型：**默认要用户本人在微信里点「确认收款」，24 小时不点就关单、钱退回商户**。提现流程要多出「等用户确认」一步，自动到账也要用户在场才能到账。
2. 现有的 7 个提现状态、分录模板、只查不重提、对账框架都能沿用，按「第三个通道」加进去即可，改动集中在：收款账号（用微信授权代替填账号）、打款中的子状态与时限、按通道分的限额与水位、三端拉起微信确认页。
3. 微信默认额度很低（§1.2：单笔 200 元），不申请提额就只能承接小额提现。
4. 建议：现在就在契约和表结构里给微信通道留位，实现排在支付宝通道沙箱跑通之后，通道开关默认关，商户号、场景和额度批下来并实测后再开。

### 1.2 额度

[设置转账额度](https://pay.weixin.qq.com/doc/v3/merchant/4013747667)写的非个体户商户默认值：单笔 200 元，单日对同一用户 2,000 元，单日合计 5 万元，单月 3,000 万元（单月不可改）；提额在商户平台申请，结果按场景审核和商户号历史决定。旧版「商家转账到零钱」文档里有「佣金报酬单笔最高 2 万元」的说法，与此不一致。**我方商户号实际能拿到多少，只能以开通后商户平台显示的为准。**

### 1.3 没查清的

- 「用户授权免确认」模式在佣金报酬场景能不能用、授权多久有效、能否被用户随时解除。
- 运营账户余额有没有查询接口（影响水位自动取数）。
- 查单返回「单据不存在」的具体错误码，以及发起转账超时后原单是否一定可查。
- 佣金报酬场景的场景 ID、报备信息的固定取值、要交的证明材料。
- 收款微信是非大陆实名或未成年人实名时的处理。

## 2. 和现有提现规则的差别

| 环节 | 支付宝（现规划） | 微信零钱 |
| --- | --- | --- |
| 收款账号 | 用户填支付宝登录号和姓名 | 没有可填的账号，只能由用户在 App 里做一次微信授权，服务端换出 openid |
| 姓名核对 | 是否强制校验待验证（BR-WDR-22 ③） | 传了姓名才核对 |
| 到账 | 接口成功即到账 | 接口成功只到「等用户确认」，用户点了才到账 |
| 时限 | 无 | 24 小时不确认就关单退回 |
| 资金占用 | 成功才出金 | 等确认期间资金已锁在微信侧 |
| 超时后 | 只查不重提 | 微信允许原单号重试，但我方可以继续只查不重提（更严，不冲突） |
| 默认额度 | 待书面确认 | 默认单笔 200 元 |
| 回调 | 不用 | 有回调，也可以只靠查单 |

## 3. 建议方案

### 3.1 模式：先做「用户确认收款」

每笔由用户在微信里确认。免确认模式更贴近自动到账，但适用条件没查清（§1.3），查清并实测后再作为后续优化，届时另写变更。

### 3.2 收款账号

- `payout_method` 增加 `wechat`；`withdraw.payout_methods` 是否对用户开放由配置决定，默认不含 `wechat`。
- 绑定方式：原生 App 发起微信授权，授权凭证交服务端换 openid（与 BR-ID-04 同一条「身份只由服务端换取」的要求）。绑定只用于收款，**不**把这个微信变成登录方式（登录方式的绑定与解绑仍按功能对照 Q-26 放 P1）。
- 存 openid 密文、HMAC 和所属 AppID。双品牌下每个 App 的 AppID 不同，openid 也不同，提现单快照要带 AppID。
- 一个微信同一时刻只能被一个会员绑定（与 BR-WDR-02 ② 同口径）；换绑计入同一个每月次数；黑名单按 openid 的 HMAC 判（BR-ID-31）。
- 不需要付费核验。「收款人必须是本人」靠打款时传实名姓名由微信核对（§3.5）。
- 本机没装微信时不显示这种收款方式（沿用 BR-ID-04 细则「未安装微信时」）。

### 3.3 提现状态与时限

7 个提现状态不变。微信单在 PAYING 期间多一个通道子状态，用来区分「等用户确认」和「结果未知」：

| 微信单据状态 | 我方处理 |
| --- | --- |
| SUCCESS | W5，记成功分录 |
| FAIL、CANCELLED | W6，冻结额退回可用余额；不计入当日与当月提现次数（现有计数口径本来就不含 FAILED） |
| WAIT_USER_CONFIRM | 保持 PAYING，子状态记「等用户确认」，写确认截止时间；App 显示【去微信确认收款】 |
| ACCEPTED、PROCESSING、TRANSFERING、CANCELING | 保持 PAYING，继续查单 |
| 超时、5xx、未列入清单的错误码 | 结果未知，按 BR-WDR-14 只查不重提 |

- 用户点【去微信确认收款】时，原生 App 向服务端取本单的拉起参数（新接口，只有原生 App、只有本人、只在「等用户确认」时返回），再用 OpenSDK 拉起；从微信回来后立即触发一次查单。H5、JSBridge、Agent 不能取这个参数。
- 截止时间到了仍未确认：系统调撤销接口并继续查单，查到 CANCELLED 才走 W6。**BR-WDR-14 的「24 小时未知转人工」只对结果未知的单计时**，「等用户确认」不算未知；撤销后超过约定时长仍不是终态，才置 needs_manual。
- 用户确认前想取消：MVP 不提供，沿用「不能自撤，走客服」（BR-WDR-10）；客服受理后由后台对该单发起撤销。
- 不使用微信回调：payout 进程没有公网入口（BR-WDR-13），结果只靠查单。

### 3.4 自动到账与人工审核

- 判为自动到账的微信单：系统审核并执行后，单据很快进入「等用户确认」，用户刚提交完提现就能在 App 里直接去确认，体验上接近实时到账。
- 转人工审核的微信单：审核通过并执行后才进入「等用户确认」，此时用户多半不在 App 里，要靠推送和站内信叫回来，24 小时内不确认就退回余额。
- 批量打款（BR-WDR-12）可以包含微信单，执行结果是「已发起、等用户确认」而不是「已到账」，后台列表的展示状态要加这一种。
- 线下打款补录（W8）：企业没有线下向个人微信零钱转账的正规途径，微信单默认不开放 W8。

### 3.5 姓名、限额、水位

- **姓名**：每笔都传实名姓名让微信核对（我方最低提现额 1 元，高于 0.3 元门槛）。微信实名与 App 实名不一致的单会失败并退回，归为账号类失败，提示用户换收款方式。
- **限额**：提现金额限制目前是全局的（BR-WDR-04）。微信默认单笔 200 元，需要增加按收款方式的单笔上限，超过时在申请时就拦下并提示改用支付宝或银行卡；payout 进程的单笔、单日上限按通道分别配置（BR-WDR-32 ② 已有 `payout.<channel>.*` 的写法）。
- **水位**：BR-WDR-18 现在只看企业支付宝余额。微信从运营账户出资，且等确认期间资金已被锁住，水位要按通道分别算，微信的在途金额要算上所有「等用户确认」的单。余额能否自动取数待核（§1.3），取不到时与支付宝一样由财务手工录入。

### 3.6 判定清单与对账

- 结果判定沿用 BR-WDR-28 的三份清单，按通道单独一套。实测前按保守默认：只有 SUCCESS 算成功，FAIL、CANCELLED 是否直接算明确失败也等实测留样后再进清单；同步返回的错误码一律按结果未知处理并暂停该通道队列。NOT_ENOUGH（资金不足）是付款方侧失败的候选。
- 对账（BR-WDR-23）增加微信运营账户资金账单，按 out_bill_no 匹配。查单只支持 30 天，超过后以账单为准。
- 业务单号沿用 out_biz_no，现有格式（ASCII 字母数字、≤32）符合微信要求。

### 3.7 账务

- 增加微信出金科目（与 CASH_ALIPAY、银行卡出金科目并列）。分录模板、记账时点不变；微信没有手续费，不影响 BR-WDR-19。
- 税、劳务协议不变（BR-WDR-20、31）。转账场景选「佣金报酬」，与劳务协议的口径一致。

### 3.8 密钥与部署

- 商户证书私钥、APIv3 密钥、微信支付公钥只放 KMS，只有 payout 进程能读（与 BR-WDR-13 同口径）。
- payout 进程的出口 IP 要固定并登记到商户平台。
- 以后会员购买也用微信支付时，会有别的进程要用商户密钥，那份评估里再定是否分商户号。

## 5. 受影响的页面、接口与任务

- **页面**：绑定收款账号页（加微信）；提现页（按收款方式显示上限）；提现详情与记录（【去微信确认收款】、截止时间）；后台提现列表、批次结果、水位看板、对账。线框与高保真稿里这几页要补状态。
- **接口与契约**（由契约线落到 `rebate-platform/contracts/`，本工作区不直接改）：`payout_method`、`payout_channel` 枚举加 `wechat`；收款账号与提现单快照加微信字段；提现单加通道子状态与确认截止时间；新增「取确认收款拉起参数」接口；配置键 `payout.channel_enabled.wechat` 及微信通道的限额、清单、水位键；字典文案。
- **任务**（05）：B1-13（收款账号）、B2-05（申请校验）、B2-06（新增 WechatChannel）、B2-07（对账）、B2-09（后台接口）、B2-11（自动到账）、F1-08（后台页面）、APP-09、HM-08（三端）。新增能力验证 CAP-X-15「微信商家转账」。
- **外部资料**（06）：微信支付商户号、商家转账产品与佣金报酬场景、额度批复；Q-C12 微信开放平台移动应用是前置。

## 6. 验收

- 通道开关关闭时：不能绑定微信收款，已有微信单不执行，其他通道不受影响。
- 沙箱或小额实测留样后才把状态和错误码写进判定清单。
- 用例至少覆盖：确认成功；24 小时未确认退回且不计次数；用户取消确认后再次确认；姓名不一致；超过单笔上限在申请时被拦；发起转账超时后只查不重提；运营账户余额不足时暂停队列；同一个微信被第二个会员绑定被拒。
- 资金不变量不变：冻结额 = 非终态提现单合计（BR-FUND-14）。

## 7. 恢复方式

- `payout.channel_enabled.wechat` 置 off：新单不再执行；已在「等用户确认」的单继续查单，到期照常撤销退回。
- 从 `withdraw.payout_methods` 去掉 `wechat`：不能再绑定或选择微信收款；已绑定的用户提示改绑。
- 这两个开关都不涉及数据回滚，已完成的单不受影响。
