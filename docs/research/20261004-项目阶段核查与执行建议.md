## 3. 数据库写到哪里

已有 **6 条迁移，app schema 中 11 张逻辑表，另有 2 张默认分区**。基础设施的 pg-boss 队列表、迁移记录表不能计作返利业务表。

| 分组 | 已落库定义 |
| --- | --- |
| 平台底座，3 张 | `idempotency_keys`、`processed_events`、`event_log` |
| 身份，5 张 | `users`、`devices`、`user_oauth`、`login_logs`、`device_registrations` |
| 转链，3 张 | `links`、`link_logs`、`link_open_attempts` |

来源：[迁移目录](https://github.com/zora4523-bot/rebate-platform/tree/7e5ba24f656fa1b9ee2b0d6a157bd4dd8da07e30/db/migrations)、[生成的表结构快照](https://github.com/zora4523-bot/rebate-platform/blob/7e5ba24f656fa1b9ee2b0d6a157bd4dd8da07e30/db/schema.sql)。B1-01f、B1-02a、B1-06a 的公开任务证据包含容器验证成功与双方最终评审通过；身份表、转链表的验证不覆盖其尚未实现的业务服务。

商品相关业务、订单、账务、结算、提现的完整业务表尚未建立。apps / 配置 / 种子、不变量 SQL、分区维护按各自任务继续补齐；`link_logs` 的实际分区是按日，相关月分区任务标题需由编排者对账，避免只照标题实现。

数据库不需要先一次性写完所有远期表。按主线逐批完成：**规则和契约 → 迁移及约束 → 临时 PostgreSQL 中执行 → 生成 schema / 类型 → 独立规则测试与业务实现 → 并发 / 故障验证 → 评审和验收证据**。已有表复用并增量演进，不重复建设；建表完成和部署完成分别记录。

两家模型相互认可并不能保证正确。真正可依赖的是：**来源明确、规格版本固定、测试期望独立、实际运行证据、与待合并代码对应的 CI，以及真实业务验收。** 每次报告都区分已合并、已验收、已上线；没有执行的检查明确写未执行。

本次发现三个现有流程仍需收口的点，交给原编排者评估、沿既有编号登记小任务，不在本会话另起编排：

| 待收口项 | 影响与建议 | 验收应证明什么 |
| --- | --- | --- |
| 规格引用完整性 | 部分任务因任务书长度限制清空或省略 refs；检查只覆盖已列条款，任务书和评审范围也受影响。保留适用规则编号及哈希，按条款分片读取正文，避免通过删依据缩短输入 | 修改适用规则能触发 stale；所有适用条款可追溯到任务 / 测试；不因文本预算排除关键规则 |
| 派工与状态一致性 | 就绪和跨任务路径检查主要在看板，派工工具已有同任务认领但仍依赖编排者核全局条件；本次出现 done 与运行态不一致 | 同一任务不重复、未满足依赖不派发、共享文件冲突被阻止，完成任务状态能核对并收口 |
| 验收证据闭环 | 已有容器结果、树哈希与双评审核查；先红原因、规则测试评审关闭过程及 AC 记录的自动联动仍不完整。先保证人工证据齐全，再补最必要的检查与生成工具 | 能从某个提交追到实际运行、评审发现及关闭记录和对应 AC；历史失败与最终通过不会混淆 |

这些是对当前工具覆盖范围的发现，不是宣布相关已合并业务有错误，也不要求停下所有开发重建工具。优先修复会导致重复开发、规则漏读或错误验收的环节；已有验证过的能力保留。
