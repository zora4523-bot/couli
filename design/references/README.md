# 凑狸 UI / UX 参考

研究日期：2026-10-01。交付用途：为凑狸的商品发现、AI 找货、购买跳转、订单与钱包建立可落地的交互方向。

本次选择 **Apple Store、Airbnb、Perplexity、Rakuten、Things 3** 五个 App。下面的「官方事实」来自开发者发布的产品页、App Store 介绍和帮助文档；「凑狸建议」是针对本项目提出的设计方案。**未安装这些 App 做设备实测，也未验证其当前版本的每个屏幕、动效或可访问性表现。** 网页帮助中描述的通用交互不等同于 iOS 界面实测。

官方链接兼作查看官方截图、视频和说明的入口；本目录不下载、不转存第三方截图或商标。参考交互原则，不复制其布局、品牌色、插画与文案。本文不改变 `规划/` 中的功能范围、业务规则或平台能力结论。

## 1. 一眼看懂五个参考

| 参考 App | 要学习的交互 | 用在凑狸哪里 | 当前采用范围 |
| --- | --- | --- | --- |
| Apple Store | 商品信息与购买服务分层；能找到当前订单进度 | `ProductDetail`、`OrderDetail` | 详情页突出主操作，状态与售后入口清楚 |
| Airbnb | 将模糊需求逐步变成可修改的筛选条件 | `Search`、`AgentChat` 的条件摘要 | 当前平台内筛选、条件回显，不新增跨平台同款能力 |
| Perplexity | 用自然语言追问，保留可核对的信息入口 | `AgentChat`、商品详情「问问 AI」 | 短说明、结构化商品卡、当前会话内追问 |
| Rakuten | 解释购物跳转与返利跟踪；为缺失记录提供找回入口 | `JumpTip`、`OrderList`、`OrderDetail`、`FindOrder` | 购买前说明、返利状态解释、订单找回 |
| Things 3 | 用清晰层级控制信息密度，按需展开次要细节 | `OrderList`、`Wallet`、`Settings` | 稳定行布局、明确分组、次要信息渐进展开 |

对应流程草案见 [interaction-patterns.md](interaction-patterns.md)。这些参考各解决一个问题，不把五套导航混成一套。

## 2. Apple Store：商品明确，下一步明确

**官方事实与证据**

- Apple 发布的 App Store 介绍把商品探索、个人相关信息、支持分到不同区域，并描述继续先前浏览、查看订单进度的能力。[Apple Store 官方 App Store 页面](https://apps.apple.com/us/app/apple-store/id375380948)
- Apple 的购物帮助描述了订单详情中的状态信息与进度条。这是其在线购物帮助中的事实，不据此断言手机 App 使用相同组件。[Viewing & Changing Orders](https://www.apple.com/shop/help/viewing_changing_orders)

**凑狸建议**

- 详情页首屏优先呈现商品主图、标题和购买所需的信息，价格、返利与说明组成可扫描的信息组；辅助说明用次要层级承载。
- 底部主操作区使用凑狸主色；购买按钮与「问问 AI」形成明确主次。按钮文案和可用状态引用 BR-PRICE-21、F-PROD-05，不因视觉稿自行统一成一种购买文案。
- 用户从登录或平台授权回到详情时，保留商品位置与待继续操作，降低重新找商品的成本；恢复行为依 BR-ID-10、BR-ID-17。
- 订单详情把当前状态放在最显眼的位置，历史过程在下方展开；异常原因与帮助入口紧跟当前状态，不埋到页面底部。

**边界与避免照搬**

采用其信息分工，不复制 Apple 的商品大片风格、购物袋图标或商标。凑狸的交易在第三方平台完成，不引入自己的购物车、支付或设备个性化推荐。收藏与最近浏览也不因这一参考自动加入 MVP。

## 3. Airbnb：让筛选条件可见、可改

**官方事实与证据**

Airbnb 帮助页描述通过 Filters 缩小结果，并按预算、房型、设施等维度筛选；页面也说明有时会显示推荐筛选条件。这一来源证明其筛选模式，不证明凑狸应采用相同的筛选维度或推荐算法。[Using search filters](https://www.airbnb.com/help/article/479)

**凑狸建议**

- `Search` 顶部保持平台切换，下面用少量条件项显示价格区间、优惠券等已选条件。条件文字完整可读，不依靠颜色表示已选择。
- 在筛选面板中分组编辑，明确提供应用与清除操作；退出未应用的编辑时保留原结果，避免列表无提示变化。
- AI 识别出的平台、商品关键词和规格采用同一套视觉标签。标签是当前检索条件的回显，不是已验证商品满足条件的证明；逐卡条件标记由 BR-AI-24 约束。
- 没有结果时先保留用户条件，让用户知道为什么为空，再提供修改条件的入口；AI 自动放宽条件的反馈依 BR-AI-08。

**边界与避免照搬**

MVP 只画 F-PROD-01 已有筛选项，价格口径及排序范围引用 BR-PRICE-15。不新增地图、收藏、个性化筛选推荐。跨平台同款和截图找同款仍为 P1（F-AGENT-18）；多平台出现相似商品不能画成「已确认同款」。Airbnb 的价格计算口径不适用于凑狸。

## 4. Perplexity：问一句，得到可核对的结果

**官方事实与证据**

- Perplexity 开发者的 App Store 介绍明确列出会话追问与来源引用。[Perplexity 官方 App Store 页面](https://apps.apple.com/us/app/perplexity-ai-search-chat/id1668000334)
- 其官方 Enterprise 查询介绍说明可查看答案使用的来源，并继续提出后续问题。此项来自 Enterprise 网页产品说明，不视为手机端布局证据。[An introduction to Queries](https://enterprise-prod.perplexity.ai/enterprise/videos/an-introduction-to-queries)

**凑狸建议**

- 空态用现有示例问题帮助用户起步；输入框持续可见，支持表达商品、平台、预算与规格，减少学习命令格式的成本。
- 每轮形成「短说明 → 商品卡 → 下一步」的阅读顺序。商品卡承载金额、取价时间、平台与规则入口；AI 文本承担解释和引导。数据与文本分工引用 BR-AI-04、BR-AI-06。
- 提供现有多轮能力的快捷入口；点击后回显用户意图，保留前一轮结果，帮助用户对比条件变化。支持范围引用 F-AGENT-05，不扩展为自动化购物代理。
- 加载时只呈现正在获取结果的真实状态；已有卡片先可阅读。无结果、单平台失败和模型降级分别反馈，不用一个空白页承载所有异常。

**边界与避免照搬**

「可核对」在凑狸中对应联盟接口商品卡、规则卡和订单卡，不引入任意网页搜索作为价格来源（BR-PRICE-16）。AI 单独同意、内容标识、广告标识和披露继续按 BR-AI-13、BR-TEXT-16、BR-AI-10 执行。MVP 不新增历史会话列表、跨会话记忆、文件上传、语音或代下单能力（BR-AI-20、规划/01 §1）。

## 5. Rakuten：把返利过程解释清楚

**官方事实与证据**

- Rakuten 美国服务的官方帮助将 Cash Back 区分为不同状态，解释点击到商家的 Shopping Trip 记录，并提供 Missing Cash Back 入口。[Online Cash Back](https://www.rakuten.com/help/category/online-cash-back-26577737853715)
- 官方帮助首页把缺失返利与查看付款进度列为直接入口。[Rakuten Help Center](https://www.rakuten.com/help)

**凑狸建议**

- 购买跳转前的说明与当前商品、平台关联；用户能理解下一步去哪里以及为何需要授权。说明内容与触发时机引用 BR-ATTR-21、BR-ID-17，不把界面上的跳转成功表现为返利已确认。
- 订单列表每行以商品和当前状态为中心；金额标签与异常说明常驻，详情提供时间线与原因解释。
- 「未跟单」与已有订单的「返利异常」分别提供入口，避免用户把找回当成通用解决按钮；页面与行为引用 J5、BR-ATTR-17、BR-TEXT-05。
- 钱包把可操作余额与解释性信息分开，收益明细保留来源标记；账户展示引用 BR-FUND-18、BR-TEXT-01，不新增账户或汇总口径。

**边界与避免照搬**

这是**美国 Rakuten 返利服务**，不是日本乐天商城。仅学习透明解释与找回路径；不照搬它的确认周期、支付周期、税务、追踪机制或故障建议。凑狸用户术语和预计结算信息只引用 BR-TEXT-01～08，平台跳转能力只以 `规划/09` 实测为准。美团、会员月账单与分平台对账单透视仍为 P1（F-ORD-13、F-SET-09）。

## 6. Things 3：复杂信息也能从容阅读

**官方事实与证据**

- Cultured Code 的功能页介绍：任务可展开查看细节，次要字段按需使用；项目可用标题组织；Quick Find 用于查找和导航。[Things 3 Features](https://culturedcode.com/things/features/)
- 官方手势说明介绍了 Quick Find、拖动新增与排序等操作。这证明操作的存在，不构成凑狸必须实现相同手势的理由。[Using Gestures](https://culturedcode.com/things/support/articles/2803582/)

**凑狸建议**

- 订单采用稳定的列表行高度与对齐规则，关键信息在展开前可读；金额说明、流水详情和状态历史按需要进入下一层。
- 设置按账号、隐私、通知、关于等现有信息架构分组，使用短标题与清楚的当前值，减少用户反复进入页面确认状态。
- 轻量动效用于表达打开、返回与内容更新，避免页面位置跳变；减少动态效果时保留瞬时状态反馈。具体平台组件在实现时按三端规范选择。
- 主动操作后给出文字和图形反馈；对于服务端决定的订单或资金状态，界面只反映真实结果，不由用户手势改变。

**边界与避免照搬**

不把订单做成可勾选完成的任务，不允许滑动触发提现或购买，也不为展示创意而加入拖拽式购买。Things 的计划、提醒与项目系统不是凑狸需求；降价提醒仍按 E21 在 P1 推进。列表清晰度可以现在采用，复杂手势无需随之引入。

## 7. 落到凑狸的一致性约束

| 设计对象 | 采用方向 | 必须引用的项目依据 |
| --- | --- | --- |
| 导航 | 沿用首页、AI 助手、订单、我的；按开放状态执行既有替换 | 规划/01 §4.1、D16 |
| 商品与价格 | 以接口报价为主，返利与口径有清晰层级；无券、金额未知等状态分开 | BR-PRICE-03～05、08～11、17、21 |
| 购买按钮 | 一个明确主操作，加载、防重复点击、恢复与异常反馈 | F-PROD-05、F-LINK-01、BR-ID-10、BR-PRICE-13/14 |
| AI | 短说明、卡片事实、条件可见、异常可恢复 | BR-AI-04～10、13、14、20、23、24 |
| 订单与钱包 | 状态、预计结算信息与操作入口分工，保持单一余额 | BR-FUND-18、BR-TEXT-01～08 |
| 无障碍 | 重要状态同时用文字/图标表达；保持放大字体后可读；关键操作有显式入口 | 三端设计系统；[颜色与对比度规范](../colors/colors.md)、[App 图标规范](../app-icon/README.md) |

上述表格只指定视觉与交互着力点。完整文案、金额、状态、授权和接口行为仍在 `规划/08_业务规则/` 唯一维护；本目录不建立第二套业务规则。
