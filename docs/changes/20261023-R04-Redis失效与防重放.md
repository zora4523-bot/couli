### 2.3 数据整体丢失时（重启时没有持久化、被清空、换成空实例）

- 防重放：签名时间窗 ±300 秒，nonce 键 TTL 600 秒（`risk/domain/request-signature.ts:16,18`；BR-ID-09）。丢失前约 300 秒内发出的签名请求，在丢失后最多约 300 秒内可以各重放一次；时钟偏差到 300 秒时，上限是从丢失算起 600 秒。
- 已用的用户 step-up 令牌，在过期前（≤300 秒）可以再用一次。
- `refresh_grace`、验证码、oauth 尝试、后台会话与登录票据全部失效：少量用户被登出或要重新取码，管理员全部掉线。
- 频控与配额计数清零：当天可以再用满一轮，实名可以再调 3 次供应商，会产生费用。
- 持久化现状：staging 的 Redis 只开 RDB（20 分钟快照），AOF 关（`docs/changes/20261008-Agent受理与额度改用PG.md` §2）。快照最多落后 20 分钟，重启后最近这段时间的 nonce 都不在，对防重放来说和整体丢失一样会留下窗口。本地、CI、测试机的一次性 Redis 不落盘（`infra/local/compose.yaml:28-41`），只用于测试。

重放窗口里能被利用的，比上面的上限要少（**推断**，没有实测）：22 个签名接口中有 12 个标 `x-idempotent: true`、必须带 `Idempotency-Key`（04 §5「幂等」，记录在 PG 的 `idempotency_keys`；转链、外跳、提现、找回、收款账号、实名、绑手机、绑联盟、绑邀请人、并号、劳务协议、注销），逐字节重放会命中幂等回放，拿到原响应、业务不再执行一遍。剩下 10 个是发码、四种登录、oauth 尝试、step-up、refresh、放弃幂等键、输入解析：验证码和 oauth 尝试跟着 Redis 一起丢了，用它们的重放会失败；refresh 重放会被当成令牌复用、吊销会话，攻击者拿不到令牌；放弃幂等键重复执行结果不变。真正的残余主要是重发短信（计数也清零了）和输入解析。

## 3. 可选方案

前提相同：签名、限流、计数和会话的键在 Redis 上，不在故障时改记别处。

| | A 维持失败即拒，Redis 按关键依赖准备 | B 失败即拒 + Redis 高可用 | C 防重放平时就存 PG |
| --- | --- | --- | --- |
| 做法 | 代码不变；规划如实写；持久化开 AOF（`appendfsync always`，或 `everysec` 加「异常退出按数据丢失处理」，见下文）；不可达与写入被拒告警（D10-212、B1-01zzh），加上已有的内存 70% 告警；重启与重建 runbook（B1-01zzl）；02 §20 的停 Redis 演练 | 主从 + Sentinel，或改用云上 Redis 高可用版；故障时自动切到副本 | nonce 登记改为 PG 唯一约束，按时间分区清理；限流、验证码、step-up、会话仍在 Redis |
| Redis 故障期间用户能做什么 | 不能：登录、刷新、发码、购买（转链与外跳）、提现、找回、实名、绑手机、绑联盟、搜索（42901）、设备注册；后台全部不能用。能：凭有效 access_token 浏览首页与商品、看订单与余额、Agent 对话；打款与订单同步照常 | 同 A，但故障缩短到自动切换的秒级 | 签名阶段不再挡路；但搜索与购买仍被限流 42901 挡住，除非另定限流降级（这又是一项取舍）；登录、提现、后台仍不可用（验证码、step-up、会话在 Redis） |
| 防重放 | 故障期间什么都不受理，窗口为 0。数据丢失：`always` 下已确认的写入不会因进程异常退出而丢；清空、换空实例（以及 `everysec` 下的异常退出）由 runbook 规定从故障开始等满 600 秒再接入；两种情况窗口都为 0 | 异步复制，切换时丢失复制延迟内的 nonce（毫秒到秒级），各可重放一次 | 随 PG 持久化与时间点恢复，最连续；PG 回到过去时按 ADR-0002 §3、§4 的恢复流程处理 |
| 运维与成本 | 不花钱；AOF 与数据库同盘，多一点 IO 与磁盘（maxmemory 2G，靠重写控制大小），`always` 每批写入都要 fsync，写延迟在 staging 实测；`everysec` 下 Redis 异常退出后要等约 10 分钟才恢复签名接口；多一条告警、一份 runbook | 要另买节点（Pigsty 一个节点只能属于一个 Redis 集群，Sentinel 要另找节点）或云产品：花钱，可能是新供应商；prod 数据库是单节点、和 Redis 同机，整机故障时两个一起停，收益有限 | 每个签名请求多一次 PG 写（公开后转链与外跳是最热的写）；要清理任务；代码与测试要改 |
| 规划与 ADR | 改 02 §14、§3.1；ADR 正文不改（见 §6） | 改 ADR-0002 §2、§3：**需新 ADR**，由负责人决定 | 改 ADR-0001 §2 的 Redis 用途与 §4.2 第 17 项、02 §3.1、08 BR-ID-09 影响面：**需新 ADR**，并有实现任务 |

**排除**（不满足 R-04 约束）：Redis 故障时跳过 nonce 登记（失败放行）；Redis 故障时把 nonce 改记到 PG 或进程内存（故障时换存储：故障前登记在 Redis 里的 nonce 在新存储里看不到，照样能被重放）；只对转链与外跳放行（同第一条）。

**A 的持久化取值**：`everysec` 每秒 fsync 一次，进程异常退出最多丢约 1–2 秒的写入，这段时间登记的 nonce 对应的请求可以各重放一次，不满足「防重放连续」。所以 A 要求已确认写入的 nonce 不丢：默认 `appendfsync always`（Redis 把一批客户端的写入合并后 fsync 一次再回复）；staging 实测写延迟不能接受时退到 `everysec`，同时把异常退出后的重启当作数据丢失，按 runbook 等满 600 秒再接入（Redis 异常退出后不能自动重启后直接对应用开放）。Jev 问的是「AOF everysec 或等效」，这里为满足 R-04 的约束把残余窗口也收掉，属同一方案内的取值细化。

**A 的可选加强**（这次不做，记下备查）：在代码里认出「Redis 被清空或换了实例」（比如比对实例标识，或一个带 TTL 的代次键不见了），之后 600 秒拒绝签名请求，不靠人工就能做到等待（risk 模块要改，属实现方案，由编排决定是否派任务）。
