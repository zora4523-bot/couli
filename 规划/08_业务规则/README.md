## 0. 怎么用

修改规则（改取值、新增、作废、改状态）一律走 `规划/00` 的变更流程，细则见 §0.5。

### 0.1 本文地位

- 凡是「一旦改变会牵动数据库、接口、页面、客服话术」的业务规则，只在本文维护一处。`规划/00–07`、`09`、`10`、契约与代码注释引用规则时，**只写编号 + 一句话摘要，不得复述规则细节**（数值、公式、状态迁移、文案都不复述）。复述出现分歧时以本文为准。
- 本文与 `规划/04` 的分工：04 定义字段、枚举、接口、错误码的**形状**；本文定义它们的**取值规则与业务含义**。04（及 00–07、09、10）需要随本文调整的地方怎么落、还剩哪些没落，见 §0.6。
- 本文的规则来自已审定的主题材料；「来源」行列出依据文件，「取代」行列出被本条替换的旧写法（旧写法所在文档不再作为依据）。

### 0.4 条目结构

每个主题一节：先一句话概述，再用表格列出规则（列：编号、规则、状态、影响面），表格下为「细则」，逐条给出：默认值、决策人、依赖的平台能力、取代的旧写法、来源，以及公式、例子、边界。主题末尾列出本主题的未决问题。

### 0.5 修改规则

- 修改、新增、作废任何条目，走 `规划/00` 的变更流程（见 00 变更流程）：先评估影响的规则、页面、接口、历史数据、验收标准，再改本文，最后同步引用处。
- 改变金额口径、订单归属、用户授权或本期范围时由负责人决定；当前会话已经明确的决定可直接同步。普通实现选择、错误引用与摘要同步可由 Claude Code 或 GPT 处理，不因条目未标「代理可自定」而另行等待（00 D27）。运营在既定权限与范围内调整参数，走对应后台发布流程（D26）。
- 改变状态（如「待验证」→「已确认」）时，在细则中写明依据（验证证据路径或决策记录）。
