# 2026-11-02 佣金版本（commission_version）推进规则

- 决定方式：00 §8 第 ② 类（影响用户看到的预估金额）。08 原文没写清，按 规划/11 §7.1 由代理经 TypeSafe Jev（jev-1.14.0）判定后回写，事后报告负责人；编排裁定 D10-578。
- 起因：代码仓库 B2-03q（commission 预估端口）落地时查出，实现与 08 两处相反——结算收入已有后，预估一变仍推版本；结算收入到达或变化，从不推版本。前者让已入账单出现没有金额行的版本，扣回与账单按当前版本读快照会出错（已由 B2-03q 用「复制上一版本」兜住）；后者让结算差异不进金额行，钱包预估与提现风控读到的仍是旧额（相关跟进 FU-COMMISSION-VERSION-RULE、FU-CREDITED-AMOUNT-ROWS、FU-NEGATIVE-SETTLE-SNAPSHOT）。

## 1. 内容

BR-CALC-15「只有新 N 与已存值不同时 commission_version 才 +1」里的 N，指 BR-CALC-02 的有效联盟佣金（结算收入为空时取最新预估，一旦非空只取结算收入）：

1. 结算收入非空后，联盟只回传新的预估佣金：只存档 `est_commission_fen`，**不推版本**，金额行不动（Jev 0.90，置信 0.80）。
2. 结算收入首次到达或发生变化，使有效联盟佣金与当前版本存的值不同：**推一个版本**，按新的有效联盟佣金用同一算法（与快照、扣回、补差相同）写该版本的金额行与 totals（Jev 0.76，置信 0.52）。
3. 「当前应得额取最大 commission_version 的行」不变；入账（BR-CALC-14）、入账后调整（BR-CALC-23 (a)）、扣回（BR-FUND-08）的算法与取值不变。

## 2. 涉及的规则

- BR-CALC-15（写明 N 的含义，正文已回写）、BR-CALC-02（取值阶段，不改）、BR-FUND-03（「settle 非空后预估单独变化只存档」，与第 1 条一致，不改）、BR-CALC-27（每个新版本落四段金额，不改）。

## 3. 受影响的页面与接口

- 用户钱包预估（`/v1/wallet/summary`）、订单列表与详情的预估金额：结算收入到达后改按结算收入显示，不再停在预估。
- 提现风控读金额行的标签（如自购预估、订单佣金占比）：按当前有效联盟佣金计算。
- 后台订单与资金页面的预估与四段金额：同上。
- 代码：orders 的订单同步列计划（`planOrderSyncColumns`）、settlement rebate 的版本前进判据与 commission estimates 端口的 refresh。不加迁移、不改契约。

## 4. 验收与恢复

- 验收：代码仓库规则测试覆盖——结算后只改预估不推版本；结算收入首次到达且换算后的有效 N 变化时推版本、新版本金额行等于按新 N 计算的应得；结算收入变化后钱包与订单页同数；入账后结算变化的金额行与 BR-CALC-23 (a) 算出的新应得一致。
- 恢复：回退该任务的提交即恢复原推进方式（金额行只追加，已写的版本行保留，不影响已入账金额）。
