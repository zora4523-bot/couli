# 变更记录：Agent 受理与额度改用 PG，终止原因以落库为准（2026-10-08）

- 状态：已写回（负责人 2026-10-08 在对话中确认两项决定，见 §2）
- 来源：代码仓库 B3-03d（Agent 发送消息 HTTP 层）规则测试两轮过审共 16 条 S1，其中 11 条是崩溃收尾、并发与时间窗口问题；根因是 BR-AI-23 细则「受理记录与收尾」把具体步骤留给 B3-03（规划/12 X-10 未关闭），终止依据又分在 Redis 注册表与 PG 两处。编排会话改为先写收尾协议设计（运行仓库 `couli-runs/B3-03g/design.md`，第 5 版定稿，Codex 对抗评审 5 轮）。
- 类别：两部分。① 受理、计数与收尾的实现位置由 Redis Lua 改为 PostgreSQL 事务——实现方案（00 §8 第 1 类），但 BR-AI-23、BR-AI-15 的影响面与细则写着 Redis，须同步；② 「终止原因以落库为准」改变了崩溃时撤回同意 / 开关关闭的结算口径，触及用户授权边界与额度结算，属 00 §8 第 2 类，由负责人确认。
- 范围：不新增、不作废 BR，不改任何 BR 的状态与编号；不新增错误码。额度数值、计数主体、自然日、退还条件、校验顺序 ①–⑩ 与返回码都不变。

## 1. 内容

- **受理与额度改用 PG**：Agent 消息受理（BR-AI-23 ⑥ 去重、⑦ 会话级 run 锁、⑧–⑩ 判断与计数）与 run、用户与回复两条消息的写入改在同一个 PostgreSQL 事务内原子完成；每日条数、分钟窗口、会话轮数按已受理的 `agent_runs` 计，退还即把该 run 记为退还、不再计入受理日；会话级 run 锁存于 `agent_sessions`；run 结束时结算、终态与释放锁同一事务写入；进程崩溃后的收尾由同键重试、同会话新消息与 worker 定时扫描共用同一个收尾函数完成。Redis 只保留取消信号的加速路径，完全不可用时 Agent 受理、额度、收尾与取消照常。`done.quota_left` 按结束时的日上限计算（BR-AI-15「本条结束后当日剩余」的字面口径）。
- **终止原因以写入 run 记录为准**（规则澄清）：run 选定结局时立即写入终止原因，写入提交才算该 run 已经发生；用户取消记在 run 记录上，与终止原因的写入按先提交者为准；写入前崩溃的，有取消记录按取消，否则按 50001（未下发卡片的退还 1 条）。不再用同意记录、开关状态或任何外部时间戳倒推未落库的终止原因。
- **取消接口**：只在 run 截止前且尚无终止原因时接受，接受即写入 run 记录，返回成功即保证以取消结束；已成功取消的重复调用幂等返回成功；其余返回 30505。截止按取得该 run 记录的锁之后的服务端时刻判断。
- **异常返回**（代理自定的异常处置补充）：受理事务提交结果不明时按 client_msg_id 回查，仍不明或存储暂不可用返回 JSON 50401，请客户端用同一 client_msg_id 重试（不保证未计数）；遗留 run 数据异常、无法自动收尾时标记待人工处理，该会话的消息返回 JSON 50001（先于「仍在进行」判断），客户端引导新建对话。

## 4. 受影响的页面与接口

- `POST /v1/agent/sessions/{id}/messages`：新增 JSON 50401（受理结果未知或存储暂不可用，同键重试）与 JSON 50001（本会话遗留 run 待人工处理）；正常受理、重复消息与各拒绝码的形状不变。契约由代码仓库 CT-agent-accept 改（`openapi.yaml` 加 50401、50001，补 42901）。
- `POST /v1/agent/runs/{run_id}/cancel`：取消写在 run 记录上；截止后或已有终止原因返回 30505；返回 200 即保证以 cancelled 结束；重复取消幂等 200。契约描述由 CT-agent-accept 补。
- AI 助手页：发送消息收到 JSON 50001 时引导新建对话，收到 50401 时用同一 client_msg_id 重试（规划/03 §7.2）。
- worker 进程：新增 Agent 遗留 run 的定时收尾（代码仓库 B3-03h）。
- 规划同步：08 BR-AI-12、13、14、15、23 与 BR-ID-03、§13.11；02 §3.1 Redis 行、§9.2「配额与熔断」「取消与断线」、§14 Redis 降级行；03 §7.2；04 §3.2 `agent_sessions` / `agent_runs`、§6.5、§7、§8.1「重复消息」；05 B3-03、B3-09 行与 §9；12 §9 X-10。

## 5. 已知后果（以落库为准）

- 进程在 run 的终止原因写入之前崩溃时，该 run 按 50001 结束——即使用户恰在此前撤回了 AI 同意，或运营关闭了 `agent.enabled`，只要活进程还没把 10004 / 30501 写进 run 记录。
- 后果按每个 run 计：未下发卡片的退还 1 条（撤回同意本应不退，这里改为退，对用户有利）；开关关闭本就未出卡即退，只是错误码 50001 代替 30501；已下发卡片的都不退。
- 一次撤回同意作用于同一用户（游客按设备）的全部在途 run，一次关开关作用于全部在途 run；一次故障里每个落在崩溃窗口内的 run 各自如此处理、各自至多差 1 条，合计条数不设上限估计。
- 只涉及 Agent 消息条数：不涉及资金、订单归属与授权边界。撤回同意与关开关本身照常生效（之后的请求一律 10004 / 30501），只是不被记作这条已崩溃 run 的终止原因。用户取消不受影响：取消一经写入 run 记录即按取消结束。

## 6. 验收与恢复

- 验收用例与话术：规划/10 的 Agent 相关用例（重复消息、30506 后拉历史、崩溃恢复）在 B3-03g / B3-03h 合并时补「以落库为准」「取消兑现」「JSON 50401 同键重试」「JSON 50001 引导新建对话」四类断言，登记在 X-10 余下项；BR-TEXT-14 的 50001 行（「请稍后再试 / 重试」）对 Agent 发送消息的待人工处理情形按 §13.11 改为引导新建对话，随契约任务 CT-agent-accept 同步话术键，本记录不改 BR-TEXT-14 原文。

- 验收：B3-09b（迁移 0022，B3-09a 受保护测试全绿）；B3-03g 崩溃注入模型测试（每步前后注入崩溃 + 并发恢复，检查只结算一次、终止帧等于终态、以落库为准、取消兑现等不变量）与确定性用例（同键并发、同一用户跨会话第 N 条、先收尾再受理、取消裁决、限额下调后的剩余额度、Redis 全停照常）；替换后的 `stream-admission` 规则测试（原 39 条中保留 37 条行为，删去 2 条 Redis 专有断言）；B3-03h 真 HTTP + 真 PG + worker 集成（崩溃后无人重试由定时扫描收尾、两 worker 并发只退一次、取消 200 后杀实例收尾为 cancelled）。规划/12 X-10 中「B3-03 的崩溃收尾设计与同键并发验收」在 B3-03g 合并后关闭。
- 恢复：迁移 0022 只加列、约束与索引，可留在库里；代码按 PR 回退即回到 B3-03c 的 Redis 实现（Agent 未上线，无生产数据需迁移），同时回退本记录对 08 的改写。以上直接回退只适用于上线前（无生产数据）；上线后默认保留 PG 实现、就地修复，确需恢复 Redis 实现时另立方案：停 Agent（`agent.enabled=off`）、等全部 run 收尾，再按 PG 中当日用量、分钟窗口与会话轮数重建 Redis 计数并核对后切换，不能只靠停机与收尾。负责人改选「终止原因按同意记录 / 开关状态倒推」时，回退 BR-AI-23 细则「崩溃不改变结果」与 BR-AI-12、13、14、15 补的句子，另开任务恢复 CFG-HIST、ID-AIC 前置。
