## 0. 请负责人选（业务选择题）

**问题**：Redis 坏了的时候（它和数据库在同一台机器上，单实例），登录、购买（转链）、提现这些带签名的操作，要不要继续能用？

| 选项 | Redis 故障期间用户会怎样 | 代价 |
| --- | --- | --- |
| **A（建议；Jev 1.0）**：维持现在代码的做法，故障时一律拒绝；同时把 Redis 当关键依赖来保：开持久化、告警、runbook；加一项小的代码任务，Redis 数据丢了能自己认出来，先停签名操作约 10 分钟再恢复 | 不能登录、刷新、购买、提现、找回、实名、搜索，后台也不能用；登录过期的用户会被登出。能浏览、看订单与余额、和 Agent 对话；打款、订单同步不受影响 | 不花钱；规划写成实际行为。Redis 数据真丢了（很少发生）时，签名操作多停约 10 分钟，约占月可用性余量（99.9%，每月约 43 分钟）的四分之一 |

## 1. 约束

R-04 的要求：
- 任何方案都要**同时保证防重放连续**；
- **不做「故障时换存储」**；
- 裁定之前，先把 Redis 当关键依赖准备好（告警、持久化、重启与重建 runbook）。

ADR-0001（负责人 2026-10-01 授权代理定版）§4.2 第 17 项是编排者同日补定的实现选择，规定防重放 nonce、配额计数、`refresh_grace` 不得被静默淘汰。

D10-212（编排，已定）：api 的 `/health` 不探 Redis，否则 Redis 故障时 api 会被反复重启，故障扩大；Redis 能不能连上，放进 worker 的健康检查（B1-01zzj）和告警（B1-01zzh），api 只出指标。

### 2.3 数据丢失时（重启时没有持久化、实例被清空、换成空实例）

- **防重放**：签名的时间窗是 ±300 秒，nonce 键的 TTL 是 600 秒（`risk/domain/request-signature.ts:16,18`；BR-ID-09）。丢失前约 300 秒内发出的签名请求，丢失后最多约 300 秒内可以各重放一次；时钟偏差到 300 秒时，上限是从丢失算起 600 秒。
- **step-up**：已经用过的用户 step-up 令牌，在过期前（≤300 秒）可以再用一次。
- **会话与验证**：`refresh_grace`、验证码、oauth 尝试、后台会话与登录票据全部失效。少量用户被登出或要重新取码，管理员全部掉线。
- **计数**：频控与配额计数清零，当天可以再用满一轮。实名可以再调 3 次供应商，会产生费用。
- **持久化现状**：staging 的 Redis 只开 RDB（20 分钟一次快照），AOF 关（`docs/changes/20261008-Agent受理与额度改用PG.md` §2）。快照最多落后 20 分钟，重启后这段时间的 nonce 都不在，和整体丢失一样会留下窗口。本地、CI、测试机上的一次性 Redis 不落盘（`infra/local/compose.yaml:28-41`），只用于测试。

重放窗口里真正能被利用的，比上面的上限少（**推断**，未实测）：
- 22 个签名接口中有 12 个标 `x-idempotent: true`，必须带 `Idempotency-Key`（04 §5「幂等」，记录在 PG 的 `idempotency_keys`）：转链、外跳、提现、找回、收款账号、实名、绑手机、绑联盟、绑邀请人、并号、劳务协议、注销。逐字节重放会命中幂等回放，拿到原来的响应，业务不会再执行一遍。
- 其余 10 个是发码、四种登录、oauth 尝试、step-up、refresh、放弃幂等键、输入解析：
  - 验证码和 oauth 尝试跟着 Redis 一起丢了，用到它们的重放会失败；
  - refresh 的重放会被当成令牌复用，会话被吊销，攻击者拿不到令牌；
  - 放弃幂等键执行几次结果都一样。
- 真正剩下的，主要是重发短信（短信计数也清零了）和输入解析。

## 3. 可选方案

三个方案的前提相同：签名、限流、计数、会话用的键都在 Redis 上，故障时不改记到别处。

| | A 维持失败即拒，Redis 按关键依赖准备 | B 失败即拒 + Redis 高可用 | C 防重放平时就存 PG |
| --- | --- | --- | --- |
| 做法 | ① 持久化开 AOF：`appendfsync always`，重写期间不跳过 fsync；② 新开实现任务「代次识别」（见下）；③ 代码就绪前的 runbook 与 ACL；④ 告警（D10-212、B1-01zzh）、重启与重建 runbook（B1-01zzl）、02 §20 的停 Redis 演练 | 主从 + Sentinel，或改用云上 Redis 高可用版；故障时自动切到副本 | nonce 登记改用 PG 唯一约束，按时间分区清理；限流、验证码、step-up、会话仍在 Redis |
| Redis 故障期间用户能做什么 | 不能：登录、刷新（access_token 到期的用户被登出）、发码、购买（转链与外跳）、提现、找回、实名、绑手机、绑联盟、搜索（42901）、设备注册，后台全部不能用。能：凭有效 access_token 浏览首页与商品、看订单与余额、Agent 对话；打款与订单同步照常 | 同 A，但故障缩短到自动切换的秒级 | 签名阶段不再挡路，但搜索与购买仍被限流 42901 挡住，除非另定限流降级（这又是一项取舍）；登录、提现、后台仍不可用（验证码、step-up、会话在 Redis） |
| 防重放 | 故障期间什么都不受理，窗口为 0。`always` 下，已确认的写入不会因进程崩溃或重启而丢。实例被清空、换成空实例时，代次识别让签名请求在去重时长内一律拒绝，窗口为 0。代码就绪前：换空实例靠 runbook 隔离，原实例上被误清空仍有窗口 | 异步复制，切换时会丢掉复制延迟内（毫秒到秒级）的 nonce，这些请求各可重放一次 | 随 PG 持久化与时间点恢复，最连续；PG 回到过去时，按 ADR-0002 §3、§4 的恢复流程处理 |
| 可用性代价 | 每次数据丢失事件，签名接口多停约 10 分钟，约占 99.9% 月余量（约 43 分钟）的四分之一；`always` 下普通崩溃与重启不触发。Redis 故障本身的停机全部计入 | 故障时间最短 | 签名阶段不计入，其余同 A |
| 运维与成本 | 不花钱。AOF 与数据库同盘，多一点 IO 与磁盘（maxmemory 2G，靠重写控制大小）；`always` 每批写入都要 fsync，写延迟在 staging 实测。实测不能接受、退到 `everysec` 时，每次重启都要按数据丢失处理（代次识别再加上实例标识比对），普通重启也会停约 10 分钟。另有一项小的代码任务 | 要另买节点（Pigsty 里一个节点只能属于一个 Redis 集群，Sentinel 要另找节点）或云产品，花钱，可能是新供应商。prod 数据库单节点、和 Redis 同机，整机故障时两个一起停，收益有限 | 每个签名请求多一次 PG 写，公开后转链与外跳是最热的写；要清理任务；代码与测试要改 |
| 规划与 ADR | 改 02 §14、§3.1（草稿见 §6）；ADR 正文不改，持久化取值按 ADR-0002 §10 第 7 项补；ADR-0002 §2 理由句需新 ADR 更正 | 改 ADR-0002 §2、§3：**需新 ADR** | 改 ADR-0001 §2 的 Redis 用途与 §4.2 第 17 项、02 §3.1、08 BR-ID-09 影响面：**需新 ADR**，并有实现任务 |

**排除**（不满足 R-04 约束）：
- Redis 故障时跳过 nonce 登记，即失败放行；
- Redis 故障时把 nonce 改记到 PG 或进程内存，即故障时换存储。故障前登记在 Redis 里的 nonce 在新存储里看不到，照样能被重放；
- 只对转链与外跳放行（同第一条）。

**为什么 A 用 `always` 并要求代次识别**（couli #187 r1 评审 S1-1）：
- 持久化只用 `everysec` 时，进程异常退出最多丢约 1–2 秒的写入，这段时间登记的 nonce 对应的请求可以各重放一次，不满足「防重放连续」。
- 应用里也没有「接入」这道闸门：连接是延迟建立的，每条命令失败后，下一条会重新连（`platform/redis/index.ts:9-12`），api 也不探 Redis（D10-212）。所以 Redis 一旦被自动拉起或换了实例，应用马上就会用上。在原实例上被清空时，连接一直没断，窗口当场打开。
- 因此，「等满去重时长」只靠 runbook 做不到，要由代码来认。

**代次识别**（实现任务的要点，细节由任务定）：
- risk 模块维护一个带 TTL 的代次键，正常运行时持续续期，保证不会自然过期。
- 签名检查发现代次键不在（实例被清空或换成了空实例），就重建它，并从这一刻起在 nonce 去重时长（BR-ID-09）内拒绝签名请求，按 Redis 不可用处理。
- 持久化退到 `everysec` 时，实例标识变化（重启）也当作数据丢失。

**代码就绪前**：
- runbook 规定：换空实例时，先不让应用连上（停服务或改口令），从故障开始等满去重时长再放开；
- 应用账号用 ACL 禁用 FLUSHALL、FLUSHDB、DEBUG、CONFIG 等命令，运维要清库也按 runbook 走同样的等待；
- 在原实例上被误清空，仍有窗口。

## 4. 影响面

- **涉及的 BR**：
  - BR-ID-09：签名与 nonce，取值不变；
  - BR-ID-01：判定顺序 ① 签名、⑬ 限流，不变；
  - BR-ID-07：refresh 与 `refresh_grace`，不变；
  - BR-ID-08：step-up 一次性，不变；
  - BR-TEXT-14 细则、08 §13.11：「刷新失败清会话」不变，但它让 Redis 故障时 access_token 到期的用户被登出（§2.2）。是否把 50001、42901、网络错误排除在「刷新失败」之外，是另一项取舍（§7）。
- **接口与契约**：不变。签名接口在 Redis 故障时返回 50001、限流返回 42901，都是现有的错误码和现有的行为（04 §7）。代次识别期间也按 Redis 不可用返回 50001，不新增错误码。
- **页面**：不改。三端与 H5 按通用 50001、42901 的现有方式处理；access_token 到期的用户会被带回登录页，而登录要等 Redis 恢复。
- **客服话术**：不新增 BR-TEXT 键。按现有 50001「服务端错误」、42901 的口径应答。要不要为 Redis 故障加专门的「暂时不可用」码和话术，列为 §7 待定，默认不加。
- **验收用例**：10 里没有 Redis 故障的用例，不改。停 Redis 演练（02 §20）的预期：
  - 签名接口 50001，搜索 42901；
  - 浏览与 Agent 可用；
  - access_token 到期的用户被登出；
  - 打款不受影响；
  - 恢复后不重启进程就自动好转。

> - 带签名的接口（逐个以 openapi `x-signed` 为准，§12.2）登记 nonce 失败，返回 50001，不跳过防重放（ADR-0001 §4.2 第 17 项）。

> - access_token 到期的用户刷新失败，客户端按 BR-TEXT-14 清会话，用户被登出；登录要等 Redis 恢复。

> - 缓存路径按未命中处理，直读 PG 或调联盟。
