  - 不能验证的 provider 的剩余风险与补偿（微信；华为核对为不支持或未核对时相同）：一份还没有兑换的 code 一旦落到别人手里，谁先提交谁就能用——配另一个尝试、另一台设备、另一种用途都能通过，因为服务端分不出它原本属于哪一次尝试。补偿措施只有这些：code 一次有效（被别人先兑换后，原请求必然失败）；尝试一次有效，并绑定设备与用途；身份只取服务端换得的结果；二次验证时，换得的身份必须等于当前登录账号已绑定的那一个，且第三方方式的二次验证只用于 BR-ID-08 允许的场景（未绑手机的账号申请注销）。这是这类 provider 的已知限制，规划不把它写成「凭证只能用于取得它的那次尝试」。
  - 请求体：三个第三方登录接口只收 `attempt_id` 和授权凭证（规划/04 §6.1）：微信 `code`；Apple `identity_token`、`authorization_code`；华为 `authorization_code`。不设 union_id、open_id、sub、昵称、头像、手机号字段，也不收客户端自带的 nonce；出现未定义字段返回 20001，不建号。
  - Apple：身份以服务端换码所得为准。服务端用 authorization_code 向 Apple 换码，取回 Apple 签发的身份令牌和 refresh_token；对换回的身份令牌用 Apple 公钥验签，并逐项校验签发方（iss）、受众（aud，本 App 的 Bundle ID）、有效期（exp）与 nonce（对应本次尝试）。客户端提交的 identity_token 按同样的项目校验，并且它的主体（sub）必须与换码所得的主体相同。任一项不过、两个主体不一致，或换码被拒 → 20004。全部通过后，取换码所得的 sub 作为 union_id，并加密保存同一次换码得到的 refresh_token（本条正文）。换码响应里没有身份令牌或缺少必需声明时，按第三方服务异常处理（50305 并告警），不退回到只信客户端提交的令牌。
  - 微信：code 一次有效，由服务端换取 openid 与 unionid（开放平台 AppSecret 只在服务端，规划/02 §12.6）。换取结果里没有 unionid 时登录失败，返回 50305 并告警，不得用 openid 充当 union_id。
  - 华为：code 一次有效，由服务端向华为账号服务换取 unionID、openID；换取结果带身份令牌时，按 Apple 的同一组项目验签并核对 nonce 之后才取身份。华为渠道 Android 包与鸿蒙是两套接入，换取端点与返回字段分别按官方文档核对（规划/09 5_X §5.4 只确认了文档入口）。
  - 用途隔离：登录接口只接受用途为 login 的尝试；`POST /v1/auth/step-up` 只接受用途为 step_up、且 uid 与 action 相同的尝试（BR-ID-08）。对能验证关联的 provider（Apple；华为核对为支持时），为登录取得的凭证不能用于二次验证，反过来也不行。对不能验证的 provider，服务端只能保证尝试本身的用途与归属，保证不了凭证出自同一次尝试（见上一项），同一份凭证因 code 一次有效而不会在两个用途各用一次。
  - 失败处理：凭证或尝试无效、已过期、已使用 → 20004，对外不区分具体原因；第三方接口超时、限流或返回服务端错误 → 50305（data.provider），客户端提示改用其他登录方式。失败时不建号、不写 consent_records、不签发令牌；尝试已被消费的（上文 ③ 之后失败）作废，重试须重新取尝试、重新授权。
  - 最小化：服务端不调用第三方的用户资料接口，不保存第三方昵称、头像（昵称、头像的默认值见上文与 BR-ID-39）；code、identity_token、authorization_code 与换得的第三方访问令牌不落库、不进日志（Apple refresh_token 例外，按本条正文加密保存）。
  - 各第三方的接口名、凭证有效期与一次性语义以官方文档为准，接入任务核对后写入 `specs/oauth/<provider>.md`；核对前不写进对用户的承诺。
  - 四个登录接口的响应都带 `is_new_user`（本次请求是否新建了账号，规划/04 §6.1）；第三方新号的绑手机引导见 BR-INV-03 细则。
  - 为什么：令牌和授权码各验各的，挡不住「甲用过的令牌配乙的新授权码」这类拼接（会以甲的身份登录，却存下乙的 refresh_token）。以换码所得为准、核对主体和 nonce 之后，Apple 的凭证只能在取得它的那次尝试里用一次；微信等不能验证关联的 provider 做不到这一点，只能靠上面的补偿措施把影响限制住。
- 例：客户端在微信登录请求体里多带了 `union_id` 字段 → 20001，不建号；同一个 attempt_id 在通过校验并被消费之后再提交 → 20004（即使第一次换取失败）；换一个新的尝试再提交已用过的 code → 微信拒绝换取 → 20004。
- 例（先校验后消费）：设备 D2 拿到设备 D1 的 attempt_id 抢先提交 → 设备不符 → 20004，尝试保持未用；D1 随后提交 → 正常处理。两个请求同时提交同一个尝试 → 只有一个进入换取，另一个 20004。
- 例（拼接）：提交甲的 identity_token 和乙的 authorization_code → 换码所得的主体是乙，客户端令牌的主体是甲 → 20004，不建号、不保存 refresh_token。
- 例（旧令牌）：提交甲上一次登录用过的 identity_token 和甲这一次新取的 authorization_code → 旧令牌的 nonce 对不上本次尝试 → 20004。
- 例：Apple identity_token 的受众不是本 App 的 Bundle ID → 20004；Apple 换码接口超时 → 50305（data.provider=apple），登录页提示改用手机号登录。

**服务端可验证的绑定能力**（BR-ID-04 细则，2026-10-03 第 2 轮评审补；「绑定」指服务端能证明这份凭证出自这一次授权尝试）：

| provider | 服务端能否验证 | 依据与要求 |
| --- | --- | --- |
| Apple | 能 | 换码所得身份令牌里的 nonce 对应本次尝试。nonce 传给 SDK 时用原样还是摘要，在 `specs/oauth/apple.md` 固定为唯一一种并给出测试向量，服务端只接受这一种，不为兼容而同时接受两种 |
| 华为 | 待核对 | 接入时核对华为账号服务是否支持 PKCE，或换码返回的身份令牌是否带回授权请求里的 nonce。支持哪一种就必须用，由服务端校验；都不支持，或还没有核对完，一律按「不能」对待。结论写入 `specs/oauth/huawei.md`（规划/09 5_X §5.4 未知项，规划/05 CT-15） |
| 微信 | 不能 | 换取结果不带 nonce 或 state，服务端无从核对；剩余风险与补偿措施见上文「不能验证的 provider」一项 |

#### BR-ID-05 细则 · 短信验证码与注册风控

- 44003（需要人机验证）为规划/04 缺失的码；后端规划原写 43002，规划/04 无 43xxx 子段，按 44xxx 风控段顺序取号（13 §13.3）。
- 例：同一 IP 在 09:00、09:10、09:20、09:30、09:40 各新注册 1 个账号，09:50 该 IP 发码未带人机验证凭证 → 44003；带有效凭证 → 进入 42901 频控判定。窗口取 [now − 3600 秒, now]（两端闭区间）：10:00:00 时 09:00 的注册仍在窗口内，仍需验证；10:00:01 起窗口内只剩 4 个（&lt;5），不再强制（`sms.captcha_mode=always` 除外）。

- **发码与设备注册的风控默认值**（2026-10-03，功能对照 G-20；默认值为代理补全，决策人运营，全部可在配置中心修改、修改写审计）：原来 App 内发码只按手机号限频，人机验证只在「同一 IP 新注册过多」时触发——只发码不注册的刷量碰不到任何一条，设备注册也没有上限。

  - 判定位置：发码判定顺序不变（签名 → 20001 → 44001 → 44003 → 42901）。44003 的触发条件现在有三个，任一成立即要求人机验证：该 IP 一小时内新注册 ≥5 个账号（原有）；该 IP 一小时内发码条数达到 sms.ip_sends_per_hour；sms.captcha_mode=always。42901 的判定里，先看设备的不同号码数，再看手机号的 60 秒与每日额度。
  - 设备的不同号码数（2026-10-03 评审后改写，原写法「请求过就计入、计入过就放行」可以靠重试绕过）：每台设备分开记两样东西。
    - 准入集合：这台设备在窗口内获准发码的号码，每个号码记最近一次通过本项检查的时刻，超过 3600 秒没有再通过的移出。集合大小不超过上限。只有它参与判定。
    - 请求记录：这台设备请求过的全部号码（含被本项拒绝的）、时刻与结果，只供风控分析与告警，不参与判定；记号码的 HMAC，不记明文。
    - 判定：号码已在准入集合里 → 通过，并刷新该号码的时刻；不在集合里且集合未满 → 加入集合后通过；不在集合里且集合已满 → 42901，不加入集合。被拒绝过不构成任何资格，下一次请求仍按同一规则判。
    - 原子性：「清理过期号码、判断是否在集合里、判断是否已满、加入或刷新」必须在同一个原子操作里完成（例如一段 Redis 脚本，或按 device_id 加锁的事务），不得先读后写。并发请求多个新号码时，准入的个数不得超过剩余名额。
    - 准入之后不论后续结果如何都占名额：手机号频控的 42901、供应商发送失败都不退还。准入之前就被拦下的请求（签名、20001、44001、44003）到不了本项，不占名额，也不进准入集合。
    - 存放准入集合的存储不可用时按拒绝处理（42901），不放行。
  - 「一键对所有请求开启人机验证」就是把 sms.captcha_mode 置为 always（已有配置，本次不新增开关）；该项放进配置中心的风控配置页，修改需 step-up（权限点 `config.risk`，规划/04 §11）。
  - 人机验证服务不可用时（未开通或故障），需要人机验证的发码请求返回 42901，不因验证不可用而放行；是否启用人机验证仍待决策（13 §13.3 的 44003 行），启用前上述「改为必须人机验证」的两种情形都按 42901 处理。
  - 窗口都是滑动窗口 [now − 3600 秒, now]，两端闭区间，口径同本条的同 IP 注册判定。IP 取网关识别出的客户端 IP；同一出口 IP 下用户很多（运营商网络、校园网）时默认值可能偏紧，运营按告警与投诉调整。
  - 其他接口的三维限流默认值（转链、搜索）仍见 规划/06 Q-B4，Agent 见 BR-AI-15，本条不重复。
  - 例：一台设备 10:00、10:05、10:10 依次对 A、B、C 三个号码发码（准入集合 = A、B、C），10:20 对号码 D 发码 → 42901，D 不进准入集合；10:21 再对 D 发码 → 仍是 42901（原写法在这里会放行）。10:25 对 A 重发（距上次已过 60 秒）→ 正常，A 的时刻刷新为 10:25。11:05:01 起 B 滑出窗口（A 因 10:25 的重发仍在窗口内），此后对 D 发码 → 准入。
  - 例（并发）：准入集合里已有 A、B，同一台设备同时对 5 个新号码各发 1 个请求 → 恰好 1 个准入，其余 4 个 42901；准入集合 = A、B 加上那 1 个。
  - 例：某 IP 在 09:00–09:30 内发码成功 20 条，09:31 该 IP 的发码请求不带人机验证凭证 → 44003；带有效凭证 → 进入 42901 判定。
  - 例：当日已发送 4000 条（预算 5000）→ 告警一次；运营把 sms.captcha_mode 置为 always → 之后所有发码都要人机验证。

- **手机号规范化**（2026-10-03，功能对照 G-19；「MVP 只支持中国大陆手机号」按功能对照 Q-24 默认 A 写，待负责人确认，规划/06「功能对照待确认」）：不规范化的话，「+86 138…」与「138…」会算出两个哈希，同一个人可以注册两个账号，并绕过手机号唯一约束、黑名单与防重复领奖。
  - 函数 normalize_phone，服务端与三端、H5 落地页用同一份实现规格与同一份测试向量（`specs/phone-normalize.vectors.json`）。步骤：① Unicode NFKC（全角数字转半角）；② 删除全部空白字符（含 U+3000、U+00A0）、零宽字符（U+200B–U+200D、U+FEFF）与连字符（「-」及 U+2010–U+2015）；③ 去国家码：以「+86」开头，或以「0086」开头且其后恰为 11 位数字，或以「86」开头且其后恰为 11 位数字时，去掉该前缀；④ 结果必须匹配 `^1[3-9][0-9]{9}$`。不匹配（含其他国家码、位数不对、含字母）→ 20001，data.fields=[phone]、data.reason=phone_invalid，不发短信、不计入发码频控，文案见 BR-TEXT-14 表 B。
  - 用规范化后的值的地方（全部）：`users.phone_cipher` 与 `phone_hmac`（唯一约束，BR-INV-05）；验证码的 (手机号, purpose) 键与发码频控键（本条）；号段黑名单 sms.blocked_prefixes 的前缀比对；blocklist 的手机号维度（BR-ID-31，后台登记与导入时同样先规范化）；deleted_identities.phone_hmac（BR-ID-28、BR-ID-06）；并号与 30411 的判定（BR-ID-06）；落地页接口的幂等主体 `p:<phone_hmac>`（规划/04 §5）；客服工单的 contact_phone_hmac；后台按完整手机号查询用户。任何地方不得对未规范化的输入直接计算 HMAC。

**授权方式**（2026-10-03，功能对照 G-01；两种授权方式按功能对照 Q-04 第一问默认「两种都准备、以 09 实测为准」写，待负责人确认；账号名不显示已由负责人 2026-10-03 确认，docs/changes/20261003-拍板第三批.md §3；docs/changes/20261003-功能对照补缺.md）：

| auth_method | 用户侧流程 | bindings 请求体里的凭证 | 服务端怎样取得淘宝用户会话 |
| --- | --- | --- | --- |
| `web_code`（网页授权回跳） | 客户端用系统浏览器或淘宝客户端 SDK 的官方授权页打开 auth_url → 用户同意 → 回跳 App 带回授权码 | `code` | 用授权码换取会话 |
| `sdk_token`（客户端 SDK 换令牌，不回跳） | 客户端经淘宝客户端 SDK 完成淘宝登录与授权，SDK 直接返回访问令牌 | `access_token`、`expires_in` | 把访问令牌当作会话凭证（能否这样用即 CAP-TB-05 (f) 的待验证项） |

- 下发：30101 / 30102 的 data 与 auth-url 的响应都带 `auth_methods[]`（有序）。取值来自配置 union.taobao.auth_methods.&lt;ios \| android \| harmony>，默认 `["web_code"]`；客户端按顺序取本端能执行的第一种，不自行增减。`sdk_token` 要在 CAP-TB-05 (f) 对该端验证通过并经负责人确认后才写进生产配置；非生产环境按实验需要配置。两种方式都没有通过验证的端，淘宝按 规划/09 CAP-TB-05「不支持时怎么办」降级。
- 两种方式共用同一套 state 规则（绑定 uid + device_id + link_id，10 分钟，一次性）；bindings 先校验 state（30104），再取会话、调备案保存接口、做唯一校验（BR-ID-19）。
- state 记录本次下发的内容（2026-10-03，按评审补；第 2 轮修订）：服务端生成 state 时，除 uid、device_id、link_id 外，同时记下端、本次下发的 `auth_methods` 列表，以及每种方式所用的应用配置（用哪一个应用的标识与密钥去换取或使用凭证；只取服务端配置，不取客户端上报的任何应用标识）。端以设备记录为准：取这个 device_id 在 devices 表里登记的端；请求头 `X-Platform` 只是客户端的声明，与设备记录不一致时按设备记录处理并记风控日志，不按请求头选配置。state 只在签发它的环境里有效，配置按环境分别维护，非生产环境为实验打开的方式不会随 state 或客户端带进生产。
- 「按端下发」不是安全门：设备记录里的端来自设备注册时的声明，MVP 没有接入系统级的应用证明，服务端证明不了请求确实出自某个端的正式应用。按端配置的作用是不把没验证过的方式下发给相应的端，它挡不住把自己登记成另一个端的客户端。能当门用的只有两样：生产环境的配置只含验证通过并经负责人确认的方式；凭证是否属于所用的应用，由淘宝在换取或使用时判定——这一点依赖上游，登记为 CAP-TB-05 实验 (f) 的跨应用凭证反例，结论出来前不写成已验证。日后要把按端开放当成安全门，须先有可验证的应用身份依据（例如系统级的应用证明），另行立项。
- bindings 先校验、后消费：调用淘宝之前先做三项核对——① state 存在、未过期、未使用，uid、device_id 与请求一致；② 设备记录里的端与 state 记录的端一致；③ 请求的 `auth_method` 在 state 记录的下发列表里，并且此刻仍在该端的配置 union.taobao.auth_methods.&lt;端> 里（下发之后被关闭的方式同样拒绝）。任一项不过即拒绝（① → 30104；②③ → 30104，data.reason=method_not_allowed），state 保持原样：uid 或设备不符的请求不能把别人的 state 用掉，原持有人随后仍可提交。三项都通过，才把 state 从「未用」原子地改成「已用」（条件更新，并发提交只有一个成功），然后做 ④：用 state 记录的应用配置去换取或使用凭证。④ 的结果取决于淘宝：凭证无效、过期、已使用，或被淘宝判定不属于该应用 → 30104（data.reason=credential_invalid），此时 state 已用，不恢复。state 的存储不可用时拒绝（50001），不调用淘宝。生产配置只含验证通过并经负责人确认的方式，所以客户端自行提交没有下发的 `sdk_token`，在生产一定被 ③ 拒绝。
- 幂等键（2026-10-03，按评审补）：每一次绑定尝试用一个新的 Idempotency-Key。换了 state 或换了凭证就是一次新的尝试（包括 30104 之后重新发起的那一次），不得沿用上一次的键；只有同一个请求（请求体完全相同）因超时或断网没有收到响应而重发时才沿用原键，此时按幂等规则返回首次结果（BR-WDR-07）。带原键提交不同的请求体会得到 20901，带原键重发原请求体只会再次得到首次的 30104。
- 凭证无效：授权码或访问令牌无效、已过期、已使用，或该令牌不能用于渠道备案 → 30104（data.reason=credential_invalid），绑定状态不变，这个 state 同时作废。客户端重新调 auth-url 取新的 state，用新的幂等键发起新的绑定尝试：`auth_methods` 里还有下一种方式就改用下一种，没有就按 BR-ID-18 的授权失败处理。收到 method_not_allowed 时重新调 auth-url，只按新下发的 `auth_methods` 执行。服务端按「端 × auth_method」统计备案失败并告警，供调整配置。
- 只传凭证：bindings 请求体只有 `state`、`auth_method` 和上表的凭证字段。淘宝昵称、头像、淘宝用户 ID 以及 SDK 会话里的其他资料不上传，服务端不接收、不保存；请求体出现未定义字段返回 20001。授权码与访问令牌只在这一次备案调用中使用，不落库、不进日志。
- 淘宝账号名（负责人 2026-10-03 确认，docs/changes/20261003-拍板第三批.md §3：授权管理页只显示「已授权 / 未授权」，不显示淘宝账号名，打码形式也不显示，不新增收集项）：备案保存接口出参里的账号名直接丢弃，不保存、不下发、不显示；`GET /v1/unions/bindings` 只返回各平台的授权状态。不设显示开关；日后要显示须负责人另作决定，并先把这一项写进个人信息收集清单（06 Q-F1）。
- 待验证（规划/09 2_TB CAP-TB-05 (f)，结论出来前两种方式都不写成对用户的承诺）：SDK 换取令牌时用的应用标识能不能是联盟开放平台应用（规划/09 2_TB §2.5：百川应用拿不到淘宝客权限包，且与联盟应用分属两个淘宝账号）；该令牌能否作为备案保存接口的用户会话；`expires_in` 的实际值与是否一次性；两种方式对同一淘宝账号得到的 relation_id 是否相同；订单是否带回该 relation_id；三端 SDK 是否都提供这种换取方式。
- 例（web_code）：30101 的 data.auth_methods=["web_code"] → 客户端打开 auth_url → 回跳带 code → bindings `{state, auth_method: "web_code", code}` → active → 用新的幂等键重新发起 open。
- 例（sdk_token，仅在该方式已验证并配置后）：data.auth_methods=["sdk_token", "web_code"] → SDK 返回访问令牌 → bindings `{state, auth_method: "sdk_token", access_token, expires_in}`；服务端调备案接口被拒 → 30104（credential_invalid）→ 客户端重新取 state，用新的幂等键改走 web_code。
