# ADR-0002 PostgreSQL 托管用 Pigsty

- 状态：已采纳（负责人 2026-10-01 提议；2026-10-02 在选择题中确认「采纳 Pigsty，带退路」，并同意三项配套：staging 数据库节点交给代理操作、数据库 critical 告警夜间也发短信、prod 上线前开临时 ECS 预演三节点 runbook）。四项阻断验证（§10 第 1–4 项）任何一项在 staging 过不了即退回 RDS。
- 日期：2026-10-02
- 取代：ADR-0001 §2「数据库」「缓存」两行的云上托管方式（阿里云 RDS、云上 Redis）、§4.2 第 11 项的「按 RDS 规格复核」、§5 待核项里关于 RDS 与云上 Redis 的三条；`规划/02` §3.1 的 RDS、Redis 两行
- 被取代：无
- 相关：ADR-0001（版本线、角色、连接池、迁移与测试库规则不变）；`规划/02` §3、§12.6、§13、§14、§15.2、§20；`规划/05` B1-23～B1-26；`规划/06` Q-C21；`规划/11` §7.3 第 10 项、§9.3 #8

## 1. 背景

ADR-0001 把 staging 与 prod 的 PostgreSQL 定为阿里云 RDS（高可用 + 1 个只读实例），Redis 定为云上单实例，并留下几条要登录控制台才能核对的待核项。负责人 2026-10-01 提议改用 Pigsty 发行版管理 PostgreSQL。Pigsty 把 PostgreSQL、Patroni（自动切换）、pgBackRest（备份）、HAProxy、etcd 和一套监控打包成一份 Ansible 配置，装在自己的 Linux 机器上，v4.0.0 起为 Apache-2.0 许可。本文引用的 Pigsty 事实于 2026-10-01 对照 pigsty.io 文档与 `pgsty/pigsty` 仓库 v4.5.0 标签核实；只读过文档、没有在阿里云上跑过的，一律列入 §10，不当规则用。

采纳理由与代价：

- **权限不再受限**：ADR-0001 §4.2 第 4、8、14 项依赖 `SECURITY DEFINER` 函数、自建角色和迁移角色安装 pg-boss schema。RDS 的高权限账号不是超级用户（依据未逐字核对，§10 第 9 项），这三项在 RDS 上都还没核过；自建库有完整超级用户，不存在这个问题。
- **版本自己定，配置是一份文件**：云上与本地可以钉同一个大版本、同一个 pgvector 版本，不跟平台的内核发版节奏走。拓扑、参数、访问规则、备份策略都写在清单里，可以评审，可以先在 staging 跑，符合「代理做日常、负责人只做决定」。
- **随时能离开**：它就是标准 PostgreSQL（§8 退出路径）。
- **代价**：高可用、备份、告警、系统与数据库补丁的责任，从阿里云转到我们自己。§3–§7 就是为接住这份责任写的。

## 2. 决定

| 项 | 决定 | 版本线 | 说明 |
| --- | --- | --- | --- |
| PostgreSQL（staging、prod） | Pigsty 管理的集群，跑在阿里云 ECS 上 | Pigsty 4.5.x，首装 v4.5.0（2026-08-14 发布）；PostgreSQL 18，小版本以该版离线包为准 | 用离线包安装，不在线跟随上游软件源（文档强烈建议生产这样做）；升级先 staging 后 prod；已部署环境不重跑 `deploy.yml`。退版预案不变：staging 验证发现 PG 18 的离线包或 pgvector 有问题时退 PG 17（ADR-0001 §2），不改代码 |
| 操作系统 | Ubuntu 24.04 LTS，x86_64；同一集群各节点同版本，全新系统 | — | Pigsty 的验证基线之一；离线包绑定系统小版本，ECS 镜像要对得上（§10） |
| PostgreSQL（local、test、CI） | 不变：`pgvector/pgvector:0.8.6-pg18-trixie` 容器 | 同 ADR-0001 | Pigsty 需要 Linux 节点，不进开发机和 CI。大版本与云上一致，小版本允许不同 |
| 扩展清单 | 业务用到的扩展只由迁移里的 `CREATE EXTENSION` 建；云上版本须与本地镜像一致（现为 pgvector 0.8.6） | — | Pigsty 预置的 `monitor` schema 和约 15 个扩展是运维对象，不进 `db/schema.sql`；快照与漂移比对只针对由迁移重建的库（ADR-0001 §4.2 第 13 项不变） |
| Redis（staging、prod） | 也由 Pigsty 的 REDIS 模块管理：单实例，引擎 `redis`，与数据库同机 | Redis 7.x（同 ADR-0001） | 理由见下 |
| 配置存放 | 私有仓库 `rebate-private/ops/pigsty/`（清单、自写的告警规则、包装脚本、演练脚本）与 `rebate-private/ops/runbooks/`（中文操作手册） | — | 清单含内网地址与拓扑，不进公开仓库；密钥的值不进任何仓库（§7） |

**Redis 也交给 Pigsty 的理由**：Redis 只剩缓存、令牌桶、防重放，不可用时缓存路径直读 PG、写接口照常（`规划/02` §14），可用性要求低于数据库。用同一套工具管，监控与告警现成（自带规则的内存阈值正好是 ADR-0001 §4.2 第 17 项的 70%），staging 与 prod 配置相同，少买一个云产品，也省掉「云上 Redis 可选版本」这条待核。必须改掉四个默认值：淘汰策略改 `noeviction`、设口令、只监听内网地址、最大内存设 2GB。prod 的 Redis 固定放在三台中的一台，那台故障时应用按降级运行，负责人按 runbook 在另一台重建成空库：缓存可以再生，防重放与配额键清空后的口径待核（§10 第 7 项）。哪天改回云上 Redis 只是换一个连接串。公开后如果 Redis 停机的降级影响大，再评估主从加 Sentinel 或改回云上 Redis：Pigsty 里一个节点只能属于一个 Redis 集群，Sentinel 要另找节点放，不是在现有三台上改配置就行。

## 3. 拓扑分阶段

| 环境 / 阶段 | 节点 | 部署 | 自动恢复的 | 要人工的 |
| --- | --- | --- | --- | --- |
| staging | 1 台 ECS（2C4G 起，实测后调整） | Pigsty 单节点：数据库、etcd、监控各 1 份，同机 Redis；备份到 OSS | 无 | 整机或磁盘故障时从 OSS 备份重建。staging 允许停机 |
| prod：内测（M3）起，公开上架后不变 | 3 台 ECS（4C8G 起），跨两个可用区 2 + 1 | Pigsty 三节点高可用：每台各跑数据库、etcd、监控；1 主 2 从；同机 Redis 单实例 | 任意一台故障时的数据库切换（见下） | 同时失去两台；数据盘写满；误操作；Redis 所在机器故障后的重建 |

**3 台时的行为**（文档定的生产最小高可用；etcd 需要多数成员存活）：

- **主库所在的机器或进程故障，自动**：Patroni 把一台从库升为主库，HAProxy 把主库端口指向新主库。跨可用区按文档建议用 `pg_rto: safe`，文档口径最坏约 91 秒（未实测，§10 第 6 项）。旧连接会被断开，应用要重连（§5）。
- **一台从库故障，自动**：只读端口摘掉它；两台从库都不可用时只读端口回落主库。
- **一台机器上的 etcd 或监控故障，自动**：另外两台继续工作。
- **同时失去两台，人工**：包括失去放了 2 台的那个可用区。剩下的一台不会自动升主，数据库停止对外写入，要负责人按 runbook 恢复。这是两个可用区的固有限制；该地域如有第三个可用区，改为 1 + 1 + 1（§10）。剩下那台如果不是当时的同步从库，可能缺最后几笔已确认的事务：人工升主后先保持资金开关关闭，跑不变量 SQL 并与支付宝账单、联盟订单对账，再恢复写入（写进 runbook）。
- **数据丢失口径**：prod 用 Pigsty 的 `crit` 参数模板，同步提交，已向应用确认的事务在切换后不丢。代价是提交略慢，两台从库都不可用时写入会停住；3 台里只坏 1 台不触发这个情况。staging 单节点用默认的异步模板。实测不达标就退回异步，并在 runbook 写明切换后必须跑的对账（§10）。
- **不用两节点方案**：它只在一个方向自动切换，管理节点整机故障时主库的行为，文档两处说法不一。
- **对照 `规划/01` §7.2（RPO ≤5 分钟、RTO ≤1 小时）**：3 台里坏 1 台时自动切换，按文档口径满足（切换耗时待实测）。要从备份恢复的情形（同时失去两台且剩下那台也不可用、误操作、1 台起步期间整机故障）不保证达标：会丢掉最后一次 WAL 归档之后的写入，归档间隔和恢复耗时都还没测，恢复多快还取决于负责人多久能上线操作（§10 第 6 项）。
- **三节点的做法没法先在 staging 试**（staging 只有 1 台，代理不碰 prod）：prod 上线前先开临时 ECS 由代理预演一遍三节点 runbook 并修订手册（负责人 2026-10-02 同意）；之后三台装好、还没有真实数据时，由负责人把三节点的 runbook 各走一遍（主从切换、失去多数成员、时间点恢复、磁盘写满），代理按脱敏输出修订 runbook，之后才承接真实订单；走不通同样回到 RDS 方案（§9）。想让代理先预演，要另开 3 台按量付费的临时 ECS 当演练环境（花钱，且要 `规划/11` §7.3 第 10 项已确认，负责人定）。

| 时点 | 最低要求（内测与公开上架的差别） |
| --- | --- |
| prod 承接第一笔真实订单之前 | 目标是 3 台，默认等 3 台到位再接真实订单。负责人同意时可以先用 1 台起步，前提是 OSS 备份已通、恢复演练通过过一次；这期间整机故障要从备份重建，全站不可用，之后从 1 台扩到 3 台是带着真实数据做的生产操作，同样没法先在 staging 试 |
| 打开任一平台的 `credit.enabled` 或 `payout.enabled` 之前（真实资金进账本） | 必须已是 3 台，主库切换演练、恢复演练各通过一次，critical 告警短信实测收到 |
| 公开上架（M5）之前 | 台数不变；切换演练与恢复演练各再通过一次；按 QA-06 压测结果复核规格。上线后每季度做一次计划内主库切换，由负责人按 runbook 执行（`规划/02` §20） |

## 4. 备份与恢复

- **仓库**：pgBackRest 备份到阿里云 OSS 私有 bucket，staging 与 prod 各一个，各配一个只能读写该 bucket 的 RAM 用户，走内网地址；开加密（AES-256-CBC，口令 `cipher_pass`）。v4.5.0 一次只能启用一个仓库，选 OSS，不用默认的本机仓库（它和数据库在同一台机器上，机器坏了一起丢）。
- **策略**：每周一次全量、每天一次增量、WAL 持续归档。prod 按时间保留 30 天，staging 保留 14 天。文档给的口径是「周全量 + 14 天保留」可恢复约 14–21 天，30 天按同一规律约为 30–37 天，实测确认。原 RDS 方案是时间点恢复 7 天加每日快照 30 天，新口径不低于它。
- **防误删**：prod 清单设 `pg_rm_backup: false`（默认删主库时会连备份一起删）；bucket 开版本控制（与 pgBackRest 过期清理是否兼容待核）。
- **恢复方式**：能恢复到指定时间、LSN 或事务号。默认「恢复成一个新集群，核对无误后再切换」，原地覆盖只作最后手段；新集群要另开按量付费的 ECS 来放（花钱，事故时由负责人当场决定，runbook 写明规格与开通步骤）。恢复类命令在 prod 只由负责人经包装脚本执行（§7）。pg-boss 的任务在同一个库里，随备份一起恢复（ADR-0001 §3 不变）。
- **恢复后先对账再开资金**：恢复到过去的时间点，等于丢掉那之后的账本写入，而那之后已经打出去的款不会回来，库里的打款任务还可能再跑一遍。切到恢复出的库之前，`payout.enabled` 和各平台的 `credit.enabled.<platform>` 先关，用支付宝账单与联盟订单把缺的部分对齐，不变量 SQL 全过后再开（写进时间点恢复的 runbook）。

**自动恢复演练**（账本是最要紧的数据，每次演练都要留下记录；Pigsty 文档明确说，备份状态检查代替不了真实恢复）：

| 项 | 规定 |
| --- | --- |
| 频率 | staging 每周一次；prod 每月一次，另在每次升级 Pigsty 或 PostgreSQL 之后加一次 |
| 步骤与位置 | 从 OSS 仓库把库恢复到一个一次性实例（不归档、不对外服务），时间点取演练开始前 10 分钟。staging 在同机起临时实例；prod 默认在一台从库节点上起，先查剩余磁盘不少于库大小的 2 倍，不够直接判失败；它会和线上从库抢磁盘与内存，那台若正承担同步提交会拖慢主库写入，所以限速、避开高峰，演练完销毁实例。做法在 staging 验证，行不通或影响线上就改用按量付费的临时 ECS（花钱，负责人定） |
| 判定 | 四项全过才算通过：① 实例能启动并回放到目标时间点；② `db/invariants/` 的不变量 SQL 全过（BR-FUND-19）；③ 主库在目标时间点之前的最后一条分录和最后一条 `event_log`，在恢复库里都存在；④ 记下耗时，即实际恢复时长 |
| 记录与告警 | `rebate-private/ops/drills/records.csv` 每次一行：日期、环境、备份标签、目标时间点、耗时、四项结果、通过或失败、执行人或运行号。prod 的演练在生产环境内执行，代理只读这一行结果（这一行怎么从生产环境送到私有仓库待定，生产节点不放仓库的写凭据，§10 第 7 项）。演练失败，或超过期限没有通过记录（staging 8 天、prod 35 天），发 critical 告警（§6） |

## 5. 连接方式

清单里设 `pg_default_service_dest: postgres`，主库端口和只读端口都绕过连接池直连数据库（Pigsty 的 `ha/safe` 模板同样做法），与 ADR-0001 §4.2 第 11 项「不用 PgBouncer，咨询锁和通知需要会话模式」一致。应用和迁移都不连 6432：那是 PgBouncer 的事务池，会破坏会话特性；PgBouncer 进程保持默认不关（关掉对监控的影响未核实）。这个设置一旦被改回默认值，5433 会悄悄变成经事务池，会话级咨询锁失效而不报错：清单评审把它列为必查项，各进程启动时自检连接没有经过 PgBouncer，不通过就拒绝启动（做法在 staging 定，§10 第 4 项）。

| 使用方 | 数据库角色 | 端口 | 说明 |
| --- | --- | --- | --- |
| api、stream、worker、admin 主库池；pg-boss 与它们共用连接池 | `couli_app` | 5433（主库，直连） | 同事务入队、咨询锁、通知都可用 |
| payout | `couli_payout` | 5433 | 口令只有 payout 进程读得到（`规划/02` §12.6） |
| worker 的分区维护任务 | `couli_maint` | 5433 | 只能执行分区函数（ADR-0001 §4.2 第 4 项） |
| admin 报表的 `dbRead` | `couli_readonly` | 5434（从库，直连；无可用从库时回落主库） | staging 单节点时落在主库 |
| 迁移（发布流程里的迁移步骤） | `couli_migrator` | 5433 | DDL 只能到主库；口令只给发布流程的迁移步骤 |
| 运维与监控 | Pigsty 自带的 `dbuser_dba`、`dbuser_monitor`、`replicator` | 节点本机与管理节点 | 应用不得使用；口令属最高信任资产（§7） |

- **五个 `couli_*` 角色仍由 `db/bootstrap/roles.sql` 建**（ADR-0001 §4.2 第 8 项不变），不加入 Pigsty 的 `dbrole_*` 角色：加入后 Pigsty 的默认授权会让它们拿到超出设计的表权限，`couli_maint`、`couli_payout` 和只插入的分录表首当其冲。登录靠清单里自写的访问规则（`pg_hba_rules`）：按角色放行，强制 SSL 和口令认证。连接经 HAProxy 转发后，数据库看到的来源地址是节点自己而不是应用那台机器（按转发原理推断，未实测，§10 第 3 项），所以不指望用来源地址把 payout 或迁移同其他进程分开：来源限制靠安全组（只放行应用 ECS 与管理来源），角色之间靠各自的口令隔离。
- **连接池大小与入口地址**：池大小沿用 ADR-0001 §4.2 第 11 项，上线前按节点规格复核各进程之和（直连模式下 Pigsty 的最大连接数自动值是 1000）。staging 直接连那一台的内网地址；prod 默认在三台节点的 HAProxy 前放一个内网负载均衡，应用只认它的地址（§10）。
- **切换时**：旧主库上的连接被强制断开。连接池要开 TCP keepalive，出错后重建连接；进行中的事务回滚后按现有幂等规则重试；咨询锁随连接消失，代码不得假定锁能跨连接保持。切换演练要验证这三点（B1-26）。

## 6. 监控与告警

- **复用 Pigsty 自带的监控**（Grafana、VictoriaMetrics、VictoriaLogs、Alertmanager）：数据库、Patroni、etcd、主机、Redis、pgBackRest 的指标和日志都在里面。应用日志、链路、崩溃采集不变。指标与日志默认各留 15 天。应用的业务指标（`规划/02` §13）是否也并入这一套、不再另买托管 Prometheus，等 staging 核对后再定，核对前 `规划/02` §13 的业务指标行不变：资金类业务告警不宜和数据库节点同生共死，Pigsty 接自定义采集目标和规则的做法也没核过（§10 第 8 项）。
- **通知要自己接**（B1-25）：Pigsty 的 Alertmanager 默认接收器是空的，不发任何通知。自带规则直接用：数据库宕机、复制延迟、事务号回卷、连接数过高、数据盘超过 90%、内存不足、时钟漂移、etcd 无主、Redis 内存超过 70% 等。
- **自己补的规则**（v4.5.0 没有任何备份相关告警）：最近一次成功备份超过 26 小时；WAL 归档失败或积压；恢复演练失败或超期；监控心跳丢失；发生了主从切换（自带规则已覆盖的不重复加）。

| 级别 | 包含 | 去向 |
| --- | --- | --- |
| critical | 主库不可写、发生了主从切换、etcd 无主或失去多数、数据盘超过 90%、备份过期或 WAL 归档失败、恢复演练失败或超期、事务号回卷预警、监控心跳丢失 | 短信发到负责人手机，同时推企业微信告警群 |
| warning | 复制延迟、连接数高、内存不足、Redis 内存 70%、时钟漂移等 | 只推企业微信告警群，按 `规划/02` §13 的夜间规则汇总 |

- **短信怎么发**：比照站长联盟授权告警（BR-ID-24：到期或失效时发短信并在后台告警），走阿里云短信。不同点是这条路不能依赖被监控的数据库：Alertmanager 把告警发给一个不连 PG 和 Redis 的小转发器，它跑在数据库节点以外的 ECS 上，号码和模板从环境配置读。监控自己坏了也要能知道：Alertmanager 持续发一条心跳，转发器 10 分钟收不到就发短信「监控失联」。数据库节点不绑公网地址，企业微信群消息也只能经转发器发出，所以转发器是全部数据库告警的唯一出口，要有第二条路：用阿里云云监控盯转发器所在 ECS 的存活，并给数据库 ECS 的宕机、磁盘使用率各设一条报警，短信发到同一个手机（云监控的免费额度和短信设置待核，§10 第 8 项）。
- **夜间**：`规划/02` §13 定的是夜间只推资金类（拍板第二批 TECH-15）。本文把 critical 级按资金类对待，因为账本所在的库不可用或备份失效就是资金风险。这扩大了夜间范围，要负责人确认；确认前按「发」实现并做成开关。

## 7. 运维边界

代理不连生产库、不登录生产节点，这条不变（`规划/00` §9、`规划/02` §12.7）。

| 环境 | 谁改配置 | 谁执行 | 凭据 |
| --- | --- | --- | --- |
| staging | 代理在 `rebate-private/ops/pigsty/` 提改动，另一家模型评审 | 现行：负责人按中文 runbook 执行一条包装命令，代理读脱敏后的输出。`规划/11` §7.3 第 10 项经负责人确认后：Claude 编排会话用 staging 专用密钥直接执行 | 与 prod 完全不同的一套口令和密钥 |
| prod | 同上，按 RV2 评审（涉及生产数据） | 只由负责人：在生产管理节点按中文 runbook 执行包装命令（先打印将要做的事，输入确认词后才执行）。以后若想换成由负责人点批准才运行的流水线，属硬边界变更，届时另走 `规划/11` §7.3 批准栏，本文不预先放行 | 对代理不可见 |

- **密钥**：清单里的口令字段只写占位，值放在管理节点上的密钥文件里，不进仓库，KMS 凭据管家留一份副本。备份加密口令 `cipher_pass` 和自签 CA 的私钥，负责人另外离线保存一份：丢了 `cipher_pass`，全部备份不可恢复。首装用 `./configure -g` 把默认口令随机化，它不覆盖 `cipher_pass`，要单独设。管理用户的 SSH 私钥等于所有节点的 root，同样只在负责人手里。
- **保护开关与加固**：prod 清单显式打开 `pg_safeguard`、`etcd_safeguard`、`redis_safeguard`（默认都是关）。时间点恢复的 playbook 不等确认就覆盖数据目录，删除集群的 playbook 默认连备份一起删，这两个在 prod 只能经包装脚本运行。Pigsty 的默认配置面向可信内网的开发和演示，生产按 `ha/safe` 模板加固：强制 SSL、口令强度检查、备份加密；删掉单节点模板对公网开放的 5432；数据库节点不绑公网地址，安全组只放行应用 ECS 和管理来源。
- **分工与 runbook**：代理每周核对备份与演练记录、看告警记录（只读转发器留下的告警清单和演练记录，不登录 prod 的 Grafana 与日志，数据库日志里可能带业务数据）、准备补丁升级的改动（先 staging）、维护 runbook；负责人执行 prod 命令、接短信、保管离线密钥。runbook 用中文写，放私有仓库（B1-24、B1-26 交付）：首次安装（含怎么登录管理节点、上传离线包、生成并离线留存密钥）、时间点恢复、整机重建（含管理节点丢失）、主从切换、失去多数成员、磁盘写满、补丁升级、Redis 重建、从 1 台扩到 3 台。每份 runbook 交付前至少照着执行过一遍；三节点的那几份在 prod 没有真实数据时走（§3）。
- **还没定的两步**（§10 第 8 项）：负责人怎么登录生产管理节点（节点没有公网地址，候选是阿里云控制台的远程连接）；评审过的清单怎么送到生产管理节点（节点上不放私有仓库凭据），包装脚本执行前要核对清单与评审通过的版本一致。

## 8. 与 RDS 的取舍

| 维度 | 改用 Pigsty 得到的 | 改用 Pigsty 后自己承担的 |
| --- | --- | --- |
| 权限与扩展 | 完整超级用户；扩展和版本自己定；ADR-0001 的角色与函数设计不必再核 | 权限配错没有平台兜底，靠评审和 staging |
| 高可用与备份 | 切换逻辑、备份策略、保留期、加密都看得见、可以演练；能随时克隆出一个库来核对 | 至少 3 台才有真正的自动切换；没有平台 SLA；备份失败没人替我们发现，告警和恢复演练必须自己建（§4、§6） |
| 监控与日常运维 | 仪表盘和日志比云控制台深，业务指标可并入；配置是文件，代理可以准备和核对 | 通知要自己接，监控栈自己养；系统补丁、数据库小版本、磁盘、证书轮换、etcd、Pigsty 自身升级都归我们；大版本升级要新建集群加逻辑复制 |
| 费用 | 没有 RDS 的托管溢价，Redis 不单独买 | 多 3 台 ECS、云盘、OSS 备份、内网负载均衡，恢复和大版本升级时还要临时 ECS；总额还没按规格重算（`规划/02` §15.2），不能当作比 RDS 省钱；隐性成本是运维时间和事故风险 |
| 供应方风险 | 开源，不锁定云厂商 | 项目主要由一人维护，原公司主体已清算；开源版无担保，支持只有社区 |

**退出路径**：数据库是标准 PostgreSQL，应用只认连接串。要回 RDS（它已支持 PG 18，高可用系列是否支持未核实），用逻辑复制或导出导入迁过去，改连接串即可。Pigsty 停止维护时，装好的 PostgreSQL、Patroni、pgBackRest 都是独立的开源软件，可以继续运行；离线包留存一份。

## 9. 影响

- **消失的**：ADR-0001 §5 的三条待核（RDS PG 18 高可用系列与 pgvector；RDS 是否允许 `SECURITY DEFINER` 函数与自建角色；云上 Redis 可选版本）。`规划/11` §9.3 #8 的 RDS 控制台核对。`规划/02` §3.1 的 RDS、Redis 两行和 §15.2 对应的两行成本。`规划/06` Q-C21 里的 RDS、Redis。
- **新增的**：任务 B1-23（staging 建库）、B1-24（备份与恢复演练）、B1-25（告警外发）、B1-26（prod 上线）。`规划/02` §12.6 的数据库与运维密钥、§13 的数据库告警、§14 的主库故障行、§20 的 runbook 与演练项。`规划/11` §7.3 第 10 项（待负责人确认）。§10 的验证项。
- **不变的与受影响的**：ADR-0001 的版本线、五个角色、连接池规则、迁移与测试库做法、本地栈和 CI 都不变；应用代码不感知 Pigsty，区别只在连接串和端口。要改的只有 platform 模块的连接池配置（加 keepalive 和断线重建）、QA-05 故障注入（加一项主库切换）、`规划/02` §20 的演练（改为主从切换加备份恢复）。
- **迁移步骤与回退**：现在没有任何已部署的数据库，不存在数据迁移，按 B1-23 → B1-24 → B1-25 → B1-26 的顺序建。§10 标「阻断」的项在 staging 过不了，或 B1-26 的三节点演练在 prod 还没有真实数据时走不通，就回到 ADR-0001 原方案（RDS），本文标作废，损失是已花的工时和 ECS 费用。上线后要离开按 §8 的退出路径。

## 10. 待核

都是只读过文档、没有在阿里云上实测的，在 staging（B1-23、B1-24）核对后把结果补进本文，不另开 ADR；只有三节点才测得了的（第 5、6 项）在 prod 上线前、还没有真实数据时测（B1-26）。标「阻断」的过不了就不上 prod。

1. **阻断**：v4.5.0 离线包在阿里云 ECS 的 Ubuntu 24.04 上能装（ECS 镜像的系统小版本与离线包是否对得上；开源版离线包的范围，订阅页与安装文档说法不一）；离线包里 PostgreSQL 18 的具体小版本；pgvector 0.8.6 可用。
2. **阻断**：OSS 作 pgBackRest 仓库：内网备份、增量、时间点恢复、克隆成新集群全流程；RAM 用户最小权限；30 天保留的实际恢复窗口；bucket 版本控制与过期清理是否兼容。
3. **阻断**：五个 `couli_*` 角色不加入 `dbrole_*`、只靠自写访问规则登录时，权限与 ADR-0001 §7 的实测一致；`dbuser_monitor` 读得到哪些业务表；经 HAProxy 连接时数据库看到的来源地址是什么（决定访问规则能不能按来源区分）。
4. **阻断**：5433 / 5434 直连下 pg-boss、咨询锁、同事务入队正常；进程启动时怎么自检连接没有经过 PgBouncer；断线后各进程自动重连、任务不丢（staging 单节点用重启数据库来模拟，真正的主库切换在 B1-26 验）。
5. prod 入口：内网负载均衡转发到 HAProxy 是否可行，它的空闲超时会不会切断连接池里的长连接；备选是集群域名或多主机连接串（node-postgres 是否支持未核实）；虚拟 IP 在阿里云上文档没有指引。
6. 高可用实测：`crit` 同步提交的提交耗时、一台从库故障时写入的停顿；`pg_rto: safe` 的切换耗时（文档两处平均值不一致）；两个可用区 2 + 1 时，失去放 2 台的可用区后的人工恢复步骤；目标地域是否有第三个可用区；WAL 归档间隔与从备份恢复的实际耗时，对照 `规划/01` §7.2 的 RPO、RTO。
7. 资源与同机：监控栈在 4C8G 上占多少（文档没有数字）；PG 与 Redis 同机时内存怎么分；staging 用 2C4G 够不够；REDIS 模块的持久化默认值（RDB 开、AOF 关）下，重启后防重放与配额键的恢复口径；prod 恢复演练在从库节点起临时实例的做法和对线上的影响；prod 的演练记录怎么送到私有仓库。
8. 外发与密钥：企业微信群机器人是否要适配器；备份类规则用到的 `pgbackrest_exporter` 指标名；转发器的实现；三台各有一份监控时同一条告警会不会重复发、怎么去重；阿里云云监控作第二条路的额度与短信设置；应用业务指标能否作为自定义采集目标接入；数据库日志里的慢查询语句会不会带个人信息，留存是否符合 BR-ID-30；清单口令字段改为从管理节点密钥文件注入，Pigsty 的各个 playbook 是否都认；负责人登录生产管理节点的方式；评审过的清单送到生产管理节点的方式。
9. 没核到的依据：境内镜像站从 ECS 访问的连通性与速度；GitHub 上的已知问题没有读到（接口限流）；RDS 侧两条对比依据未逐字核对原文（高权限账号不是超级用户；高可用系列是否支持 PG 18）。

**staging 首装实测**（2026-10-07，B1-23 第一段；节点与配置记录在私有仓库 `rebate-private/ops/pigsty/staging/`）：

- 云：staging 节点由负责人在**火山引擎**采购（4C8G、Ubuntu 24.04、x86_64，系统盘 20G + 数据盘 30G），不是本文写的阿里云；prod 用哪家未定，按本文继续以阿里云为默认，换云时补 ADR。备份仓库在阿里云 OSS 与火山 TOS 之间由负责人选定后再接（跨云走公网有流量费）。
