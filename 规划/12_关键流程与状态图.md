### 0.3 名词

- **双状态**：「我方统一订单状态」= 子订单上的 `platform_status`（order-sync 唯一写者）+ `rebate_status`（settlement 唯一写者）；用户看到的 `display_status` 由二者加 `hold`、`rights_pending` 派生、不入库（BR-FUND-01、BR-FUND-17）。
- **同一事务**：图中 `critical` 块内的写入要么全部提交、要么全部回滚；领域事件与任务在同一事务入队，提交后才可被取走（02 §11）。
- **幂等键**：标 I 的接口必须带 `Idempotency-Key`，落 `idempotency_keys`；同键处理中 40901、同键不同请求体 20901、同键已完成原样返回首次结果（成功与 3xxxx 业务错误都写入，1xxxx、2xxxx 不写；04 §5）。
- **CAS 冲突**：状态迁移一律 `UPDATE … WHERE status=:from`；影响 0 行时重读，按迁移表重新判定——已被并发处理成同一结果就幂等结束，仍可迁移就重做，变成表外事件才按非法迁移处理（02 §18）。
- **身份主人**：一次转链所用归因身份属于谁。自己的 link 是当前用户；分享 link 是分享者；`no_rebate` 购买没有身份主人（BR-ATTR-05、BR-ID-18）。

## 1. 订单生命周期（双状态）

「我方统一订单状态」是子订单上两个互相独立的状态（BR-FUND-01，已确认）：`platform_status` 只由 order-sync 按平台状态码映射驱动；`rebate_status` 只由 settlement 迁移。`hold`、`rights_pending` 是 settlement 写的标志位，不改 `rebate_status`（BR-FUND-06）；用户看到的 `display_status` 由二者加标志位与金额派生、不入库（§1.4）。迁移一律 CAS（`row_version` 加 1），同一子订单按 `order_key` 取 `pg_advisory_xact_lock` 串行；CAS 冲突与表外事件的处理不同，见 §0.3 与 §3.2。

下面两张状态图只画「从、到、迁移编号与事件」；守卫、记账与副作用以 BR-FUND-01 迁移表为准（测试 ID `SM-PLT-P<n>`、`SM-REB-R<n>`）。事件名在 08 多为中文标签，只有 02 §7.2 的 `PLATFORM_*` 与 rebate 侧的 `CLAIM_APPROVED` 等有编码（§9 O-02）。

- [x] 乱序与重复回传（§3.2）
- [ ] 入库首态为 RECEIVED、SETTLED、INVALID，跳级迁移，同状态更新：08 未定义（§9 O-01、O-04），画不出

**覆盖的异常情况**

- [x] 入库时未归因、之后被同步重跑归因（R3a）或找回、改派（R3，置 `locked`）
- [x] 已作废且未归因的订单被找回或改派（R3b：只补归属，不生成快照、无分录；找回路径是否走得到见 §9 S-08）
- [x] 入账前失效、部分退款、佣金变化（R6、R7，无分录，§4.1）
- [x] 入账后全额或部分扣回、佣金变化、结算补差（R8、R9、R9b、R10，分录与迁移同一事务，§4.5、§4.6、§4.7）
- [x] 售后中或风控、客服暂停（`rights_pending`、`hold` 只做标志，月结时暂缓或跳过，§4.2、§4.4）

## 2. 点击 → 转链 → 外跳 → 归因

出卡（搜索、详情、首页、识别、Agent）只登记 `link_id` 与报价快照、不转链；点击购买一律走 `POST /v1/links/{link_id}/open`（拍板第二批 TRADE-03）。`POST /v1/links/convert` 只供没有 link_id 的 H5 入口（`trade.convertAndOpen`），同一请求内登记 link 后按 open 同样处理。京东、拼多多在服务端转链；淘宝不调链接 API，open 下发百川打开指令、由客户端百川 SDK 完成淘客转链（变更记录 20261003，BR-ATTR-05、BR-ATTR-27 淘宝说明）。

open 要求设备签名，所以「分享链接可匿名打开」指 **App 内未登录**的用户；App 外（微信、浏览器）没有签名与桥，走不签名的 `GET /v1/share-pages/{link_id}`（§2.8）。

服务端判定拆成两张路由图（§2.1、§2.2），客户端对响应的处理三平台共用一张（§2.3），之后每个平台一张（§2.4–§2.6）只画该平台特有的步骤与归因交接。

## 4. 佣金：预估 → 月结 → 入账 → 扣回，与余额

资金流向（02 §17）：settlement 只产出记账指令；ledger 是唯一改余额处；金额只由 `packages/domain` 计算。订单相关的余额与分录只能在该子订单 `rebate_status` 迁移（含自迁移）的同一事务内变更，不依赖领域事件（BR-FUND-01）。分录模板、uniq_key 格式与金额口径只在 08（BR-FUND-05、BR-FUND-08、BR-FUND-09）与 `specs/ledger-rules.md` 维护。

「联盟结算」与「用户入账」是两个节点：平台状态到 SETTLED 不等于入账，入账要等月结账单校验通过、人工确认后的批次执行（§4.2–§4.4）。业务扣回（CLAWBACK，§4.5）与纠错红冲（uniq_key 加 `:REVERSE`，BR-FUND-16）是两回事，后者只用于改派（R14）与调账更正。

### 4.1 预估与入账前的变化

预估阶段不写任何分录、不动 `account_balances`（BR-FUND-03）。下图是 settlement 命令对一个尚未入账的子订单处理一次事件，事务由调用方持有（订单同步见 §3.2）。

```mermaid
sequenceDiagram
  autonumber
  participant W as 调用方（order-sync、rights-imports）

    T-)N: ORDER_TRACKED（各受益人各推自己的份额，首次预估为零不推，BR-TEXT-09、BR-FUND-03）
```


### 4.4 单个子订单的入账事务（R5、R5a）

批次里有两类项：首次入账（订单为 WAITING，R5）与受益人补入账（订单已 CREDITED、该受益人的暂缓已解除，R5a）。**先判定每个受益人怎么处理，再写互斥的凭证**：正常入账、暂缓不入账、失效记平台，三者只取其一。

```mermaid
sequenceDiagram
  autonumber
  participant T as settlement（settle.batch_execute）
  participant DB as PG（orders、commission_split_*、settle_batch_items）
  participant M as commission（packages/domain 拆分）
  participant L as ledger
  participant EV as 领域事件

  T->>DB: 开事务，pg_advisory_xact_lock（order_key），重读订单、结算记录 seq、分佣快照当前版本
  break 首次入账项的守卫不过：已不是 WAITING，或 hold、rights_pending 为真，或结算记录 seq 与校验时不一致（BR-FUND-04 ⑦）
    T->>DB: settle_batch_items 记 skipped 与原因，订单保持原状，留给后续批次
  end
  break 补入账项的守卫不过：订单不是 CREDITED，或该受益人仍在暂缓
    T->>DB: 记 skipped，留给后续批次
  end
  break 入账基数为空（未知）
    T->>DB: 跳过并告警，不按零入账（BR-FUND-17）
  end

  critical 同一事务记账
    T->>L: 涉及的 account_balances 按 account_id 升序 FOR UPDATE（BR-FUND-16。users 行的加锁顺序见 §9 F-03）
    alt 首次入账（R5）
      loop 每个受益人份额
        alt 正常（含注销冷静期）
          T->>L: 该受益人一张凭证，贷 USER_BALANCE.available（份额为零不写）
        else 已注销、封禁，或未成年人的推广份额

        else 冻结或账户申诉中
          T->>DB: 追加 held 事件，本次不入账，解除后走补入账
        end
      end
      T->>L: 平台留存一张凭证（尾差归平台）
      T->>DB: rebate_status → CREDITED（CAS），写 booked_base_fen
      T-)EV: order.credited（同事务入队）
      T->>DB: settle_batch_items 记 credited
    else 受益人补入账（R5a，订单保持 CREDITED）
      alt 暂缓已解除且状态正常
        T->>L: 该受益人单独一张凭证，uniq_key 沿用其入账键，只入一次
      else 已转为封禁
        T->>L: 份额记平台，追加 forfeited 事件
      end

  option 凭证借贷不平
    T->>T: 整单回滚并告警，订单保持原状
  end
  Note over T,L: 入账基数为零时只迁移状态，不写凭证、不推送（BR-FUND-05）。暂缓满时限只告警，不自动入账也不自动剥夺（BR-CALC-13）
```

- [x] 受益人注销、封禁、未成年（份额记平台，不入其账户）；冻结或申诉中（暂缓，其余受益人照常）

### 4.5 入账后扣回（R8、R9）

CREDITED 的子订单收到逆向事件时，扣回凭证与状态迁移在触发方的同一事务内完成（订单同步 §3.2、维权导入、后台复核确认）。判定顺序：先认出确定归零的事件，再给其余事件取新基数；先定每个受益人的扣回记到哪里，再写凭证。

```mermaid
sequenceDiagram
  autonumber
  participant X as 触发方（order-sync、rights-imports、后台复核确认）
  participant T as settlement（命令）
  participant M as commission
  participant L as ledger
  participant P as payout 模块（evt 消费者）
  participant N as notification

  X->>T: CREDITED 子订单的逆向事件（退款、维权成功、处罚、平台失效、结算后退款或失效、佣金由正变零、BLACKLIST_CONFIRMED）
  break 同一事件重放（该事件的 uniq_key 已存在）
    T->>T: 不写，幂等结束
  end
  alt 整单类事件（R8：整单失效、全额维权成功、处罚、结算后失效、黑名单复核确认）
    T->>T: 新基数取零，不看本次有没有带佣金字段
  else 其余事件（部分退款、部分维权等），且本次自带联盟新佣金
    T->>T: 新基数取该值（为零时同样走 R8）
  else 其余事件，order_rights 记录了应扣佣金
    T->>T: 新基数按应扣佣金算出（算法见 BR-FUND-08 ②）
  else 其余事件，两者都没有
    T->>T: 新基数未知
  end
  break 新基数未知
    T->>T: 不写扣回，order_rights 置 WAIT_COMMISSION，订单进待处理表并告警，等联盟回传新佣金（BR-FUND-08）
  end
  T->>M: 按新基数与快照重拆，算各受益人应扣额与平台留存差额
  break 各受益人与平台的差额都为零
    T->>T: 不写
```

```mermaid
  W->>DB: 按建单同样的顺序加锁，advisory 锁 auto_payout_daily 内把 BR-WDR-30 ①–⑬ 全部检查一遍
  W->>DB: 写 auto_decision（结果、全部未满足的条件、规则版本）与 review_mode
  alt 判 manual（任一条件不满足。系统不自动驳回）
    W->>W: 单据留在 PENDING_REVIEW，转人工审核（§5.3）
  else 判 auto
    W->>DB: W2 APPROVE（CAS，条件是仍为 PENDING_REVIEW，操作人记系统自动到账）
    alt CAS 影响 0 行（人工已先处理）
      W->>W: 只保留 auto_decision，不建批次，结束
    else CAS 成功
      W->>DB: 为该单建 payout_batches（kind=auto），做执行前置检查（BR-WDR-12 ①–③）
      alt 前置不过：打款开关关闭、队列暂停、会员提现阻断、已有转账尝试、通道未开通、水位不足
        W->>DB: 单据留在 APPROVED，auto_decision 追加 execute_blocked 与原因，转人工批次。系统不自动重试执行
      else 前置通过
        W->>DB: W4 EXECUTE → PAYING（CAS），execute_seq 加 1
        W-)Q: 同事务入队 payout 任务，去重键为 withdrawal_id 加 execute_seq（→ §5.4）
      end
    end
  end
  Note over W,DB: 判 auto 后留在 APPROVED 的单怎么从 auto 批次转入人工批次，08 没写，待定：见 §9 W-03
```

**覆盖的异常情况**

- [x] 事件重复投递（只判定一次）
- [x] 自动判定与人工审核抢同一单（CAS 影响 0 行就结束，不建自动批次）
- [x] 任一条件不满足转人工，不自动驳回
- [x] 判 auto 后执行前置不过（留在 APPROVED，转人工批次，不自动重试）
- [x] 银行卡通道未开通（判定时即转人工，BR-WDR-30 ⑪）

**实现的 BR / AC**：BR-WDR-08（W2、W4）、12、29、30；拍板第二批 FUND-02、FUND-08；AC-S2-53。

### 5.3 人工审核与批次执行

```mermaid
sequenceDiagram
  autonumber
  actor U as 用户
  participant F as 财务（后台，step-up）
  participant A as admin·payout
  participant L as ledger
  participant Q as payout 队列
  participant N as notification

  F->>A: /admin/v1/withdrawals 审核一张 PENDING_REVIEW 单（BR-WDR-10）
  break 驳回（W3，必填原因码）
    alt CAS 影响 0 行（自动判定或另一人已处理）
      A-->>F: 20902（data.resource=withdrawal）
    else 成功
      A->>L: 同一事务 → REJECTED，WITHDRAW_RETURN（frozen 退回 available）
      A-)N: 提现未通过通知
    end
  end
  break 审核通过的守卫不过：余额为负，或 blocked_reason 非空（BR-WDR-05）
    A-->>F: 拒绝
  end
  break CAS 影响 0 行（自动判定或另一人已处理）
    A-->>F: 20902（data.resource=withdrawal）
  end
  A->>A: W2 → APPROVED，写 reviewer_id、reviewed_at
  F->>A: /admin/v1/payout-batches 对勾选的 APPROVED 单建 kind=manual 批次并执行（一人可完成，BR-WDR-11、12）
  break 批次级前置不过（打款开关关闭、队列暂停），或可执行集合水位不足（BR-WDR-18）
    A-->>F: 整批拒绝，不迁移任何单
  end
  loop 批次内每张单
    alt 不满足逐单条件：已不是 APPROVED（如同时被驳回）、会员提现阻断、已有转账尝试、收款通道未开通
      A->>A: 保持原状，执行结果里列出原因
    else 满足
      A->>A: W4 → PAYING（CAS），写 executor_id、batch_id、executed_at，execute_seq 加 1
      A-)Q: 同事务入队 payout 任务（去重键含 execute_seq，→ §5.4）
    end
  end
  opt 留在 APPROVED 的单线下打款后补录（银行卡通道未开通，或已有转账尝试只能手动成功）
    F->>A: W8 MANUAL_PAID 录入并确认（流水号、实付时间、实付金额，BR-WDR-16）
    alt 守卫不过：存在 pending、success、unknown 的转账尝试，或会员提现阻断，或流水号已用过，或实付不等于应付净额
      A-->>F: 拒绝
    else CAS 影响 0 行（同时被执行或驳回）
      A-->>F: 20902
    else 成功
      A->>L: 同一事务 → PAID_MANUAL，成功分录一张凭证（WITHDRAW_PAID、WITHDRAW_FEE、TAX_WITHHOLD），更新 tax_ytd
      A-)N: 提现成功通知
    end
  end
  opt 审核通过后要驳回（W3 from APPROVED）
    F->>A: 驳回
    alt 该单存在 pending、success、unknown 的转账尝试
      A-->>F: 拒绝驳回，只能按 §5.5 的人工处置结束
    else 没有，或只有失败的尝试
      A->>L: 同一事务 → REJECTED，WITHDRAW_RETURN
    end
  end
  opt 用户想撤销（不能自撤，拍板第二批 FUND-20）
    U->>F: 联系客服建工单 withdraw_cancel，财务以 USER_REQUEST 驳回
  end
```

**覆盖的异常情况**

- [x] 驳回（冻结额退回，不再往下走）
- [x] 余额为负或被阻断时不得审核通过
- [x] 审核与自动判定、驳回与执行、执行与手动成功互相并发（都以 CAS 判定，后到者 20902 或保持原状）
- [x] 批次级前置不过、水位不足（整批拒绝）
- [x] 批次内个别单不可执行（逐单独立，不整批重跑）
- [x] 银行卡通道未开通（跳过执行，线下转账后 W8 补录）
- [x] 已有转账尝试的单不得再执行、不得随意驳回
- [x] 用户撤销（客服工单加驳回）

**实现的 BR / AC**：BR-WDR-05、08（W2、W3、W4、W8）、09、10、11、12、16、18、32；拍板第二批 FUND-20、§8 ADD-04、ADD-05；AC-S2-20、AC-S2-23、AC-S2-28、AC-S2-29、AC-S2-54、AC-S2-59；AC-WDR-05、AC-WDR-06。

### 5.4 payout 任务：复核与转账

payout 进程是唯一持有通道密钥的进程，没有公网入站，所以**不接收支付宝异步通知**，结果只靠同步返回、主动查询与每日对账（是否接通知见 §9 W-08）。

```mermaid
sequenceDiagram
  autonumber
  participant Q as payout 队列
  participant P as payout 进程
  participant DB as PG（withdrawals、payout_attempts、ledger_*）
  participant Z as 支付宝开放平台

  Q->>P: 取任务（去重键为 withdrawal_id 加 execute_seq。转账任务不自动重试，单并发，BR-WDR-13）
  P->>DB: 读单据
  break ① 单据不是 PAYING，或任务的 execute_seq 不是单据当前值（重复或过期任务）
    P->>P: 直接结束，不转账也不查询
  end
  break ② 该单已有 kind=transfer 的尝试记录（进程在请求发出后崩溃重启、任务被重投）
    P->>P: 不转账，转入 §5.5 的查询
  end
  P->>DB: 在 advisory 锁 payout_daily 内按序复核（BR-WDR-13 ③，开关直读 PG）
  break ③ 复核不过
    P->>DB: W9 HOLD → APPROVED（CAS），写 hold_reason（payout_disabled、queue_paused、member_blocked、single_cap、daily_cap 之一）与 hold_at，清空执行人与执行时间
    Note over P,DB: 这类单没有转账尝试，条件恢复后可以再次执行（新任务的 execute_seq 加 1）。因余额为负被阻断的，回到 APPROVED 后按 §5.7 驳回
  end
  P->>DB: ④ 同一把锁内写 payout_attempts（kind=transfer，result=pending）并提交（先记后发）
  P->>Z: ⑤ alipay.fund.trans.uni.transfer（out_biz_no、收款账号与姓名取单据快照。场景字段与证书签名见 09 §5.3，待 CAP-X-06）
  Note over P,Z: 通道调用在事务之外，不持有行锁。结果另开事务写回
  alt 明确成功
    P->>DB: 同一事务 W5 → PAID_API（CAS），记通道单号与到账时间，写成功分录一张凭证（BR-WDR-09），更新 tax_ytd，尝试记 success
  else 返回码在 payout.definite_fail_codes 内（验证前清单为空，BR-WDR-28）
    P->>DB: 同一事务 W6 → FAILED，WITHDRAW_RETURN，记 fail_code，尝试记 fail
  else 返回码在 payout.payer_side_codes 内（验证前清单为空）
    P->>DB: W9 → APPROVED，hold_reason=payer_side_after_transfer，不退回余额，置 payout.queue_paused 并告警
    Note over P,DB: 这张单已有转账尝试，不得再执行，只能手动成功（W8）或驳回（W3），BR-WDR-17
  else 返回了三份清单之外的业务码
    P->>DB: 按结果未知处理：保持 PAYING（W7），尝试记 unknown。同时置 payout.queue_paused 并告警（BR-WDR-28）
  else 超时、网络错误、HTTP 5xx、SYSTEM_ERROR
    P->>DB: 结果未知：保持 PAYING（W7），尝试记 unknown
  end
  opt 结果未知（后两种）
    P->>P: 排入 §5.5 的查询。任何情况下都不再调转账接口，不换 out_biz_no（BR-WDR-14）
  end
```

**覆盖的异常情况**

- [x] 重复或过期任务（直接结束）
- [x] 已发出过转账的单再次被取到（只查询，绝不到达转账调用）
- [x] 发出前复核不过（W9，不到达转账调用；没有转账尝试，可再次执行）
- [x] 进程在请求发出后崩溃（先记后发，重启后只查询）
- [x] 明确成功、明确失败、付款方侧失败（暂停队列，不退回）
- [x] 清单外的业务码（按未知处理，并暂停后续出款）
- [x] 超时、网络错误、5xx、SYSTEM_ERROR（只查不重提）

**实现的 BR / AC**：BR-WDR-08（W5、W6、W7、W9）、09、12、13、14、17、28、32；BR-FUND-14；CAP-X-06（待验证）；AC-S2-20、AC-S2-24、AC-S2-25；AC-WDR-06、AC-WDR-07。

### 5.5 结果未知：查询与人工处置

```mermaid
sequenceDiagram
  autonumber
  participant P as payout 进程
  participant DB as PG（withdrawals、payout_attempts、withdraw_holds、ledger_*）
  participant Z as 支付宝开放平台
  participant F as 财务（后台，step-up）
  participant A as admin·payout

  loop 每到一个查询时点，且单据仍为 PAYING、needs_manual 为假（时点与期限见 BR-WDR-14）
    P->>Z: alipay.fund.trans.common.query（out_biz_no、product_code、biz_scene）
    Z-->>P: 状态，或查询调用失败（查询本身可以重试，不算转账）
    P->>DB: 写 payout_attempts（kind=query）
    break 查询状态按 payout.query_status_map 映射为 success
      P->>DB: 同一事务 W5 → PAID_API（CAS），成功分录
    end
    break 映射为 fail
      P->>DB: 同一事务 W6 → FAILED，WITHDRAW_RETURN
    end
    Note over P: 处理中、订单不存在、没列入映射的状态、查询调用仍失败，都算未知，等下一个时点。验证前只有成功状态会被映射（BR-WDR-28）
  end
  alt 循环因得到确定结果而退出
    P->>P: 结束
  else 自首次转账尝试起到期限仍未知

    opt 财务点【立即查询】
      F->>A: 查询结果只存为凭证，不迁移状态
    end
    F->>A: W10 MANUAL_RESOLVE（上传支付宝侧凭证，一人可完成，BR-WDR-15）
    alt 凭证显示已成功
      A->>DB: 同一事务 → PAID_API，成功分录
    else 同时满足 BR-WDR-15 判失败的三个条件
      A->>DB: 同一事务 → FAILED，WITHDRAW_RETURN，并给该会员加 withdraw_holds（manual_failed_watch，到期自动失效）
    else 条件不足
      A-->>F: 不允许判失败，单据保持 PAYING、needs_manual 为真
    end
  end
  Note over P,A: needs_manual 的单不得转 PAID_MANUAL，不得重发转账。每日对账仍覆盖这类单（§5.6）
```

- [x] 查询得到成功或失败后退出循环，不再继续查询
- [x] 订单不存在、处理中不立即判失败
- [x] 查询调用本身失败（按 BR-WDR-14 重试，不算转账）
- [x] 到期仍未知：置 needs_manual，停止自动查询，转人工
- [x] 人工处置：成功、判失败（条件齐全才行，并加观察冻结）、条件不足不许判失败
- [x] needs_manual 之后的查询只存凭证，状态只由 W10 迁移

**实现的 BR / AC**：BR-WDR-08（W5、W6、W7、W10）、09、14、15、28；AC-S2-24；AC-WDR-07。

### 5.7 余额变负时的未完结提现单


**覆盖的异常情况**：表外事件与并发冲突（CAS 影响 0 行，后台接口 20902，AC-S2-31）；终态不可再迁移；W9 退回后只有无转账尝试的单能再走 W4（付款方侧失败的单只能 W8 或 W3，BR-WDR-17）；needs_manual 的单只能经 W10 结束。

## 6. 登录与第三方空号并号

所有登录方式与刷新都要求签名（BR-ID-09），因此必须先在用户同意隐私政策后完成设备注册（BR-ID-11）。拒绝码按 BR-ID-01 的顺序返回第一个。同一自然人用微信与手机号分别登录会得到两个账号，不自动合并；唯一例外是第三方登录新建的空号在绑定手机号时经用户确认并入老号（BR-ID-06，拍板第二批 OPS-04）。

## 7. 淘宝渠道备案（relation_id）与站长授权到期

淘宝订单的用户归属只靠 `relation_id`（BR-ATTR-07），备案只在用户点击购买时触发（BR-ID-17），一次绑定、不提供用户自助换绑（拍板第二批 §8 ADD-01）。授权页走百川还是 H5 OAuth 按 CAP-TB-05 实测定，两条都保留（09 5_X §5.5）；「百川套件备案页」在 09 中没有记录，图中按「百川授权组件或 H5 授权页」画。备案流程本身不受 2026-10-03 转链变更影响，绑定成功后的购买按 §2.6 打开。拼多多的备案见 §2.5。

### 7.1 用户渠道备案


### 7.2 站长授权每日巡检与告警

到期与探测失效是两个独立的触发条件：时间到了即使探测超时也算过期；没到期而探测得到授权失效类错误也立即算失效（BR-ID-24）。

```mermaid
sequenceDiagram
  autonumber
  participant CR as worker·union（union.auth_probe_cron）
  participant DB as PG（union_accounts、union_credentials）
  participant TB as 淘宝联盟 TOP
  participant SMS as 阿里云短信
  participant ADM as 后台告警

  CR->>DB: 每日读 auth_expires_at、auth_status、alert_stage
  opt 平台支持刷新，且剩余有效期已到自动刷新的门槛（BR-ID-24 ②）
    CR->>TB: 刷新凭据
    alt 刷新成功
      CR->>DB: 更新 union_credentials 与 auth_expires_at
    else 刷新失败
      CR->>CR: 照常按节点提醒
    end
  end
  alt 已到达 auth_expires_at（时间到期，不依赖探测结果）
    CR->>DB: auth_status 置 expired
  else 未到期
    CR->>TB: 实际调用一次依赖该授权的只读接口（探测接口登记在 specs/union/taobao.md，待 CAP-TB-12）
    alt 返回授权失效类错误
      CR->>DB: auth_status 置 expired，写 last_probe_at、last_probe_ok、last_probe_error
    else 超时、限流等非授权类错误
      CR->>TB: 按 BR-ID-24 ① 重试
      opt 重试仍失败
        CR->>ADM: 只做后台提醒，不发短信，不改状态
      end
    else 探测成功
      CR->>DB: 写 last_probe_at、last_probe_ok
      opt 此前因探测或调用被判失效，而到期时刻未到
        CR->>DB: auth_status 恢复 active
      end
    end
  end
  alt 本次进入 expired，且还没发过过期提醒（alert_stage 防重复）
    CR->>SMS: UNION_AUTH_EXPIRED 发给 union.auth_alert_phones 的全部号码
    CR->>ADM: 后台告警，alert_stage 记 expired
  else 剩余有效期到了某个提醒节点，且该节点没提醒过（union.auth_alert_days）
    CR->>SMS: UNION_AUTH_EXPIRING
    CR->>ADM: 后台提醒，alert_stage 前移
  else 其他
    CR->>CR: 不提醒
  end
  opt 没有配置告警手机号
    CR->>ADM: 只做后台告警，联盟账号页标未配置
  end
  Note over CR,ADM: 属运维告警，不受免打扰与用户通知开关约束。短信通道故障时后台告警仍在（02 §14）
  Note over CR,TB: 任何一次联盟调用返回授权失效类错误，也立即置 expired 并按上面提醒，不等每日巡检
```

**覆盖的异常情况**

- [x] 到期前多节点提醒去重；过期提醒只发一次
- [x] 时间到期而探测超时（照样置 expired）
- [x] 未到期但探测得到授权失效（立即置 expired 并短信）
- [x] 探测超时或限流（重试，仍失败只做后台提醒，不改状态）
- [x] 误判失效后探测成功（未到到期时刻时自动恢复 active）
- [x] 自动刷新失败（照常提醒）；未配置告警手机号；短信通道故障

**实现的 BR / AC**：BR-ID-24 ①②、BR-TEXT-20；拍板第二批 §8 ADD-02、ADD-08；CAP-TB-12（未实测）；AC-S1-64。

## 8. App ↔ H5 桥签名请求

App 内 H5（`TrustedWebView`）调用需签名的接口只能经桥方法 `net.signedRequest` 由原生代签代发；h5_token 不能直接调签名接口（BR-ID-32）。原生只签 `bridge.schema.json` 的 `signed_paths`，MVP 只有 `POST /v1/orders/claims`（拍板第二批 TECH-30）。签名只防网络层重放；防恶意页面反复调桥靠用户手势、路径白名单与限流。下图以找回提交为例；方法级别、超时、桥错误码以契约 `bridge.schema.json` 为准。
