# 完整验证改认 GitHub 上的检查结果（2026-10-06）

## 内容

负责人 2026-10-06 在对话里决定：「改成认 GitHub 上的检查结果」。

- RV2 任务合并前的**完整验证**，以 PR 头提交上的必过 CI 检查为准：ci-gate（verify-fast、verify-int、guard-git）、contracts-gate、longrun-props。
- 证据文件 `ops/evidence/<id>.json` 不再要求本机容器 `verify` 记录；本机容器完整验证改为可选自查，写进证据文件的容器记录须在头提交树上通过。
- 不变：先红（容器 red 运行，规划/11 §2.3 第 3 步）、spec_commit 与规则测试未改、两家评审、受保护目录树哈希、长跑属性测试、`mode: host` 不接受；证据文件不抄 CI 记录（`mode: ci` 照旧拒收，CI 检查本身就是结论）。

起因：本机 Docker 负载过高（多个项目的常驻容器、各会话并行的容器验证），RV2 落地前的本机完整验证排队数小时；而 CI 每次合并本来就在头提交上再跑一遍完整检查，二者重复。

安全依据：CI 工作流（`.github/**`，保护路径第三类）与验证配方（各 `package.json` 的 scripts、验证配置，第二类）都在保护路径里，`protected-paths` 检查用 `pull_request_target` 从基线运行，PR 改动它们须负责人批准标签，因此 PR 不能改弱 CI 跑的内容。

## 涉及的 BR

无（流程与门禁，不涉及业务规则取值）。

## 受影响的文档、页面与接口

- 规划/11 §2.3 第 7 步、§3.2（RV2 合并条件、证据文件）、§4.1 验证入口表 `verify` 行。
- 代码仓库：`tools/ci/evidence-check.ts`（与其测试）、`ops/approvals.yaml` 第 21 条、`tools/ops/README.md`。
- 页面与接口：无。

## 验收与恢复

- 验收：代码仓库门禁 PR 合并后，RV2 任务 PR 的 `evidence-check` 在证据文件不含容器 verify 记录、必过 CI 检查全绿时通过；含失败或树不符的容器 verify 记录时失败。
- 恢复：回退代码仓库该门禁 PR（evidence-check 恢复「必须有容器 verify 记录」），并回退本记录与规划/11 的相应改动。
