# 原路退款不设二次验证

2026-10-05。负责人在对话里确认（原话「退款不需要验证」）。

## 1. 内容

后台发起原路退款（权限点 `pay.refund`，BR-PAY-06）不再要求二次验证。其余不变：只有超管或被勾选 `pay.refund` 权限点的账号可以操作，必须选原因码，写审计，退款合计不超过实付。

此前写法：2026-10-04 收款基础设施一稿写「step-up」；2026-10-05 合并后台二次验证分档时按「其余为动态码档」标为动态码。两处均由本记录取代。

## 2. 涉及的规则与位置

| 位置 | 变更 |
| --- | --- |
| 08 BR-PAY-06 | 「step-up」改为「不设二次验证」 |
| 04 §11.2 `pay.refund` | step-up 列由「动态码」改为「–」 |
| 01 F-PAY-04、05 F1-13 | 摘要同步 |

`switch.pay`、`pay.resolve` 与 BR-ID-34 的两档划分不变。

## 3. 影响

- 页面与接口：后台支付单的退款操作不弹二次验证；`POST /admin/v1/pay-orders/{id}/refunds`（以 04 §6.6 为准）不带 step-up 标记。代码仓库 `contracts/` 里若已为该接口声明 x-step-up，随下一个契约任务去掉。
- 风险：退款是向外出款的操作，去掉二次验证后只靠登录态、权限点与审计约束；已登录的后台会话被他人使用时可以直接发起退款（上限为各支付单的实付金额，且只能原路退回付款人）。

## 4. 验收与恢复

- 验收：有 `pay.refund` 权限点的账号发起退款不出现二次验证；无权限点的账号看不到按钮且服务端拒绝；审计日志有记录。
- 恢复：把 04 §11.2 该行的 step-up 列改回「动态码」或「短信」，并同步 BR-PAY-06 与上表各处。
