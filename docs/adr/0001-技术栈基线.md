## 1. 背景

规划里的技术栈一直标「当前方案，可调整」（00 D27、02 §16.3、03 §3.3），版本号、主键类型、迁移工具、测试库策略等第一天搭脚手架就要用的决定都没写。负责人 2026-10-01 指示：技术栈现在定下来，先把基础搭好，眼光放长远。

选型原则：一人运营，少一个要维护的组件就少一类故障；资金路径（锁账户、判幂等、写分录）要有编译期类型检查；凡是可能被替换的库，业务代码只依赖自有接口；版本用锁文件钉死，不追新。

版本核对与兼容性实测于 2026-10-01 在本机完成（PostgreSQL 16 容器）；pg-boss、Kysely 工具链、分区与角色于同日验证日在 PostgreSQL 18.6 容器复测，结果见 §7。仍标「待核」的项核实后补入本文。

## 3. 与 `规划/02` §16.3 的差异

| 项 | 原方案 | 现方案 | 原因 | 代价 |
| --- | --- | --- | --- | --- |
| 数据访问 | Prisma | Kysely + pg | 资金核心路径在 Prisma 里几乎全是原生 SQL，还要靠两个预览特性；CHECK 约束在其 schema 里不可见；它的 CLI `latest` 标签已指向下一个大版本的候选版 | Kysely 仍是 0.x；普通增删改查更啰嗦；迁移全部手写 |
| 迁移 | `prisma migrate` + 分区表另写 SQL | 全部 SQL 文件，一个序列 | 消除「Prisma 不管分区表」与单一 schema 文件并存的矛盾 | 没有 schema 总览文件，靠 `db/schema.sql` 快照 |
| 队列与事件 | BullMQ + 独立 queue Redis + outbox 表 + relay 进程 | pg-boss：领域事件作为任务在业务事务内入队 | 少一个要持久化的 Redis 和一个进程；任务随 PG 备份与时间点恢复；排查用普通 SQL | 社区较小；任务写入压在主库；没有官方 Nest 模块，自写薄封装；海报出图要把轮询调到 0.5 秒或开通知（0.5 秒已实测可设；通知方式未测） |
| HTTP 测试 | Supertest | Fastify `inject` | 已够用 | — |
| 版本 | 没写 | 见 §2 | 多个 `latest` 是几周内的新大版本，且互不兼容 | — |
| H5 组件库 | react-vant | 不引第三方移动组件库，组件自写（2026-10-06） | 维护停滞，对 React 19 的支持未核实；H5 页面少，设计系统已有组件规格 | 组件要自己写与测，量不大 |

- TECH-09 的实质不变：保留分区、手写 SQL 迁移、引用订单的外键指向 `order_keys`。
- 02 §18 写「代码不得自创其他模式」，其中领域事件一行由本 ADR 改为：业务写入与任务入队同一事务 → 至少一次投递 → 消费端 `processed_events(consumer, event_id)` 去重。「资金不依赖事件」不变。
- 02、05、08、10 里提到旧方案名词的地方已于 2026-10-01 由用语同步任务改为中立说法（`规划/11` §9.1）；仍有遗漏处以本文为准。

## 4. 数据库设计规则

### 4.1 沿用不变

金额 `bigint` 分（`_fen`）、比例万分之一（`_bp`）、外部 ID 用 `text`、蛇形命名、业务表 `app_id NOT NULL`、保留外键禁级联、分录只插入加触发器（BR-FUND-16）、单一写者、CAS + `row_version`、记账按账户 ID 升序加锁、同一订单咨询锁串行、PII 信封加密加盲索引、迁移先扩展再回填再收缩、单条查询 join ≤3 张表。出处：02 §18、§19，04 §3.2。

### 4.2 本次补定

| # | 项 | 规则 |
| --- | --- | --- |
| 1 | 主键 | 实体表用 UUIDv7，由应用在 `packages/domain` 生成，列类型 `uuid`；只增不删的高频表（分录、事件日志）用 `bigint` 自增，不对外暴露。PG 18 有原生 `uuidv7()`，17 没有（已实测）；列默认值不得写 `uuidv7()`，保持退 17 不改代码 |
| 2 | `link_id`、`order_id` | UUIDv7；需要短码时另设 `short_code` 列 |
| 3 | 金额在 JSON 里 | 整数（`int64`），不用字符串；服务端用 BigInt，序列化时断言不超过 2^53−1；Swift 取 Int64，Kotlin 取 Long；pg 的 int8 统一解析为 BigInt：运行时 `pg.types.setTypeParser(INT8, BigInt)`，kysely-codegen 加 `--type-mapping '{"int8":"ColumnType<bigint, bigint, bigint>"}'`（默认映射成 string），CI 用 `--verify` 查类型漂移 |
| 4 | 分区维护 | worker 里的定时任务以 `couli_maint` 调用 `couli_migrator` 所有的 `SECURITY DEFINER` 函数（如 `app.ensure_month_partition`）建和删分区：非属主即使有 schema 的 CREATE 也建不了分区（已实测）。按月的表预建未来 3 个月，按日的表预建未来 14 天；每张分区表设 DEFAULT 分区兜底，其中有数据即告警，且须先把数据迁出才能建对应区间的分区（否则建分区报错，已实测） |
| 5 | 分区粒度 | `orders`、`ledger_entries`、`union_raw_payloads`、`event_log` 按月；`link_logs`、`events` 按日 |
| 6 | `ledger_entries` 分区键 | 新增不可变列 `booked_at`，主键 `(id, booked_at)` |
| 7 | `order_keys` | 加 `attr_at` 列：按 `order_id` 查订单时先取它，才能做分区裁剪 |
| 8 | 数据库角色 | `couli_migrator`（DDL，只在 CI）、`couli_app`、`couli_payout`、`couli_readonly`、`couli_maint`（只有分区函数的 EXECUTE，无 DDL 权限）；建角色放 `db/bootstrap/roles.sql`，每个环境执行一次；授权写在迁移里 |
| 9 | 测试库 | 每次测试运行用一个一次性 PG，入口统一读 `TEST_PG_ADMIN_URL`：有值直连（容器内 verify 由 `verify-container.sh` 在 internal 网里起库后传入），无值才由 Testcontainers 起容器（宿主直跑）。迁移只跑一次生成模板库，每个测试文件从模板建独立库；`TEST_PG_ADMIN_URL` 只给 globalSetup 用，测试用例以 `couli_app` 身份连接，权限和触发器都被真实检验。集成测试只在 Codex 沙箱外（编排者或 CI）运行；单元测试不得连库 |
| 10 | 时钟 | 统一为 `Clock` 接口加环境变量 `CLOCK_NOW`，在 local、test、staging 生效（staging 的压缩时钟全流程 AC-S2-32 要用）；prod 设置了就拒绝启动（启动断言）；`X-Clock` 请求头作废 |
| 11 | 连接池 | 不用 PgBouncer（咨询锁和通知需要会话模式）；每进程池大小 api 10、stream 5、worker 10、payout 3、admin 主库 3 加只读 5，按数据库节点规格复核；只读从库用单独的 `dbRead`，只有后台报表模块能引用。云上的端口与访问规则见 ADR-0002 §5：主库 5433、只读 5434，都直连、不经连接池 |
| 12 | 本地栈 | `pnpm dev:stack` 依次启动 compose（PG + pgvector、Redis、MinIO、Prism、WireMock）、跑迁移、跑种子；种子统一放 `db/seeds/`，含首行 `app_id`、平台字典、开关默认值、本地超管。PG 18 镜像的数据卷挂 `/var/lib/postgresql`（17 及以前是 `/var/lib/postgresql/data`）。本地栈由编排者启动，Codex 沙箱内不可达；verify 用的 PG 不与它共用（它发布宿主端口、接可出网的网络） |
| 13 | 目录 | 迁移 `db/migrations/`；快照 `db/schema.sql`，用 `pg_dump --schema-only --no-owner --restrict-key=couli` 生成（PG 18 默认每次写入随机的 `\restrict` 键，不固定就无法做漂移比对）；不变量 SQL `db/invariants/`；guard 脚本统一 `tools/guard/` |
| 14 | pg-boss schema | 安装与升级都写成 `db/migrations/` 里的 SQL 迁移，内容取自 `getConstructionPlans('pgboss')` / `getMigrationPlans('pgboss', <旧版本>)`，删掉其中的 `BEGIN;` / `COMMIT;`（否则会提前提交 node-pg-migrate 的外层事务，已实测）；同一迁移里给 `couli_app`、`couli_payout` 授 schema `USAGE` 与全部表的 `SELECT, INSERT, UPDATE, DELETE`。进程一律 `migrate:false`；库版本与 schema 版本不一致时拒绝启动，所以升级 pg-boss 的 `deps` 任务必须同时带迁移，按「先迁移、再重启全部进程」发布。不用 `partition:true` 队列，不开 `persistQueueStats`，`reindex:false`（都要属主权限）；索引膨胀由迁移角色按 `getReindexCommands()` 处理。同事务入队写 `send(..., { db: fromKysely(trx) })` |
| 15 | 请求校验 | 路由 schema 由 `contracts/` 构建期生成，控制器用 `@RouteSchema` 挂载；body 用不做类型转换的 `Ajv2020`，query / params / headers 用开 `coerceTypes` 的实例，都开 strict；header 参数名生成时转小写；全局异常过滤器把 `FST_ERR_VALIDATION` 映射为 400 加统一错误码（Nest 默认会回 500，已实测）；路由 schema 不放 `response`（它会静默删字段），响应契约在测试里校验。契约书写规则：`unevaluatedProperties` 旁必须写 `type: object`，`prefixItems` 必须配 `minItems`，否则应用启动即失败 |
| 16 | 领域事件留痕 | 新增只追加表 `event_log`：每个领域事件一行，与业务写入同一事务写入；按月分区，留存 ≥190 天。它是审计与历史查询用的日志，不是投递机制：投递仍只靠 pg-boss 任务（§3），消费端不读本表。与埋点表 `events` 无关 |
| 17 | Redis 淘汰策略 | 单实例 `maxmemory-policy=noeviction`；每个键必须带 TTL，键的基数有上限；内存使用率 70% 告警；写入失败时缓存路径降级为直读 PG；防重放 nonce、配额计数、`refresh_grace` 键不得被静默淘汰 |
| 18 | Agent 冒烟回放合并门 | 改动 Agent 服务的 PR（范围按 BR-AI-21），合并前由编排者在本机按需跑冒烟回放并通过，不等夜间任务；夜间回放是另加的全量运行 |
| 19 | 任务去重键 | `{withdrawal_id}:{execute_seq}` 这类任务键映射到 pg-boss 的 `singletonKey`，不是任务 id；「同键任务还在队列里时新任务被静默丢弃」的行为是否等价，在 B1-01 实测。08 的保证不变 |
| 20 | payout 进程的开关与出站 | payout 进程从 PostgreSQL 配置表读开关（`payout.enabled` 等），不读 Redis；出站白名单只剩 PG 与支付宝、银行卡通道 |
| 21 | `booked_at` 含义 | 记账时刻：`timestamptz`，取经应用 `Clock` 得到的记账时刻（不用 SQL `now()`，这样 `CLOCK_NOW` 压缩时钟下也成立；规划/11 §4.2 的时钟守卫不变）；会计日 `accounting_date` 由它按 +08:00 推出 |
| 22 | 事件任务积压告警口径 | 「最老未被取走的事件任务 >60 秒」只计状态为 created 且已到期的任务；等待定时重试的任务不计 |

第 6、7 项改的是 04 的表形状，已随用语同步任务回写 04 §3.2 与 BR-ATTR-22 的示例措辞（不改规则含义）。第 10 项的 staging 与第 16–22 项是编排者 2026-10-01 补定的实现选择（00 §8 第 ① 类），已同步 02、04、10 的相关句子。

### 4.3 对现有矛盾的裁定

| 矛盾 | 裁定 |
| --- | --- |
| 02 §19 要求每表 `id`、`updated_at`，04 有联合主键表和只插入表 | `id`、`updated_at` 只适用于可变实体表；联合主键表和只插入表按 04 的定义 |
| 02 §19 要求业务表都有 `deleted_at`，04 只有个别表有 | 只有 04 明确列出的表有 `deleted_at` |
| 02 §19「列表一律 keyset」，后台用页码分页 | 用户侧列表一律 keyset；后台允许页码分页，走只读实例 |
| 环境写四个又写「三个环境」 | 四个：local / test / staging / prod |

## 5. 影响

- **文档**：02 §16.3 已按本文改表；02 其余章节、05 的 B1-01 与 QA-02、08 中 13 条 BR 的实现措辞、10 §5.3 已于 2026-10-01 由用语同步任务改完（`规划/11` §9.1）。04 的表结构在 `db/schema.sql` 建立后改为指针（`规划/11` §5.4）。
- **替换成本可控**：Kysely 与 pg-boss 都隔在自有接口后面；SQL 迁移和表结构不绑定库。
- **要留意的风险**：NestJS 12、Vitest 5 都是近期的大版本；Refine 自 2026-04 后无新版，后台框架有停滞迹象；自建 Sentry 的规格未核实；向量模型与维度未定，`rule_chunks` 的迁移暂不写。Stryker 10.0.0 的 vitest-runner 在 Vitest 5 下按名过滤失效（上游 #6210），修复前变异得分不作门禁，也不要为跑变异把主测试栈降到 Vitest 4。
- **待核项**：Xcode、Kotlin、AGP、DevEco 版本（`jose` 已于 2026-10-06 核对并补进 §2）。核对结果补进 §2，不另开 ADR。Xcode 版本补进 §2 时一并写明 iOS 26 新系统外观的处理（接受新外观、不设兼容键，规划/03 §3.3；2026-10-03 功能对照 G-93）。原有的三条（RDS PG 18 的高可用系列与 pgvector；RDS 是否允许 `SECURITY DEFINER` 函数与自建角色；云上 Redis 可选版本），随 ADR-0002 改用 Pigsty 自建而取消；云上数据库的待核项改见 ADR-0002 §10。pg-boss 权限、带 pgvector 的 PG 18 镜像、OAS 3.1 校验工具链三项已于 2026-10-01 核实（§7）。

## 6. 以后怎么改基线

- **补丁与次版本升级**：在版本线内，走 `deps` 任务（`规划/11` §3.4），不改本文。
- **跨主版本、换库、改数据库设计规则**：新写一篇 ADR，文件头写「取代 ADR-0001 的 §x」，本文对应处标「被 ADR-NNNN 取代」，保留历史（00 §8）。新 ADR 要写清：为什么现方案不够、迁移步骤、回退方式、受影响的模块与测试。
- **涉及花钱、新供应商、生产数据或资金一致性的改动**：先问负责人（`规划/11` §7.1）。
- 把待核项的结果补进本文、修正错字或错引用，不算改基线。
