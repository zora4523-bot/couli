2026-10-06 · 00 §8 第 ② 类（改变风控与对外可用范围），负责人 2026-10-06 在对话中决定：「不需要开通人机验证」。同日负责人对英文名提出「couli？」，代理按此回写（§5）。

- 涉及 BR：BR-ID-05、BR-ID-32、BR-INV-05（只改引用）。
- 涉及页面与接口：登录页发码（`POST /v1/auth/sms-codes`）；邀请落地页发码（`POST /v1/landing/sms-codes`）与注册绑定（`POST /v1/invites/landing-register`）；后台配置中心风控配置页。

## 1. 原来的写法

- App 内发码在三种情形下要求人机验证（44003）：同一 IP 一小时内新注册 ≥5 个账号；同一 IP 一小时内发码条数达到 `sms.ip_sends_per_hour`；`sms.captcha_mode=always`。
- 落地页每次发码都必须带人机验证凭证。
- 人机验证是付费服务，开通前上述情形一律按 42901 处理。结果是落地页每次发码都被拒，落地页注册实际走不通（规划/12 §9 A-05，`docs/changes/20261006-流程图不一致同步.md` §4）。

## 2. 改成

- MVP 不接入人机验证，任何接口都不要求人机验证凭证；44003 码号保留、不返回、不复用。
- 发码判定顺序：签名 → 20001 → 44001 → 42901。42901 依次看：
  1. 同 IP 两项：该 IP 一小时内新注册 ≥5 个账号，或该 IP 一小时内发码条数达到 `sms.ip_sends_per_hour`。任一成立就直接返回 42901，Retry-After 取已成立各项中最晚的解除时刻（计数为 N、阈值为 L 时，到第 N−L+1 条记录滑出窗口）。这次请求不进入设备准入，也不占名额。
  2. 设备的不同号码数（落地页没有设备，不适用）。
  3. 手机号频控。
- 落地页发码与 App 内发码同一套判定，只是没有签名和设备两步。落地页同 IP 注册上限（`landing.ip_register_limit`）不变。
- `sms.captcha_mode` 作废，键名保留、不再读取。全站短信量达到预算告警时，由运营在风控配置页调低各项阈值（修改需 step-up，权限点 `config.risk`）。

阈值都沿用原默认值，没有放宽：App 内原来「改要人机验证」的情形，在开通前本来就按 42901 处理，现在仍是 42901。变化只在落地页：从「每次都要验证（未开通 = 每次都拒）」改为按 IP 与手机号限流，落地页注册因此可用。

## 3. 风险与已知限制

- 没有人机验证后，落地页是唯一不签名、不带设备的发码入口。能挡住刷量的只有按 IP 的两项和全站预算告警；换 IP 批量刷的情况挡不全，由运营按告警调低阈值。以后要开通人机验证，按 00 §8 另记变更，在 42901 之前恢复 44003 一步。
- 同一出口 IP 下用户很多时（运营商网络、校园网），「一小时内新注册 ≥5」可能让同 IP 的正常用户一时收不到验证码。这本来就是开通前的行为，没有变严；运营可按投诉调高阈值。

## 7. Codex 对抗评审后的修改

第 1 轮：中 2、低 2，没有高。

- Retry-After 原写「最早一条滑出」。窗口内计数超过阈值，或运营调低阈值后，最早一条滑出时仍未解除。改为按计数算：计数 N、阈值 L 时，等第 N−L+1 条滑出。BR-ID-05 补了超阈值与调低阈值两个例子，10 AC-S1-79 ② 补了调低阈值后的断言。BR-ID-05「同时命中多项限制」限定为手机号的各项限制。
- 13 §13.11、12 §9 A-05、00 的摘要原写「原需验证的发码含落地页一律 42901」，会被读成落地页全部拒绝。改为：App 内命中同 IP 两项才返回 42901；落地页取消每次验证，按同 IP 两项与手机号频控判定。
- 13 §13.3 的 44003 行把含义标为历史含义，客户端处理改为引用 §13.11。
- `design/README.md` 不再把英文名列为待办。
