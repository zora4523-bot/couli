各缺口的建议与规划现有条目有出入、以规划为准的地方：

- G-01：清单建议 SDK 方式的请求体为 `{state, access_token, expires_in}`；写回时加了 `auth_method` 字段用来区分两种方式，并把「哪一端下发哪种方式」交给服务端配置，生产默认只含网页授权。原因是 09 2_TB §2.5 已实测百川应用拿不到淘宝客权限包、且与联盟应用分属两个淘宝账号，SDK 换得的令牌能否用于备案未经实测，不能写成能力。
- G-03：清单提到「如果淘宝分享采用只在 App 内打开方案，本条是前置任务」。负责人 2026-10-03 已确认淘宝分享用预先转好的推广链接与淘口令（BR-ATTR-10 细则），所以 App 内打开只是并行的另一条路，不是淘宝分享的前置条件。
- G-05：清单把「建号时允许填邀请码」「补填期限从绑手机时起算」列为二选一。这两项都会改变已确认的绑定条件（BR-INV-03 已确认：绑定须 phone 级别；BR-INV-07 已确认：期限从建号起算），本批都没有做，只做了提醒。
- G-08：BR-ID-09 原文「Android=OAID，取不到时用 ANDROID_ID」保留不改；按 Q-23 默认，MVP 不集成 OAID 的获取方式，实际只用 ANDROID_ID。
- 与拍板第三批（`docs/changes/20261003-拍板第三批.md`，写回期间合入 main）的关系：其 §3 已确认授权管理页只显示「已授权 / 未授权」、不显示淘宝账号名，本批原先为此预留的显示开关已删除，BR-ID-17 按已确认写；其 §4 把 Q-01 记为未回答、按现状加两处提醒处理，与本批 G-05 的写法一致；其 §1、§2（跟单通知、自购单完整订单号）不在本批范围，合并时保留双方内容。
