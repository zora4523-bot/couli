## D1 订单生命周期与平台状态映射

**D1-1 淘宝 tk_status 与维权标记**（置信度：高）
- 做法：tk_status 在入参注释里写成「11 拍下未付款、12 付款、13 关闭、14 确认收货、3 结算成功」，在出参注释里写成「3 结算、12 付款、13 失效、14 成功」。状态映射表应按出参口径画。refund_tag（0 非维权、1 维权）是一个独立标记，不属于主状态，但要能覆盖主状态。入参还有 member_type（2 二方、3 三方，不传表示全部）。
- 边界情况：13 失效包括超时未付款、付款前取消、售中退款成功、只付定金没付尾款四种情况。AgenticCPS 遇到 REFUNDED / INVALID 时，如果订单已经解冻或者已有返利主记录，会先执行冲回（reverseRebate），再改状态；更新状态时用 status_version 做 CAS。
- 对我们图的提示：D1 要把「维权」画成可以叠加在任何主状态上的独立标记，而不是主状态链上的一个节点。图上要标出「已入账后转为失效」这条边，它先触发 D4 冲回，再改状态，并用版本号防止并发覆盖。
- 来源：[bububa TaobaoTbkOrderDetailsGetAPIRequest.go](https://github.com/bububa/opentaobao/blob/main/model/tbk/TaobaoTbkOrderDetailsGetAPIRequest.go)、[bububa PublisherOrderDto.go](https://github.com/bububa/opentaobao/blob/main/model/tbk/PublisherOrderDto.go)、[AgenticCPS CpsPlatformOrderStatusMapper.java](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/backend/qiji-module-cps/qiji-module-cps-biz/src/main/java/com/qiji/cps/module/cps/service/order/status/CpsPlatformOrderStatusMapper.java)、[AgenticCPS CpsOrderServiceImpl.java](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/backend/qiji-module-cps/qiji-module-cps-biz/src/main/java/com/qiji/cps/module/cps/service/order/CpsOrderServiceImpl.java)、[QiYu grab_order_ztk_base.py](https://github.com/QiYuTechOrg/QiYuTkServer/blob/HEAD/tbk/core/cron/ztk_cron/grab_order_ztk_base.py)、[sfb SuStoreOrderServiceImpl.java](https://github.com/jacky4631/sfb_server/blob/HEAD/mshop-store/src/main/java/com/mailvor/modules/order/service/impl/SuStoreOrderServiceImpl.java)

**D1-2 反例：几个平台共用一个状态模板，未知码默认落到「已下单」**（置信度：高）
- 做法：AgenticCPS 的 mapper 虽然每个平台写了一个 switch，但都套用同一个 0–4 通用模板，再补几个平台码。
- 边界情况：京东的无效码被映射成了正向状态：validCode 2（拆单无效）映射为 RECEIVED，3（取消）映射为 SETTLED，4（帮帮主订单无效）映射为 REBATE_RECEIVED，18（官方没有列出）映射为 SETTLED，其余无效码落到默认的 CREATED；缺失值 -1 才映射为 INVALID。结果是有的失效单显示成了「已到账」。
- 对我们图的提示：每个平台单独维护一张映射表；遇到未知码一律进入「待人工」，不能落到任何正向状态。D1 的映射表要有「未知码」这一行。
- 来源：[AgenticCPS mapper](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/backend/qiji-module-cps/qiji-module-cps-biz/src/main/java/com/qiji/cps/module/cps/service/order/status/CpsPlatformOrderStatusMapper.java)、[AgenticCPS DtkJdVendorClient.java](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/backend/qiji-module-cps/qiji-module-cps-biz/src/main/java/com/qiji/cps/module/cps/client/dataoke/DtkJdVendorClient.java)、[AgenticCPS DtkPddVendorClient.java](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/backend/qiji-module-cps/qiji-module-cps-biz/src/main/java/com/qiji/cps/module/cps/client/dataoke/DtkPddVendorClient.java)、[typed-jd order.row.query](https://github.com/logerzhu/typed-jd-union-api/blob/HEAD/json-def/jd.union.open.order.row.query.json)、[bububa openpdd order.go](https://github.com/bububa/openpdd/blob/HEAD/api/ddk/order.go)、[sfb OrderUtil.java](https://github.com/jacky4631/sfb_server/blob/HEAD/mshop-system/src/main/java/com/mailvor/utils/OrderUtil.java)

**D1-3 京东 validCode**（置信度：中）
- 做法：15 待付款、16 已付款、17 已完成、24 已付定金。2–14、19–23 以及 25 以上大多表示「无效」或「违规」，其中 14 表示来源与备案网址不符。
- 边界情况：payMonth（yyyyMMdd）要等订单完成后才有值；balanceExt 按月记录实际佣金的变动，例如某月出现负数，它可以直接作为 D4 扣回的输入。parentId 是拆单前的父单号。
- 对我们图的提示：D1 的京东映射表要列出「已付定金」和「来源与备案不符」这类违规码；balanceExt 引出一条连到 D4 的边。
- 来源：[typed-jd order.row.query](https://github.com/logerzhu/typed-jd-union-api/blob/master/json-def/jd.union.open.order.row.query.json)、[dtapps jd.union.open.order.row.query.go](https://github.com/dtapps/go-library/blob/master/service/jd/jd.union.open.order.row.query.go)

**D1-4 拼多多 order_status 及附加标记**（置信度：中）
- 做法：接口同时返回 order_status 和 order_status_desc，映射时以 order_status 的数字为准。附加标记有：price_compare_status（0 正常、1 比价）、return_status（0 无、1 售后中、2 售后完成）。状态 4「审核失败」在注释里写明不可提现，可以映射为失效。订单里推广位字段的 JSON 名是 `p_id`。
- 边界情况：比价订单本身不代表订单失效，但实际没有佣金；售后中、售后完成是独立于主状态的标记。
- 对我们图的提示：拼多多的映射表要有「比价」和「售后中」两列附加标记，「审核失败」落到失效。
- 来源：[bububa openpdd order.go](https://github.com/bububa/openpdd/blob/main/api/ddk/order.go)

**D1-5 维权和处罚另走接口，而且状态可以反转**（置信度：高）
- 做法：淘宝的维权退款用 relation.refund 接口，有专用的状态枚举，查询参数里有 refund_type（1 二方、2 三方、0 不限）。处罚单用 punish.order 接口，状态 0 冻结、1 解冻，可以反复切换；处罚单结果里的 special_id 已注明不再支持。
- 边界情况：扣回有三档：没解锁的直接作废，已解锁的扣余额，余额不够时两家做法不同。sfb 扣到 0 后记录退款次数，交给人工处理；AgenticCPS 记成欠款。
- 对我们图的提示：D1 要画两条独立的输入源（维权接口、处罚接口），处罚的「冻结⇄解冻」画成双向边；扣回细节交给 D4。
- 来源：[bububa TaobaoTbkRelationRefundResult.go](https://github.com/bububa/opentaobao/blob/HEAD/model/tbk/TaobaoTbkRelationRefundResult.go)、[bububa TopApiRefundRptOption.go](https://github.com/bububa/opentaobao/blob/HEAD/model/tbk/TopApiRefundRptOption.go)、[bububa TaobaoTbkDgPunishOrderGetResult.go](https://github.com/bububa/opentaobao/blob/HEAD/model/tbk/TaobaoTbkDgPunishOrderGetResult.go)、[bububa TopApiAfOrderOption.go](https://github.com/bububa/opentaobao/blob/HEAD/model/tbk/TopApiAfOrderOption.go)、[sfb OrderRefundTask.java](https://github.com/jacky4631/sfb_server/blob/HEAD/mshop-admin/src/main/java/com/mailvor/modules/quartz/task/OrderRefundTask.java)、[AgenticCPS 资金归因安全基线](https://github.com/zhuangpengLI/AgenticCPS/blob/HEAD/docs/cps-funds-attribution-safety-baseline.md)

**D1-6 竞品对用户展示的状态**（置信度：高，指来源内容核对；状态链本身是我们综合出来的）
- 做法：省钱快报明确写出的只有「已失效」：退货、换货、退款导致订单变更，或者系统判定异常、作弊的订单，隐藏佣金会显示为已失效。
- 边界情况：「已付款（预估）→ 确认收货 → 待到账 → 已到账」这条链是我们综合出来的用户状态，竞品原文没有这样列；「维权中」单独作为延迟状态，也是我们的设计推断。
- 对我们图的提示：D1 要把内部状态和用户可见状态分成两层；用户可见状态的名称以 08 / 01 为准，不能当作竞品惯例来引用。

## D2 点击 → 转链 → 跳转 → 归因（分平台）

**D2-1 成熟 App 按平台分别接官方 SDK**（置信度：高）
- 做法：高佣联盟说明百川用于淘宝授权，京东联盟 SDK 用于唤起京东登录授权，多多进宝 SDK 用于接千万补贴商品，支付宝负责付款和实名。省钱快报说明百川旗舰版负责跳淘宝和联合登录，京东用的是「京东联盟广告 SDK」（不是开普勒），多多进宝负责跳拼多多。淘粉吧（2025-11-20 版）说明百川用于淘宝登录和商品详情，京东联盟 SDK 用于打开详情，拼多多 SDK 的用途写的是稳定性和安全性，支付宝 SDK 负责授权和支付。
- 边界情况：各家对 SDK 用途的说法不一样，不能拿某一家的说法当规范。
- 对我们图的提示：D2 每个平台画一条泳道，顺序是：检测是否安装 → SDK 或 scheme 唤起 → Universal Link / App Link → H5 → 下载提示。

**D2-2 百川 SDK 必须在用户同意隐私政策后才能初始化**（置信度：高）
- 做法：淘宝 SDK 的隐私条款写明，百川负责唤起淘宝、淘宝登录授权、打开详情页和购物车。
- 边界情况：这份条款没有提到淘客参数；「归因靠传入的 pid / relationId」这个结论来自 SDK 封装源码和 09 §5.5，不是来自条款。

**D2-3 旗舰版的两种打开方式，回调里没有订单号**（置信度：中）
- 做法：openByUrl 传链接打开，openByCode 传套件码和 itemId 打开。Android 回调是 onSuccess(int code, Object result) / onFailure(int, String)，iOS 回调是 (error, data)；插件只把成功结果当作「打开成功」处理，没有从里面解析订单号。
- 边界情况：dmcb 用 openByUrl 打开 uland 链接时仍然传了 pid 和 materialSourceUrl。这和 09 5_X §5.5 记录的百川现行 Android 文档冲突：打开 s.click / uland 时不得再传分佣参数，因为 SDK 不支持二次转链。
- 对我们图的提示：淘宝画两条分支：openByUrl(我方推广链接) **不带 pid**；openByCode(item_id) **带 pid 和 relationId**，与 `docs/changes/20261003-淘宝转链改客户端百川.md` 一致。SDK 回调只代表打开结果，归因交给 D3 的订单同步。
- 来源：[dmcb FlutterDmcbAlibcPlugin.java](https://github.com/zenganiu/flutter_dmcb_alibc/blob/master/android/src/main/java/com/example/flutter_dmcb_alibc/FlutterDmcbAlibcPlugin.java)、[dmcb MethodChannelHandle.swift](https://github.com/zenganiu/flutter_dmcb_alibc/blob/master/ios/Classes/MethodChannelHandle.swift)、[flutter_alibc FlutterAlibcHandle.kt](https://github.com/FlutterTaoBaoKe/flutter_alibc/blob/master/android/src/main/kotlin/com/wxwx/flutter_alibc/FlutterAlibcHandle.kt)

**D2-4 封装库把作者自己的推广位写成默认值（v4 封装）**（置信度：中）
- 做法：react-native-mbaichuan（README 标注 iOS 4.1.0.3 / Android 4.1.0.5，不是旗舰版）在 dealTaokeParams 里写死了作者自己的 pid、adzoneid 和 tkkey。参数缺失时会静默使用这些默认值，佣金就归了作者。代码每次都会带上 taokeAppkey，取不到时同样用默认值。

**D2-5 淘宝跳转前检查渠道绑定；客户端只传 relationId 能否归因还没证实**（置信度：中）
- 做法：QiYu 在用户购买前强制检查渠道是否已绑定。它的 relation_id 是服务端通过折淘客转链时写进链接的，客户端 taoke 参数里并没有 relationId。在 taoke 参数里带 relationId 的写法，只在 dmcb 插件里见到。
- 边界情况：只靠客户端 AlibcTaokeParams.relationId 能否让订单带上渠道归因，现有源码都证明不了。
- 对我们图的提示：「未绑定 → 引导到 D7」这个闸门要画出来。openByCode 带 relationId 的归因效果在图上标「待 CAP-TB-11 真机验证」，不能画成既成事实。
- 来源：[QiYuTkAndroid TaoBaoLogic.kt](https://github.com/QiYuTechOrg/QiYuTkAndroid/blob/HEAD/app/src/main/java/com/qiyutech/tbk/logic/TaoBaoLogic.kt)、[QiYu gao_yong.py](https://github.com/QiYuTechOrg/QiYuTkServer/blob/HEAD/tbk/core/logic/gao_yong.py)、[dmcb 插件](https://github.com/zenganiu/flutter_dmcb_alibc/blob/HEAD/android/src/main/java/com/example/flutter_dmcb_alibc/FlutterDmcbAlibcPlugin.java)

**D2-6 基础物料接口返回的链接没有协议头**（置信度：中）
- 做法：物料接口可以直接带 relation_id，返回的推广链接已经含 pid。dmcb 在 url 不含 http 时把 `//uland` 替换成 `http://uland`。
- 边界情况：dmcb 补的是 http:，而且只处理了 uland；以 `//s.click` 开头的链接没有处理。阿里云 253965 页面属于「图像搜索·淘宝联盟版」，示例链接同样不带协议头，还给了 `tbopen://` 形式的 DeeplinkUrl。这只能旁证「联盟链接常不带协议头」。bububa 建模的是旧版 material.optional，我们规划用 material.optional.upgrade（09 CAP-TB-03），出参字段名要以官方或私有库手册为准。万能转链属于邀请制，新 App 拿不到。
- 对我们图的提示：登记我方推广链接前统一补成 `https:`，`//uland` 和 `//s.click` 都要处理。
- 来源：[bububa material.optional](https://github.com/bububa/opentaobao/blob/main/model/tbk/TaobaoTbkDgMaterialOptionalAPIRequest.go)、[bububa general.link.convert](https://github.com/bububa/opentaobao/blob/main/model/tbk/TaobaoTbkDgGeneralLinkConvertAPIRequest.go)、[阿里云 253965](https://help.aliyun.com/document_detail/253965.html)、[dmcb 插件](https://github.com/zenganiu/flutter_dmcb_alibc/blob/master/android/src/main/java/com/example/flutter_dmcb_alibc/FlutterDmcbAlibcPlugin.java)

**D2-7 京东 subUnionId 与拼多多 custom_parameters：转链时写入，订单里带回**（置信度：高）
- 做法：京东 subUnionId 最多 80 位，只能是字母、数字或下划线；它和 ext1 都要联系运营开白名单后才会在订单里返回。拼多多 custom_parameters 是 JSON，最长 64 字节，常见形如 `{"uid":..,"sid":..}`。拼多多的流程是：先用 member.authority.query 查 bind；没备案时，用 rp.prom.url.generate（channel_type=10）生成备案链接让用户授权，之后才能转链。
- 边界情况：sfb 直接把 uid 写进 subUnionId，再用 parseLong 反解。sfb 注释提到，拼多多未授权的订单在这个字段里返回的是 pid，不是 JSON。AgenticCPS 明确拒绝把裸数字的外部 ID 当成会员 ID。
- 对我们图的提示：写入不透明令牌，通过映射表回查用户，不写裸 user_id。京东白名单未开、拼多多未授权这两种「字段缺失或格式不对」的情况，在 D3 里要能落到「待人工」。

**D3-1 淘宝 order.details.get 的时间窗和翻页**（置信度：高）
- 做法：每次查询的时间窗平时不超过 3 小时，大促期间不超过 20 分钟。query_type 有 1 创建、2 付款、3 结算、4 更新四种。从第 2 页起必须把上一页返回的 position_index 和 jump_type 原样传回。

## D4 佣金预估 → 结算 → 入账 → 扣回，以及账本

**D4-1 竞品的到账节奏**（置信度：高）
- 做法：按平台和金额分档，都从「确认收货且没有退换货」开始算；大额订单在次月 20 或 21 日月结。
- 边界情况：省钱快报原文的条件是：超级返 20 元以上、且用户发生过一次维权的订单，才推迟到次月 21 号到账，并不是所有维权订单都推迟。一淘对快速达、极速达用户给不低于 80 元的授信额度：快速达确认收货后立即到账，极速达付款后立即到账。
- 对我们图的提示：D4 把「平台结算」和「用户入账」画成两个节点，中间可以有提前入账（授信）的支线。数值以 08 为准。
- 来源：[省钱快报 rt/275](https://m.sqkb.com/rt/275/?type=1)、[返利网 返利相关问题](https://help.fanli.com/a/fanlixiangguanwenti/)、[一淘 购物问题](https://mo.m.etao.com/etao/shoppingchart_question)

**D4-2 上游淘宝联盟的结算节奏**（置信度：中）
- 做法：每月 20 日结算上月确认收货的订单，扣 10% 技术服务费，退款会冲减佣金。
- 边界情况：来源是 2021 年的第三方文章，结算日和服务费都要以联盟官方当前规则为准，并登记到 09 或 08。
- 来源：[taokeshow 18992](https://www.taokeshow.com/18992.html)

**D4-3 扣回的顺序和欠款处理**（置信度：高）
- 做法：先扣余额，余额不够就记欠款。部分退款按实付金额重算差额，不是整单作废。
- 边界情况：一淘的规则是：欠款期间产生的返利订单，不论金额大小，一律推迟到确认收货后的次月 21 日发放。这是**延期发放**，不是直接拿来抵欠款。「新返利先抵欠款」是我们自己的设计选择。
- 对我们图的提示：D4 的扣回分支画出「余额足够 / 不足 → 欠款」以及「欠款期间的新入账如何处理」；具体策略以 08 为准。
- 来源：[一淘 购物问题](https://mo.m.etao.com/etao/shoppingchart_question)、[返利网 晒单相关问题](https://help.fanli.com/a/shaidanxiangguanwenti/)、[返利网 返利相关问题](https://help.fanli.com/a/fanlixiangguanwenti/)

**D4-4 风控冻结与追回**（置信度：中）
- 做法：发现刷单或套利时，延长发放（最多 180 天）或者冻结，并保留追回已发金额的权利。
- 边界情况：省钱快报 rt/275 写的是：可以收回违规订单的隐藏佣金、扣可用余额，严重的扣全部可用余额，并不再提供隐藏佣金服务（不是停掉全部服务）。淘粉吧的触发条件是系统检测到异常行为，或者接到恶意套取的举报。
- 对我们图的提示：D4 画一个「风控冻结或延期」状态，以及「追回 → 扣余额」这条边。
- 来源：[淘粉吧用户协议](https://m.taofen8.com/html/userpact.html)、[省钱快报 rt/275](https://m.sqkb.com/rt/275/?type=1)、[省钱快报首页](https://www.sqkb.com/)

**D4-5 只追加的分录，以及加锁顺序**（置信度：高）
- 做法：分录只追加不修改；余额缓存在账户行上，带 version。同一个事务里先按账户 id 排序，逐个 SELECT FOR UPDATE，然后更新余额、校验约束、写分录。分录另有带索引的 event_at，和 created_at 分开；还要校验币种一致。
- 对我们图的提示：D4 的账本节点注明「按账户 id 排序加锁」和「event_at 与 created_at 分开」。我方的业务唯一键（订单 + 事件类型、提现单号 + 阶段）要在这个基础上另外加。

- 做法：竞品承诺 1–3 个或 5 个工作日到账，节假日顺延，不承诺实时。返利网自己的说法也不统一：帮助页写 1–3 个工作日，隐私政策写 5 个工作日；打款方式是银联或支付宝。

**D5-3 uni.transfer 的同步结果和查询字段**（置信度：高）
- 做法：转账到支付宝账户时，同步结果实际只有 SUCCESS 和失败两种。DEALING、REFUND 只用于转银行卡，但状态机里仍要保留 DEALING 这个非终态。

**D5-4 超时或 SYSTEM_ERROR 表示结果未知**（置信度：中）
- 做法：这种情况既不能当成功，也不能当失败。只能用同一个 out_biz_no 去查询，或者用完全相同的参数重发。

**D5-5 确定性的业务错误直接判失败；付款方问题和收款方问题分开**（置信度：中）

**D6-3 Apple 登录的服务端校验**（置信度：高）
- 做法：服务端校验 identityToken 的五项内容，并在 5 分钟内用 authorizationCode 换到 refresh_token 后保存。原生 App 的会话有效性应跟本地的 getCredentialState 结果绑定，这个调用开销很小；refresh_token 校验主要用于非 Apple 平台。每次启动都去要新的 identityToken 可能被限流。

**D6-4 Apple 身份键与 App 转移**（置信度：高）

**D6-5 Apple 服务端通知与注销**（置信度：高）
- 做法：用户对某个 App 停用 Apple 账号授权时，服务端收到 consent-revoked 通知；删除 Apple 账号还会停掉所有相关 App 的邮件转发。同一个通知 URL 可以被多个 Team 和 App 共用。注销必须能在 App 内完成：有令牌就调 /auth/revoke；没有令牌就按 TN3194 走手动流程，但注销本身必须完成。TN3194 还要求处理撤销事件：原生端监听凭据撤销，服务端处理 consent-revoked；收到后删除用户数据（包括用来撤销的令牌和 Keychain 里的数据），客户端恢复为未登录。
- 边界情况：建号时要把 refresh_token 安全保存，否则注销时没有令牌可撤。TN3194 建议每天最多校验一次 refresh_token。revoke 对已失效的令牌也返回 200，所以可以放心重试，这一点是推断。
- 对我们图的提示：D6 的注销分支有两个入口：用户主动注销、收到撤销通知。
- 来源：[Apple 处理账号变化](https://developer.apple.com/documentation/signinwithapple/processing-changes-for-sign-in-with-apple-accounts)、[Apple 账号删除要求](https://developer.apple.com/support/offering-account-deletion-in-your-app/)、[Apple revoke tokens](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)、[TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple)

**D6-6 App Store 审核指南 4.8 与 5.1.1(v)**（置信度：高）
- 做法：如果 iOS 用微信登录来建立或认证主账号，就必须同时提供一种满足三项要求的等效登录方式，Apple 登录是最省事的选择，但原文没有指定必须是它；如果微信只用于绑定或收款，4.8 不适用。5.1.1(v) 要求 App 内提供撤销社交账号凭据、断开数据访问的入口（例如解绑微信）。原文还写明 App "may not store credentials or tokens to social networks off of the device"。
- 对我们图的提示：服务端用 code 换到 openid / unionid 之后，是否长期保存微信的 access_token / refresh_token，要在图上标出来，交负责人确认实现方式。

**D6-7 短信供应商的限流和我方计数口径不一致**（置信度：高）

## D8 App 与 H5 的桥和签名请求

**D8-1 Android addWebMessageListener**（置信度：高）
- 做法：桥只会注入到 origin 命中规则的 frame 里；同源的 iframe 也会被注入，所以每次调用仍要检查 isMainFrame。
- 边界情况：「要在 loadUrl 之前注册」是从「对之后每次导航生效」推出来的。「设备不支持时就不注入桥，不退回 addJavascriptInterface」是设计决定，和规划/03 禁用 addJavascriptInterface 一致。新版 androidx.webkit 另有一个带 JavaScriptExecutionWorld 参数的重载，要先检测特性才能用，MVP 不需要。
- 来源：[WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat)、[Android 不安全的 WebView 桥](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)

**D8-2 iOS 以 WKScriptMessage.frameInfo 为准**（置信度：高，其中「返回 Promise」一点为中）
- 做法：检查 isMainFrame，并按协议、主机、端口三项精确比对 securityOrigin。需要回复的 handler（WKScriptMessageHandlerWithReply）要用 addScriptMessageHandler(_:contentWorld:name:) 注册，传 .page。这种 handler 在该 content world 的所有 frame 里都能调用，所以每次调用都要做上面的检查。回复通过 replyHandler(reply, errorMessage) 返回。
- 边界情况：「postMessage 返回 Promise」在本次读到的页面里没有原文佐证。
- 来源：[WKScriptMessage.frameInfo](https://developer.apple.com/documentation/webkit/wkscriptmessage/frameinfo)、[WKFrameInfo](https://developer.apple.com/documentation/webkit/wkframeinfo)、[securityOrigin](https://developer.apple.com/documentation/webkit/wkframeinfo/securityorigin)、[WKScriptMessageHandlerWithReply](https://developer.apple.com/documentation/webkit/wkscriptmessagehandlerwithreply)、[isForMainFrameOnly](https://developer.apple.com/documentation/webkit/wkuserscript/isformainframeonly)、[WKContentWorld](https://developer.apple.com/documentation/webkit/wkcontentworld)

**D8-3 鸿蒙 ArkWeb 的白名单和 iOS / Android 不对等**（置信度：高）
- 做法：白名单只校验 URL：path 按前缀匹配，port 留空就不检查端口，没有 isMainFrame 这样的概念。
- 边界情况：开发指南示例里，对象级白名单的注释写着「匹配就授权所有方法」；API 参考写的是方法级白名单存在时取两者交集。以 API 参考为准，并在 HM-03 实测。ArkWeb 校验的是发起调用的 frame 的 URL 还是主页面 URL，文档没说。「用 CSP（frame-src / child-src）禁止自有 H5 嵌入第三方 iframe」是推断。
- 来源：[OpenHarmony 页面调用应用侧函数](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/web/web-in-page-app-function-invoking.md)、[WebviewController API](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/reference/apis-arkweb/arkts-apis-webview-WebviewController.md)

**D8-4 每次桥调用都按调用方的 origin 实时校验，不能依赖 getUrl**（置信度：中）
- 做法：BlackHat 的研究指出，即使在调用当时取 WebView.getUrl() 做校验，也能被绕过：浏览器发起的导航还在进行时（比如桥方法或 shouldOverrideUrlLoading 里调了 view.loadUrl(url)，或者 deeplink 打开页面），getUrl 返回的是尚未提交的目标 URL，攻击页还在执行，却能让 getUrl 显示为白名单地址。
- 边界情况：OWASP MASTG-TEST-0033 建议在每个桥方法里用 getUrl 校验，这正是被证明不安全的做法，只能当反例。掘金文章推荐的是「host 完全等于，或以 `.域名` 结尾」，带点的后缀匹配是安全的，不带点的 endsWith 才不安全。微信小程序的端口规则只对 https 成立，wss 不配端口时允许任意端口。
- 对我们图的提示：D8 的校验节点使用 sourceOrigin / frameInfo，scheme、host、port 三项完全相等；shouldOverrideUrlLoading 里不要用 loadUrl 去转发导航；桥上不暴露打开任意 URL 的方法。
- 来源：[掘金 7646632889625215028](https://juejin.cn/post/7646632889625215028)、[BlackHat Asia 2021](https://i.blackhat.com/asia-21/Friday-Handouts/as-21-Qin-The-Tangled-WebView-JavascriptInterface-Once-More.pdf)、[微信小程序网络](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)、[OWASP MASTG-TEST-0033](https://mas.owasp.org/MASTG/tests/android/MASVS-PLATFORM/MASTG-TEST-0033/)

**D8-5 防重放：时间戳 + nonce**（置信度：中）
- 做法：nonce 的去重保留时长必须覆盖整个时间戳可接受窗口。阿里云 API 网关遇到重复 nonce 会报 S403NU。
- 边界情况：「nonce 15 分钟内不得重复」只在检索摘要里出现，本次读到的页面里没有原文。143207 是阿里云生活物联网平台的文档，那里 nonce 是可选项。wechatpay-go 那段代码校验的是微信支付回包和通知的签名，只有时间窗、没有 nonce 去重，挡不住窗口内的重放。微信支付的签名串和 BR-ID-09 只是结构相似，具体构造（最后一行内容、换行、签名算法）不同，以 BR-ID-09 为准。
- 对我们图的提示：校验顺序画成「时间戳 → 签名 → 原子写入 nonce」（这样攻击者没法用伪造请求提前占掉 nonce，属于推断）；nonce 保留时长从首次接受开始计，至少覆盖可接受窗口，取值见 BR-ID-09。签名只防网络层重放；要防恶意 H5 反复调桥，靠手势确认、signed_paths 和限流，与规划/03 一致。
- 来源：[阿里云 API 网关错误码](https://help.aliyun.com/zh/api-gateway/error-codes)、[阿里云 143207](https://help.aliyun.com/zh/document_detail/143207.html)、[wechatpay-go validator](https://github.com/wechatpay-apiv3/wechatpay-go/blob/main/core/auth/validators/wechat_pay_validator.go)、[wechatpay-go const.go](https://github.com/wechatpay-apiv3/wechatpay-go/blob/main/core/consts/const.go)、[微信支付签名](https://pay.weixin.qq.com/doc/global/v3/zh/4012354988)

## 来源与局限

- **来源范围**：只用了公开网页、公开 GitHub 仓库、官方文档和官方 SDK 源码，以及竞品公开的隐私政策、用户协议和帮助页。**没有下载、反编译或解包任何第三方 APK / IPA**，没有登录任何系统，没有用浏览器自动化。
- **开源淘客项目的代表性有限**：QiYu 和 sfb 分别通过折淘客、大淘客代理取单，没有直连 TOP，看到的参数和限制可能是代理方的；AgenticCPS 的部分功能（例如重叠窗口）写了但没启用。它们只能说明「别人怎么做、在哪里踩坑」，不能当作平台规范。
- **社区 SDK 注释**（bububa、typed-jd、dtapps）转录自官方文档，但可能滞后于官方，冲突时以官方文档中心和私有库手册为准（见记忆中的淘宝客 API 手册约定）。
- **竞品资料**只反映他们对用户的说法，看不到内部实现；各家说法不一致，版本日期也不同。
- **还没补上的缺口**（按图排列）：
