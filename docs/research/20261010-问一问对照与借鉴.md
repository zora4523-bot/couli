# 淘宝联盟「问一问」分析笔记 对照与借鉴（2026-10-10）

- 来源：负责人用 REA 在 AWS 测试机对淘宝联盟 App（`com.alimama.moon` 9.15.6）做的静态分析笔记，`~/我的项目/rea/ARCHITECTURE-NOTES.md` 与 `rea/docs/research/ai-guide-card-flow.md`（Codex 执笔）。笔记只读 APK 与反编译结果，没有运行 App、没有请求对方服务器，也没有取到聊天 H5 的业务脚本；所以「聊天协议、卡片字段、转链时机、模型」在对方那里全部是未知，笔记第 6 节的契约是 Codex 给我们的提案，不是对方事实。
- 本文做什么：把笔记里的每条「建议」和已确认的客户端做法，对到我们规划的现有条目上，给出 **已有 / 采纳 / 试行 / 不采纳** 四种结论和落点。按 规划/11 §2.6 与 2026-10-05 的做法（`20261005-文章方法对照.md`），外部做法先对照、最小试行、过 Codex 评审，不直接立规则；D19 架构独立照旧：只学做法，不抄对方的接口名、字段名、编码或 SDK 组合。
- 配套任务书：`couli-runs/briefs/AGENT-card-lane.md`（AI 商品推荐卡片：消息协议、卡片 schema、转链接口、三端 JSBridge）。

## 0. 一句话结论

对方客户端能确认的东西（原生壳 + WebView 承载聊天、剪贴板在 AI 页拦截淘口令、详情弹窗按点击取分享文案、受控路由与外跳兜底、开关 / 实验 / 资源 / 补丁四层控制面）我们的规划基本都已覆盖，而且在几个关键点上更严（出卡不预转链、卡片由服务端组装、模型看不到价格、三端原生对话页而不是 WebView）。真正值得补的是 6 处小项：诊断版本元组、未知事件处理、卡片曝光口径、客户端缓存键规范、AgentChat 页的剪贴板直送、SDK 能力清单。其余要么已有，要么与我们已定决定相悖。

## 5. 不学的（写明理由，免得以后再问）

- 聊天页用 WebView 承载、业务 JS 远程下发：违反 03 §1.2、§5.1 与 D19；我们三端原生对话页已拆成 APP-10。
- 识别到口令后把转换结果写回剪贴板：违反 BR-ID-16 细则「不清空、不改写」。
- `openScheme(url)` 式的通用外跳桥：我们只开放 `trade.*` 受控方法与 `ext.openApp`（apps.json 白名单）。
- 服务注册表 + Dagger + BeanContext 并存的多装配路径：我们只用 NestJS 一种依赖注入，不另引服务注册表；理由是排查一个依赖只追一条装配路径（笔记自己也指出多路径难排查），不是既有禁令。
- 原生热补丁与多渲染容器并存：MVP 不做。
