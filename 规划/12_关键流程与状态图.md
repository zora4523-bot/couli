## 1. 订单生命周期（双状态）

「我方统一订单状态」是子订单上两个互相独立的状态（BR-FUND-01，已确认）：`platform_status` 只由 order-sync 按平台状态码映射驱动；`rebate_status` 只由 settlement 迁移。`hold`、`rights_pending` 是 settlement 写的标志位，不改 `rebate_status`（BR-FUND-06）；用户看到的 `display_status` 由二者加标志位与金额派生、不入库，派生顺序只在 BR-FUND-17。迁移一律 CAS（`row_version` 加 1），同一子订单按 `order_key` 取 `pg_advisory_xact_lock` 串行；表外事件内部抛 IllegalTransition、不重试、告警，后台接口返回 20902（`data.resource=order`）。

下图只画「从、到、迁移编号与事件」；守卫、记账与副作用以 BR-FUND-01 迁移表为准（测试 ID `SM-PLT-P<n>`、`SM-REB-R<n>`）。事件名在 08 多为中文标签，只有 02 §7.2 的 `PLATFORM_*` 与 rebate 侧的 `CLAIM_APPROVED` 等有编码（§9 O-02）。

## 2. 点击 → 转链 → 外跳 → 归因

出卡（搜索、详情、首页、识别、Agent）只登记 `link_id` 与报价快照、不转链；点击购买一律走 `POST /v1/links/{link_id}/open`（拍板第二批 TRADE-03）。`POST /v1/links/convert` 只供没有 link_id 的 H5 入口（`trade.convertAndOpen`），同一请求内登记 link 后按 open 同样处理。京东、拼多多在服务端转链；淘宝按 2026-10-03 变更记录不调链接 API，open 下发百川打开指令、由客户端百川 SDK 完成淘客转链（§2.4，BR-ATTR-05、BR-ATTR-27 淘宝说明）。

## 3. 订单同步与归因流水线

按 BR-ATTR-01 的顺序画（与 02 §5.2 的先后有出入，见 §9 S-01）。`platform_status` 唯一写者 orders 的 order-sync；`rebate_status` 唯一写者 settlement，由 order-sync 在同一事务内调用 settlement 命令迁移（BR-FUND-01）。同步、找回通过、管理员改派共用同一把 `order_key` advisory 锁（02 §18）。

```mermaid
sequenceDiagram
  autonumber
  participant S as worker·scheduler
  participant Q as 队列 order-sync.{platform}
  participant W as worker·orders（order-sync）
  participant UA as union Adapter
  participant UP as 联盟订单接口
  participant DB as PG（order_keys、orders、order_status_history、sync_cursors）
  participant T as settlement（命令）
  participant M as commission
  participant EV as 领域事件（evt.*）

  S-)Q: 窗口任务，singletonKey=platform:account:kind:window_start（02 §7.1）
  alt 同键任务已在队列中
    Q->>Q: 新任务被静默丢弃（是否等价于去重待 B1-01 实测）
  end
  Q->>W: 取窗口任务
  opt 该同步依赖站长授权且授权已过期（BR-ID-24）
    W->>W: 记断点并暂停，重新授权后从断点补拉（断点存放处未定，§9 S-06）

  else 成功
    UP-->>UA: 原始订单页
    UA->>DB: union_raw_payloads（请求摘要、响应原文）
  end
  loop 每个子订单
    critical 同一事务
      W->>DB: pg_advisory_xact_lock（order_key），拿锁后重读

      end

      else 开启 attr.mtime_ordering 且平台更新时间早于库内（乱序旧数据）
        W->>W: 丢弃，不改任何字段（BR-ATTR-01）
      end
      opt user_id 为空
        W->>W: ② 用户归属（京东、拼多多 BR-ATTR-06；淘宝 BR-ATTR-07）
        alt 失败
          W->>W: 留在未归因池，计数，跳过 ⑤⑥（BR-ATTR-16）
        end
      end
      W->>W: ③ 黑名单（BR-ATTR-26）→ ④ buy_type、scene_basis（BR-ATTR-08、09）→ ⑤ 来源回填（BR-ATTR-15）
      W->>W: 平台状态码按 specs/order-status-map 映射为内部事件（BR-FUND-02）
      alt 映射表外的状态码，或缺收货时间
        W->>DB: 写待处理表并告警，状态不变（表名未定，§9 S-07）
      else 状态倒退（P10）
        W->>DB: 不迁移，写待处理表并告警
      else 正常
```

## 4. 佣金：预估 → 月结 → 入账 → 扣回，与余额

资金流向（02 §17）：settlement 只产出记账指令；ledger 是唯一改余额处；金额只由 `packages/domain` 计算。订单相关的余额与分录只能在该子订单 `rebate_status` 迁移（含自迁移）的同一事务内变更，不依赖领域事件（BR-FUND-01）。分录模板、uniq_key 格式与金额口径只在 08（BR-FUND-05、BR-FUND-08、BR-FUND-09）与 `specs/ledger-rules.md` 维护。

「联盟结算」与「用户入账」是两个节点：平台状态到 SETTLED 不等于入账，入账要等月结账单校验通过、人工确认后的批次执行（§4.2–§4.4）。业务扣回（CLAWBACK，§4.5）与纠错红冲（uniq_key 加 `:REVERSE`，BR-FUND-16）是两回事，后者只用于改派（R14）与调账更正。

### 4.4 单个子订单的入账事务（R5、R5a）

批次里有两类项：首次入账（订单为 WAITING，R5）与受益人补入账（订单已 CREDITED、该受益人的暂缓已解除，R5a）。**先判定每个受益人怎么处理，再写互斥的凭证**：正常入账、暂缓不入账、失效记平台，三者只取其一。

```mermaid

  participant T as settlement（settle.batch_execute）

        end
```

### 4.5 入账后扣回（R8、R9）

CREDITED 的子订单收到逆向事件时，扣回凭证与状态迁移在触发方的同一事务内完成（订单同步 §3.2、维权导入、后台复核确认）。判定顺序：先认出确定归零的事件，再给其余事件取新基数；先定每个受益人的扣回记到哪里，再写凭证。

```mermaid
sequenceDiagram
  autonumber
  participant X as 触发方（order-sync、rights-imports、后台复核确认）
  participant T as settlement（命令）
  participant M as commission
  participant L as ledger
  participant P as payout 模块（evt 消费者）
  participant N as notification

  X->>T: CREDITED 子订单的逆向事件（退款、维权成功、处罚、平台失效、结算后退款或失效、佣金由正变零、BLACKLIST_CONFIRMED）
  break 同一事件重放（该事件的 uniq_key 已存在）
    T->>T: 不写，幂等结束
  end
  alt 整单类事件（R8：整单失效、全额维权成功、处罚、结算后失效、黑名单复核确认）
    T->>T: 新基数取零，不看本次有没有带佣金字段
  else 其余事件（部分退款、部分维权等），且本次自带联盟新佣金
    T->>T: 新基数取该值（为零时同样走 R8）
  else 其余事件，order_rights 记录了应扣佣金
    T->>T: 新基数由已入账基数减应扣佣金得出
  else 其余事件，两者都没有
    T->>T: 新基数未知
  end
  break 新基数未知
    T->>T: 不写扣回，order_rights 置 WAIT_COMMISSION，订单进待处理表并告警，等联盟回传新佣金（BR-FUND-08）
  end
  T->>M: 按新基数与快照重拆，算各受益人应扣额与平台留存差额
  break 各受益人与平台的差额都为零
    T->>T: 不写
  end
  T->>M: 逐个受益人读账户状态，定下扣回记到哪个科目
  critical 同一事务
    loop 每个应扣额大于零的受益人
      alt 账户正常
        T->>L: CLAWBACK 凭证，只扣 available，可以变负，不动 frozen
        opt available 由不小于零变为小于零
          L->>L: 记 negative_since（BR-FUND-12）
          L-)P: account.went_negative（同事务入队，§5.7）
        end
      else 受益人已进入注销处理或已注销
        T->>L: 同一键的凭证改记平台坏账，不写其账户（BR-FUND-08）
      end
    end
    T->>L: 平台留存差额凭证（可正可负，不为零才写）
    alt 新基数为零
      T->>T: R8 → CLAWED_BACK（CAS），已入账基数清零
    else 新基数大于零
      T->>T: R9 保持 CREDITED，更新已入账基数
    end
    T-)N: order.clawed_back → CLAWBACK 通知（BR-TEXT-09）
  option 记账失败或 CAS 冲突
    T->>T: 整个事务回滚。CAS 冲突时重读后重新判定（02 §18）
  end
  Note over T,L: 逆向事件到 sub_type（FULL、PART_REFUND、RIGHTS、PUNISH）的对应关系 08 没写全，待定：见 §9 F-10。加锁顺序见 §9 F-03
```

**覆盖的异常情况**

- [x] 同一事件重放（uniq_key 幂等）、重算差额为零（不写）
- [x] 整单失效先于「取不到新基数」判定：即使没带佣金字段也按归零扣回，不会被挂起
- [x] 部分退款、部分维权取不到新基数（WAIT_COMMISSION，不扣回，继续阻止后续入账）
- [x] 扣回后余额变负（只扣 available，入队 `account.went_negative`）
- [x] 受益人已注销（改记平台坏账，与入其账户二选一）
- [x] 已入账订单命中黑名单（不自动扣回，人工复核确认后才走本图）
- [x] 记账失败、并发冲突（整体回滚）

**实现的 BR / AC**：BR-FUND-01 R8、R9；BR-FUND-06、08、10、12、16；BR-ATTR-26；BR-CALC-09、15；BR-WDR-05；AC-S2-06、AC-S2-06-JD、AC-S2-07、AC-S2-08、AC-S2-09、AC-S2-46。

### 4.6 结算额写入与佣金变化（R10 负差、R9b）

结算额低于已入账基数（负差）在写入结算额的同一事务里立即扣，不等审批；高于（正差）只生成候选，批准后才补（§4.7）。价保、比价降佣等佣金下调不属于逆向事件，不写 CLAWBACK，走 R9b。

```mermaid
sequenceDiagram
  autonumber
  participant X as 触发方（order-sync 或结算明细入库）
  participant T as settlement（命令）
  participant DB as PG（order_settlements、orders）
  participant L as ledger
  participant P as payout 模块（evt 消费者）

  alt 结算额写入（R10）
    X->>T: 联盟回传或明细里的结算佣金
    T->>DB: order_settlements 追加一条（内容不同才 seq 加 1，source 为 API 或 STATEMENT），更新 orders.settle_commission_fen（明细优先，BR-FUND-09）
    opt API 与明细金额不一致
      T->>L: recon_diffs，以明细为准
    end
    alt 内容相同的重复记录（seq 不变），或结算额等于已入账基数
      T->>T: 不补差
    else 结算额低于已入账基数（负差）
      T->>L: 同一事务按受益人写负向 SETTLE_ADJUST（uniq_key 含 seq），更新已入账基数，available 可以变负
    else 结算额高于已入账基数（正差）
      T->>T: 本事务不记账，等 §4.7 生成候选并批准
    end
  else 佣金变化（R9b：价保、比价降佣、联盟调整。既不是退款也不是维权）
    X->>T: 新的预估佣金
    T->>DB: 更新 est_commission_fen，commission_version 加 1
    alt 新基数低于已入账基数
      T->>L: 同一事务写负向 SETTLE_ADJUST（uniq_key 含 sub_type 与 commission_version），更新已入账基数
    else 新基数高于已入账基数
      T->>T: 不记账，进 §4.7 的正差候选
    end
  end
  opt 负向补差后结算佣金为零，且全部受益人与平台净额为零
    T->>DB: → CLAWED_BACK（R10）
  end
  opt 某受益人 available 由不小于零变为小于零
    L-)P: account.went_negative（§5.7）
  end
  Note over T,L: 受益人已注销时的负差记到哪里，BR-FUND-09 没写（BR-CALC-09 写记坏账），待定：见 §9 F-02
  Note over X,T: 京东的结算变动体现在哪些字段待 CAP-JD-08（§9 O-06）
```

**覆盖的异常情况**

- [x] 同一结算记录重复到达（seq 不变，不重复补差）
- [x] 结算少于已入账（即时扣，可能使余额变负）
- [x] 结算多于已入账（不自动加钱，走人工批准）
- [x] 接口结算额与明细不一致（以明细为准并出差错单）
- [x] 价保、比价降佣（R9b，不写 CLAWBACK）
- [x] 补差后净额归零（转 CLAWED_BACK）

**实现的 BR / AC**：BR-FUND-01 R9b、R10；BR-FUND-09；BR-FUND-10；BR-CALC-09、14、23；拍板第二批 FUND-11；AC-S2-11。

### 5.4 payout 任务：复核与转账

payout 进程是唯一持有通道密钥的进程，没有公网入站，所以**不接收支付宝异步通知**，结果只靠同步返回、主动查询与每日对账（是否接通知见 §9 W-08）。

```mermaid
sequenceDiagram
  autonumber
  participant Q as payout 队列
  participant P as payout 进程
  participant DB as PG（withdrawals、payout_attempts、ledger_*）
  participant Z as 支付宝开放平台

  Q->>P: 取任务（去重键为 withdrawal_id 加 execute_seq。转账任务不自动重试，单并发，BR-WDR-13）
  P->>DB: 读单据
  break ① 单据不是 PAYING，或任务的 execute_seq 不是单据当前值（重复或过期任务）
    P->>P: 直接结束，不转账也不查询
  end
  break ② 该单已有 kind=transfer 的尝试记录（进程在请求发出后崩溃重启、任务被重投）
    P->>P: 不转账，转入 §5.5 的查询
  end
  P->>DB: 在 advisory 锁 payout_daily 内按序复核（BR-WDR-13 ③，开关直读 PG）
  break ③ 复核不过
    P->>DB: W9 HOLD → APPROVED（CAS），写 hold_reason（payout_disabled、queue_paused、member_blocked、single_cap、daily_cap 之一）与 hold_at，清空执行人与执行时间

  end
  P->>DB: ④ 同一把锁内写 payout_attempts（kind=transfer，result=pending）并提交（先记后发）
  P->>Z: ⑤ alipay.fund.trans.uni.transfer（out_biz_no、收款账号与姓名取单据快照。场景字段与证书签名见 09 §5.3，待 CAP-X-06）
  Note over P,Z: 通道调用在事务之外，不持有行锁。结果另开事务写回
  alt 明确成功
    P->>DB: 同一事务 W5 → PAID_API（CAS），记通道单号与到账时间，写成功分录一张凭证（BR-WDR-09），更新 tax_ytd，尝试记 success
  else 返回码在 payout.definite_fail_codes 内（验证前清单为空，BR-WDR-28）
    P->>DB: 同一事务 W6 → FAILED，WITHDRAW_RETURN，记 fail_code，尝试记 fail
  else 返回码在 payout.payer_side_codes 内（验证前清单为空）
    P->>DB: W9 → APPROVED，hold_reason=payer_side_after_transfer，不退回余额，置 payout.queue_paused 并告警
    Note over P,DB: 这张单已有转账尝试，不得再执行，只能手动成功（W8）或驳回（W3），BR-WDR-17
  else 返回了三份清单之外的业务码
    P->>DB: 按结果未知处理：保持 PAYING（W7），尝试记 unknown。同时置 payout.queue_paused 并告警（BR-WDR-28）
  else 超时、网络错误、HTTP 5xx、SYSTEM_ERROR
    P->>DB: 结果未知：保持 PAYING（W7），尝试记 unknown
  end
  opt 结果未知（后两种）
```

- [x] 发出前复核不过（W9，不到达转账调用；没有转账尝试，可再次执行）

- [x] 超时、网络错误、5xx、SYSTEM_ERROR（只查不重提）

## 6. 登录与第三方空号并号

所有登录方式与刷新都要求签名（BR-ID-09），因此必须先在用户同意隐私政策后完成设备注册（BR-ID-11）。拒绝码按 BR-ID-01 的顺序返回第一个。同一自然人用微信与手机号分别登录会得到两个账号，不自动合并；唯一例外是第三方登录新建的空号在绑定手机号时并入老号（BR-ID-06，拍板第二批 OPS-04）。

```mermaid
sequenceDiagram
  autonumber
  actor U as 用户
  participant C as App
  participant X as 微信 SDK / Apple
  participant G as api·risk（签名 Guard、限流）
  participant I as api·identity
  participant SMS as 阿里云短信
  participant DB as PG（users、user_oauth、sessions、refresh_tokens、login_logs、consent_records）

  U->>C: 同意隐私政策（BR-ID-11）
  C->>I: POST /v1/devices（设备标识哈希）
  I-->>C: device_id、install_secret（存 Keychain / Keystore / HUKS）
  alt 后续请求返回 10402（设备未注册或已吊销）
    C->>I: 重新注册设备后重放原请求（次数 BR-ID-09）
  end

  alt 手机号验证码登录
    C->>G: POST /v1/auth/sms-codes（purpose=login，签名）
    alt 号段或手机号黑名单
      G-->>C: 44001
    else 需要人机验证
      G-->>C: 44003 → 拉起验证组件，带凭证重发
    else 发码频控
      G-->>C: 42901 加 Retry-After
    else 通过
      I->>SMS: 发送 SMS_CODE（新码作废同 purpose 旧码）
      I-->>C: 重发间隔、有效期（取值 BR-ID-05）
    end

    C->>I: POST /v1/auth/login/sms（phone、code、legal_versions、consent_at、可选 invite_code）
    alt 验证码错误
      I-->>C: 20002
    else 过期、已作废或错满次数
      I-->>C: 20003
    else 账号在注销处理中
      I-->>C: 10007
    else 新号且同设备注册超限
      I-->>C: 44001，不建号
    end
  else 微信登录
    C->>X: SendAuthReq
    alt 用户取消或拒绝授权
      X-->>C: 取消，客户端留在登录页（服务端无请求）

      X-->>C: code（一次有效）

      I->>X: 用 code 换 unionid
      alt code 已用、过期或微信接口报错
        I-->>C: 失败（错误码未分配，§9 A-04）
      end
    end
  else Apple 登录（iOS）
    C->>X: Sign in with Apple
    alt 用户取消
      X-->>C: 取消
    else 成功
      C->>I: POST /v1/auth/login/apple（Apple 凭证、legal_versions、consent_at）
      I->>X: 校验凭证得 sub，加密保存 Apple refresh_token（注销时撤销，BR-ID-04）
    end
  end

  critical 同一事务
    I->>DB: 老用户按 phone_hmac 或 user_oauth（provider、union_id）查到即登录，否则建号（register_method）
    I->>DB: 写 consent_records（登录成功才写，BR-ID-04、BR-ID-12）、sessions、refresh_tokens、login_logs
    opt 新号带 invite_code
      I->>DB: SAVEPOINT 内绑定上级，失败不影响注册（BR-INV-06）
    end
  end
  I-->>C: access_token、refresh_token、is_new_user、invite_bind
  Note over C,I: 已封禁用户照常签发令牌，之后白名单外接口一律 10006（BR-ID-31）

  opt 第三方新建账号绑定手机号
    C->>I: POST /v1/me/phone（purpose=bind 验证码，签名，Idempotency-Key）
    alt 目标手机号命中黑名单
      I-->>C: 44001
    else 目标号属于其他账号且不满足并号条件
      I-->>C: 30411（无 reason），不迁移任何资产

        U->>C: 保留当前账号，结束

        else 同键处理中
          I-->>C: 40901

          end

        end

        end
      end

    and
      C->>I: merge（账号乙，同一 provider）
    end
    Note over I: 目标账号同 provider 唯一缺数据库约束兜底（§9 A-02）
  end

  opt access_token 过期
    C->>G: 多个请求同时收到 10002，客户端单飞只刷新一次（03 §4.2）
    C->>I: POST /v1/auth/refresh（签名）
    alt 宽限内重复提交同一旧 refresh_token
      I-->>C: 返回同一对新令牌（BR-ID-07）
    else 旧 refresh_token 被复用（疑似泄露）
      I->>DB: 吊销整条 sid 链
      I-->>C: 10404 → 清会话、跳登录
    else 正常轮换
      I-->>C: 新 access_token 与 refresh_token
    end
  end
```

**覆盖的异常情况**

- [x] 设备未注册或已吊销（10402，重新注册后重放一次）
- [x] 发码黑名单、人机验证、频控（44001、44003、42901）

## 7. 淘宝渠道备案（relation_id）与站长授权到期

淘宝订单的用户归属只靠 `relation_id`（BR-ATTR-07），备案只在用户点击购买时触发（BR-ID-17），一次绑定、不提供用户自助换绑（拍板第二批 §8 ADD-01）。授权页走百川还是 H5 OAuth 按 CAP-TB-05 实测定，两条都保留（09 5_X §5.5）；「百川套件备案页」在 09 中没有记录，图中按「百川授权组件或 H5 授权页」两路画。备案流程本身不受 2026-10-03 转链变更影响（变更记录 §2 未改 BR-ID-17、19），绑定成功后的购买按 §2.4 打开。

## 8. App ↔ H5 桥签名请求

App 内 H5（`TrustedWebView`）调用需签名的接口只能经桥方法 `net.signedRequest` 由原生代签代发；h5_token 不能直接调签名接口（BR-ID-32）。原生只签 `bridge.schema.json` 的 `signed_paths`，MVP 只有 `POST /v1/orders/claims`（拍板第二批 TECH-30）。下图以找回提交为例；方法级别、超时、桥错误码以契约 CT-03 `bridge.schema.json` 为准。

```mermaid
sequenceDiagram
  autonumber
  actor U as 用户
  participant H as H5 页面（TrustedWebView）
  participant B as App 原生桥
  participant N as App 网络层
  participant G as api·risk（签名 Guard、限流）
  participant O as api·orders（找回）
  participant DB as PG（idempotency_keys、claims、claim_items）

  Note over B: 启动与回前台：bridge_origins 白名单随 GET /v1/config 下发并带服务端签名，验签失败用包内内置（03 §5.1，02 §10）
  H->>B: has（net.signedRequest）（TECH-28）
  alt 当前端未实现该方法（since 为 null 或版本过低）
    B-->>H: false
    H->>H: 不调用，提示升级（03 §4.4）
  end
  opt H5 先取 h5_token 调普通接口（不用于签名接口）
    H->>B: auth.getH5Token（L1）
    B->>N: POST /v1/auth/h5-token
    N-->>B: token、expire_at（aud=h5，BR-ID-32）
    B-->>H: code 0，data.token
    Note over H: h5_token 直接调签名接口或作用域外接口会被拒（10401 或 10403，判定顺序 BR-ID-01）
  end
  U->>H: 点击「提交找回」
  H->>B: 信封 v、id、method=net.signedRequest、params（method=POST、path=/v1/orders/claims、body）
  B->>B: L0 校验：主 frame 且 origin 在白名单
  alt origin 或 frame 不允许
    B-->>H: 90403
  end
  B->>B: L1 校验：原生已登录
  alt 未登录
    B-->>H: 90401（H5 可先调 auth.login 再由用户重新点击）
  end
  B->>B: L2 校验：最近有用户手势（时限见 03 §5.3）
  alt 无手势

  end

  N->>G: POST /v1/orders/claims
  G->>G: 验签、时间戳窗口、device_id 加 nonce 去重（BR-ID-09）
  alt 签名无效或 nonce 重复
    G-->>N: 10401
  else 设备未注册或已吊销
    G-->>N: 10402
    N->>N: 重新注册设备后带新签名重放（次数 BR-ID-09）
  else access_token 过期
    G-->>N: 10002
    N->>N: 单飞刷新后重放，沿用原 Idempotency-Key（BR-ID-07，03 §4.2）
  else 限流
    G-->>N: 42901 加 Retry-After
  end
  G->>O: 通过，进入幂等判定（04 §5）
  alt 同键处理中
    O-->>N: 40901
  else 同键不同请求体
    O-->>N: 20901
  else 同键已有结果
    O-->>N: 原样返回首次结果（成功或 3xxxx）
  else 首次请求
    O->>DB: 按 app_id 加 user_id 取 advisory 锁，按 BR-ATTR-17 顺序校验，同一事务写 claims、claim_items、idempotency_keys

  B-->>H: code 0，data.status、data.body（业务码在 body.code，见 §9 B-02）
  par 用户连点或页面重复发起
    H->>B: 第二个 net.signedRequest（新信封 id）

  opt 用户关闭页面或取消

  end
  opt 原生内部异常
    B-->>H: 90500
  end
```

- [x] 桥超时后不换键重提（90003）
- [x] 用户取消、页面关闭、原生异常（90004、90500）
- [x] h5_token 越权调用签名接口（10401 / 10403）
