## 1. 游客也能看到并关闭 Android 剪贴板开关

**原写法**：08 BR-ID-16 只写 Android「打开 App 自动识别剪贴板」默认开启、可在设置里关闭；BR-ID-02 细则列出的游客（已同意、未登录）设置清单是隐私中心、协议与隐私政策、关于、帮助、清除缓存，没有这个开关——已同意的游客会被自动识别，但在设置里关不掉。

**改为**：

1. 这个开关是**设备级设置**：存在本机，不随账号走。已同意当前版本隐私政策的游客在设置页也显示这一行、也能关闭，不需要登录，也不必撤回全部同意；登录、退出与切换账号都不改变它的值。
2. 基本模式（未同意隐私政策）不读剪贴板，设置页也不显示这一行（原规则就不读，本次写明不显示）。
3. iOS、鸿蒙不显示这一项（不变）；读取前提、时机、先提示后上传等其余限制仍只按 BR-ID-16。

**涉及 BR**：BR-ID-16（正文 Android 一句、细则新增「开关的适用范围」与两个例子、需同步一行）；BR-ID-02 细则「未登录时的隐私入口」游客与基本模式两条。

**受影响的页面与接口**：Android 游客设置页（稿面 `SettingsGuest`）多一行开关；接口与契约不变（开关只在本机，`clipboard.setAutoDetect` 不变）。

**验收**：10 AC-S1-03 的 Android 部分补一段——游客设置页有这一开关且为开启，关闭后回前台不读；随后登录，开关仍为关闭；基本模式设置页没有这一行、回前台不读。

**恢复方式**：删去 BR-ID-16 正文本次加的「该开关是设备级设置……不显示该开关」一句与细则「开关的适用范围」一段，BR-ID-02 细则删去游客清单的 Android 开关与基本模式的「不显示剪贴板开关」半句；01 `Settings` 行、03 §4.6、10 AC-S1-03 删去本次句子。

## 2. 注册被拦、没有账号的人按「注册请求」申诉

**原写法**：08 BR-ID-36 的申诉对象只有两类（账户：被封禁 / 被冻结；订单：风控作废返利），正文另写「未登录或注册被拦截者经企业微信联系客服，由客服在后台风控申诉页代为登记」，并注「代为登记是代理补全的默认，待负责人确认」。注册被拦截的人没有账号，两类对象都登记不了；规划/06「2026-10-05 设计审查待确认」第 11 项问的就是「是不是统一找客服代为登记」。

**改为**：

1. 未登录或注册被拦截者想申诉，**统一**经企业微信联系客服，由客服在后台风控申诉页代为登记（06 第 11 项已定）。
2. 申诉对象新增第 ③ 类「注册请求」：用手机号注册时被风控拦下（44001）、没有建号的那一次请求。客服按本人提供的完整手机号查出被拦的注册请求，页面只显示**脱敏手机号、拦截请求编号、拦截时间**与拦截原因类别；申诉单没有 user_id，不改任何账号的风控状态。
3. 处理时限与超时告警同账户申诉。结案：维持则拦截照旧；撤销则处理人把造成拦截的名单条目移出黑名单（BR-ID-31），本人之后可用该手机号重新获取验证码注册，系统不代为建号。
4. 没有账号，不发站内信；**处理结果由客服在企业微信会话里告知本人**。
5. 代理补全的默认：同一手机号同时最多 1 条处理中的注册请求申诉，已有的显示原申诉单、不新建。

**没定、登记到 06 第 22 项的**：非黑名单原因（设备注册数、落地页同一网络注册数）造成的拦截，撤销后怎样放行（定之前只能选维持）；已登录、账号正常的人在提现 / 换手机号 / 绑收款账号被 44001 拦下时后台按什么对象登记；第三方首次登录被拦下、没有手机号可查的人怎么登记；字段名与拦截请求编号的编码（由契约线定）。

**涉及 BR**：BR-ID-36（正文申诉对象、代为登记的说明、同一对象的唯一性、结案与通知、影响列的 target_type；细则状态、默认值、取代与新增「注册请求申诉」一段及其例子）。只作引用：BR-ID-05、BR-ID-06、BR-ID-31、BR-ID-32、BR-ID-33、BR-WDR-03、BR-TEXT-14 `cs.appeal_entry`。

**受影响的页面与接口**：后台风控申诉页【代登记申诉】（稿面 `AdmRiskAppealRegister`、`AdmRiskAppealRegisterNoAccount`）；注册页 44001 弹窗的【联系客服申诉】。04 只补形状：§3.2 `appeals.target_type` 加 `register_request`（user_id 为空，另存关联手机号 HMAC，同一手机号只 1 条处理中），`risk_hits` 写明注册请求这一行另存手机号 HMAC 与脱敏号、ref_id 即拦截请求编号；§6.1 用户侧申诉接口不接受 `register_request`；§11.2 `risk.appeal` 写明可按注册请求登记。用户侧接口与错误码不变。

**验收**：没有单列用例；后台风控申诉页验收时按 BR-ID-36 细则「注册请求申诉」的例子核对（按完整号码查到拦截请求、只显示脱敏号、登记后时限正确、撤销后可重新注册、不发站内信）。

**恢复方式**：BR-ID-36 正文改回「可申诉对象分两类」与原代为登记的写法（细则「取代」已登记），删去细则「注册请求申诉」一段；04 删去 `register_request` 及相关说明；06 第 11 项改回待负责人确认、删去第 22 项；01 F-ADM-18 删去本次半句。

## 4. 管理后台金额固定两位小数并加千分位

**原写法**：08 BR-TEXT-10（已确认）所有界面一律最多两位小数、去掉末尾 0、不加千分位，「影响」列含「后台金额列」。设计稿后台多数金额写成 ¥x.00 并加千分位，与规则不一致。

**改为**（负责人 2026-10-05「按你的建议，后台保留两位小数和千分位」）：

1. **管理后台**页面上的金额列与金额字段（列表、详情、弹窗、汇总卡、报表页）固定显示两位小数并加千分位，如 ¥20,000.00、¥0.00、-¥1.20；仍用整数分运算，负号、「+」与「¥」的位置不变；区间两端各按后台格式。
2. App、App 内 H5、站外 H5、推送、短信、站内信的写法**不变**（最多两位小数、去末尾 0、不加千分位）。
3. 比例（_bp）写法不变；后台金额输入框仍按元输入、最多两位小数，不要求输入千分位。导出文件的单元格写法不在本次范围。
4. 理由：后台要对账、比大小，位数对齐、千分位分组后不容易看错。代价：同一笔金额在 App 与后台写法不同（App ¥9.9、后台 ¥9.90），客服对照时以数值为准。

**涉及 BR**：BR-TEXT-10（正文加后台例外、影响列；细则状态、决策人、取代，新增「后台格式」一段与后台测试向量表，测试向量说明补后台向量）。

**受影响的页面与接口**：管理后台全部金额显示；`specs/client-behavior.md` 增加后台向量（建契约时写入）；接口不变（仍是整数分）。设计稿后台画板写 ¥x.00 的保留，审查点名已改成去末尾 0 的用户详情一族需改回两位小数（设计会话处理）。

**验收**：10 用例写法约定的「金额」一条补后台断言（2000000 → ¥20,000.00，0 → ¥0.00）；后台金额格式化的单元测试用 BR-TEXT-10 细则后台向量。

**恢复方式**：BR-TEXT-10 正文删去「管理后台例外」一句、影响列改回「后台金额列」，细则删去「后台格式」一段与后台向量表；03 §9.2「金额显示」与 §10.3 补句、10 的后台断言删去。
