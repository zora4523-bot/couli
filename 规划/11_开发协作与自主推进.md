## 0. 三条硬规则

1. **实现者不写自己的规则测试，也不评审自己。** 实现者只写单元测试。
2. **git 只有编排者一个写者。** 提交、推送、合并都由 Claude 主会话经 `tools/ops/` 脚本完成；任务书禁止 Codex 提交。沙箱只挡住一半：`<工作目录>/.git` 在 `workspace-write` 下只读（已实测），但 linked worktree 指向的 gitdir 不受这条保护，只有位于可写根之外才写不了（已实测：主仓库在 `/tmp` 下时 `git add` 成功、主仓库 `.git/config` 可写）。所以 Codex 结束后还要核对 HEAD 与暂存区未变（§2.4「位置断言」）。
3. **资金与归属的实现方和规则测试作者永远不是同一家模型。** 一家用不了就停，不降级。

目录约定：代码仓库 `/Users/zhixing/我的项目/rebate-platform/`；私有库 `/Users/zhixing/我的项目/rebate-private/`；运行产物 `/Users/zhixing/我的项目/couli-runs/`（不在任何仓库内）；门禁脚本的可信副本 `couli-runs/trusted/rebate-platform`（只跟随 `origin/main`）。主仓库、worktree、可信副本、`couli-runs` 一律不得放在 `/tmp` 或 `$TMPDIR` 下：那里是 Codex 沙箱的默认可写根（§2.4）。

## 2. 自主推进循环

需求文档到合并的路径：05 任务表 → `ops/tasks/` 台账 → 按 `SPEC_REF` 生成任务书 → 规则测试 → 实现 → 沙箱外验证 → 对抗评审 → 合并 → 验收记录。

### 2.1 台账

- **任务定义**：一任务一文件，`rebate-platform/ops/tasks/<id>.yaml`，覆盖四个代码仓库。格式见 `docs/templates/task-ledger.md`。入库的 `status` 只有 `todo` / `done`，`done` 在本任务的 PR 里改。
- **台账是 RV0，新任务的台账随任务 PR 一起进**（2026-10-02 负责人决定，代码仓库 `ops/approvals.yaml` 第 17 条）：`ops/tasks/**` 在 `ops/risk-map.yaml` 里是 RV0。CI 的 guard-git 照旧从基线读任务台账；只有基线没有 `ops/tasks/<id>.yaml`、而 `task/<id>` 分支的 PR 自己新增了它时，才从 PR 头提交读这一份（编号只取分支名，未提交的不算），其余守卫仍从基线跑。原来新任务的台账要先单独开 PR 进 main，而只改台账的 PR 算 RV2、要负责人打标签。
- **编号**：沿用 05 的原编号和原含义；拆分时加后缀（如 `B2-03a`）。入账脚本校验编号前缀在 `SPEC_REF` 版本的 05 里存在。05 的任务表只写计划，状态与拆分以台账为准。
- **在途状态不进 main**：存 `couli-runs/state/<id>.json`，先写临时文件再 `mv`；每天收工同步到 `rebate-private/ops-state/`。取值 `ready / spec / doing / verify / review / longrun / pr / blocked / ask / stale`，另记 `attempts`、`spec_commit`、`pid`、`started_at`、`owner_session`、`lease_until`（20 分钟，续期；过期才允许别的会话接手）。
- **看板不入库**：`pnpm ops:status` 从台账、在途状态与运行目录、git、gh、用量账本现算在途任务、未合并 PR、CI 状态、失败熔断、Codex 调用次数（只记账）、停滞告警（§7.2）。
- **归档**：`done` 满 30 天的任务文件移到 `ops/tasks/archive/<年月>/`；开场必读永不包含归档。
- 原生仓库任务的 `done` 由每晚一个 RV0 的台账同步 PR 写回。

### 2.2 驱动与互斥

- **从哪里启动**：`rebate-platform` 建好后，编排会话和定时任务一律从该目录启动。从 `couli/` 启动的会话只做规划文档。
- **心跳**：拦截钩子与 `codex` 垫片装好后启用（§7.3 第 5 项已确认）。定时任务每 30 分钟调用 `tools/ops/tick.sh`；派工脚本结束时主动触发下一步，不等心跳。定时任务的提示词写死：先只跑 `tick.sh`，输出为 `{"action":"none"}` 就不读任何文档直接结束。
- **编排锁**：`tick.sh` 第一步 `mkdir couli-runs/lock/orchestrator` 取原子锁，写入 pid 与心跳时间；锁被活进程持有就输出 none 并结束；心跳超过 20 分钟未更新才允许接管。
- **领任务**：`mkdir couli-runs/claims/<id>`，成功才派发。
- **tick 做三件事**：回收已结束的运行；算出 ready 任务（依赖全 `done`、`paths` 与在途任务不相交、该任务的失败熔断未打开）；输出下一步动作的 JSON，Claude 按输出行动。
- **负责人另开的对话**：Claude 开场先查编排锁；持锁期间不在 `rebate-platform` 提交，只把要做的事写进 `couli-runs/inbox/`。
- **后台运行**：Codex 任务可到 30 分钟，派工一律后台跑并用 `caffeinate` 防睡眠。
- **看门狗**：实现硬超时 30 分钟、评审 15 分钟。活性看 rollout 文件修改时间或进程 CPU；无活动阈值实现 5 分钟、评审 12 分钟。击杀必须杀整个进程组（§2.4「超时」）。超时的任务要拆小。

### 2.4 Codex 调用规范

Codex 只经包装脚本调用。脚本固定以下各项。已实测的坑（2026-10-01，codex-cli 0.154.0，macOS；Linux 上的沙箱未测）：

- 不关 stdin 会挂死；本机用户配置默认全盘读写加联网。
- 沙箱内没有任何网络（`workspace-write` 与 `read-only` 相同）：外网、DNS、Docker 套接字、127.0.0.1 上的 PG 都不可达，自己在回环或 Unix 套接字上监听也被拒。
- 读范围是全盘（`~` 下文件、相邻仓库都读得到）；`workspace-write` 的写范围是工作目录加 `/tmp` 与 `$TMPDIR`。
- `<工作目录>/.git` 只读，前提是目录不在 `/tmp` 下；linked worktree 指向的 gitdir 不受保护（§0 硬规则 2）。
- 在仓库根运行时，保护路径（`turbo.json`、`AGENTS.md` 等）沙箱不拦，已实测可写；路径守卫是唯一关口。
- `--ignore-user-config` 不屏蔽用户级 skill（含自动提交 skill）和用户规则。不带 `--ignore-rules` 时，规则放行的命令前缀在沙箱外执行（`git branch` 真的写进了 `.git`）。
- 带 `--ignore-user-config` 仍会把 git 工作目录写进 `~/.codex/config.toml` 的信任列表，每个路径一条；如何避免未测。

```bash
# 实现：tools/agent/codex-run.sh impl <id> 的内部等价命令
# 参数分三组各自实测跑通（§9.3 #1、#3）；三组写进同一条命令还没跑过，包装脚本首跑时自检
COULI_CODEX_WRAPPER=1 codex exec -C <wt> -s workspace-write --ignore-user-config --ignore-rules --json \
  -m gpt-6-astra -c 'model_reasoning_effort="high"' \
  -c 'skills.include_instructions=false' --disable plugins \
  -c 'sandbox_workspace_write.exclude_slash_tmp=true' \
  --output-schema $TRUSTED/tools/agent/schemas/impl.schema.json -o $RUN/impl.json \
  "$(cat $RUN/brief.md)" < /dev/null > $RUN/events.jsonl 2> $RUN/err.txt

# 评审：tools/agent/codex-run.sh review <id>（这组参数实测跑通过，当时用的是非 git 目录加 --skip-git-repo-check）
COULI_CODEX_WRAPPER=1 codex exec -C <wt> -s read-only --ignore-user-config --ignore-rules --json \
  -m gpt-6-astra -c 'model_reasoning_effort="xhigh"' \
  -c 'skills.include_instructions=false' --disable plugins \
  --output-schema $TRUSTED/tools/agent/schemas/review.schema.json -o $RUN/review-codex.json \
  "$(cat $TRUSTED/tools/agent/prompts/review-<类型>.md)" < /dev/null > $RUN/review-events.jsonl 2> $RUN/review-err.txt
```

- **参数来历**：
  - 第一组：`-s`、两个 ignore、`--json`、`-m`、推理强度、`--output-schema`、`-o`，退出码 0，`-o` 是符合 schema 的 JSON。
  - 第二组：`-c 'skills.include_instructions=false' --disable plugins`，实测后会话里不再有 skill 段和推荐插件段，自动提交 skill 出现 0 次。
  - 第三组：`exclude_slash_tmp=true`，在另一个实验里与 `-s workspace-write`、两个 ignore、`--json`、`-o` 同用，5 次成功。
- **模型**：`gpt-6-astra` 是忽略用户配置后的内置默认，显式传同一 id 被接受。其余模型 id 没试过，换模型前先单独试跑。
- **服务档位**：默认不传（标准档）。`-c 'service_tier="priority"'` 被接受，但事件和会话文件里都没有档位记录，是否生效未证实，且会多耗额度。要用时在包装脚本里显式打开，并记入用量账本（§1.3）。
- **禁用**：
  - `--dangerously-bypass-approvals-and-sandbox`。
  - 不带 `-s` 的裸 `codex exec`；不带 `--ignore-rules` 的 `codex exec`。
  - `-c sandbox_workspace_write.network_access=true`（已实测：一开即同时放开 Docker 套接字、本机 PG 和外网，拿到宿主 Docker 等于沙箱失效）。
  - 独立 `CODEX_HOME`（已实测：丢登录，401，重试 73 秒后退出码 1）。
  - `codex exec review` / `resume` 不带 `-c 'sandbox_mode="read-only"'`（这两个子命令与上面参数的组合未测，用前先试）。
  - 自带的 `--worktree`。
  - 包装脚本拒绝调用方透传 `network_access`、`sandbox_mode`、`--add-dir`（`--add-dir` 已实测能追加可写根，常规派工不用）。
- **垫片**：`PATH` 最前放一个名为 `codex` 的垫片，调用方没有 `COULI_CODEX_WRAPPER=1` 就拒绝执行（安装已获批准，§7.3 第 5 项）。
- **超时**：不得用 `alarm` + `exec`，也不得只杀 `codex` 外壳。已实测：外层 node 被杀后，原生 `codex` 进程和它的子命令又跑了约 90 秒，照常消耗额度，并在「超时」之后写出了 `-o`。包装脚本把 Codex 放进独立进程组，超时对整组先 TERM、5 秒后 KILL，确认组内无存活进程后才读 `-o`；调用前先删旧的 `-o` 文件。参考写法（只用 `codex sandbox -- /bin/sleep` 验证过：退出码 124、无残留进程；没在真实回合中途验证过）：

  ```bash
  perl -e '$p=fork; if(!$p){setpgrp(0,0); exec @ARGV; exit 127} $SIG{ALRM}=sub{kill "TERM",-$p; select(undef,undef,undef,5); kill "KILL",-$p; $to=1}; alarm N; waitpid($p,0); exit($to?124:$?>>8)' codex exec …
  ```

- **成败判定**：退出码 0，且事件末尾有 `turn.completed`，且 `-o` 存在并通过本地 schema 校验，才算有产出；退出码 1 加 `turn.failed` 时 `-o` 不存在（已实测）。有产出不等于任务成功，成败仍看 §2.3 第 7 步。
- **位置断言**：包装脚本启动前检查 `git rev-parse --git-common-dir` 的真实路径不以 `/tmp`、`/private/tmp`、`$TMPDIR` 开头；Codex 结束后核对 worktree 的 HEAD、分支列表与暂存区未变，变了按越界处理。
- **临时目录**：`workspace-write` 默认把 `/tmp` 与 `$TMPDIR` 也列为可写根（已实测：目录在 `/tmp` 下时兄弟目录、仓库外目录、`.git` 都可写）。包装脚本固定加 `exclude_slash_tmp=true`；不得加 `exclude_tmpdir_env_var=true`（已实测：vitest 5 要在 `os.tmpdir()` 下建目录，加了测试全挂；`/usr/bin/git` 每次调用都报 xcrun 缓存错误，同一脚本整轮从 24 秒涨到 68 秒）。根 `turbo.json` 要透传 `TMPDIR`（ADR-0001 §2），否则 turbo 把任务的临时目录落到 `/tmp`，vitest 报 EPERM。
- **schema 写法**：`tools/agent/schemas/*.json` 的每个 object 必须写 `additionalProperties:false`，全部字段进 `required`，由 `tools/guard` 检查。已实测：缺 `additionalProperties:false` 时请求被 400 拒绝（`invalid_json_schema`），退出码 1，没有 `-o`；`required` 这一条没单独试。提示词要求输出纯文本时，输出仍符合 schema。
- **审计来源**：`--json` 事件不是完整的命令记录（实测漏掉一条已执行的 `git branch`），也不含模型名。路径守卫以 `git diff` 为准；命令与模型以会话文件 `~/.codex/sessions/…/rollout-*-<thread_id>.jsonl` 为准（`turn_context.model`、`effort`）。
- **固定开销**：每次请求固定约 1.3 万输入 token（不关 skill 与插件是 1.8 万，加载用户配置是 1.9 万），每次工具往返都重发一遍；估用量时按这个数算。
- **提示词、schema、守卫一律从可信副本读**，不从任务 worktree 读，防止被测分支削弱卡它自己的关口。
- **规则可见性**：Codex 只自动注入从仓库根到工作目录这条链上的 `AGENTS.md`（已实测），所以默认在仓库根运行，任务书内嵌 `paths` 命中的各级 `AGENTS.md` 全文。根目录运行时只注入根 `AGENTS.md`，嵌套的不注入，所以内嵌是必须项。把 `-C` 指到模块目录已实测不可行（§9.3 #3）。
- 评审不加 `--ephemeral`（用量账本和活性判断要用会话文件）。
- 内置 `codex exec review` 输出不是结构化的且会重复，只作补充；合并门用上面的结构化评审。

### 2.5 失败、重试与熔断

- `attempts` 在派发前加一并落盘，按类型分开计：实现最多 3 次；评审按类型分开计——规则测试评审（spec-test）一个计数、最多 2 轮，代码评审（money / general / contract）一个计数、最多 3 轮。重派间隔按 15、30、60 分钟退避。
- **没有产出就结束的调用不算轮次**：硬超时或被看门狗击杀（退出 124）、没有 `-o` 文件、`turn.failed`、模型容量错误，包装脚本结束时把派发前计上的那一轮还回去（代码仓库 `tools/ops/state.ts settle`，按调用去重）；它们仍计入每任务调用上限与「连续 3 次无 `-o`」。拿到回答但校验不过的照计一轮；孤儿（包装脚本没写完运行记录）照计一次。
- 超限后：RV0 / RV1 换另一家实现一次，评审方随之对调。RV2 不换家，直接 `blocked`，根因写 `rebate-private/ops-state/blocked/<id>.md`，其余任务照常推进。
- **失败熔断（按任务）**：同一任务累计 Codex 调用满 10 次（防失控循环；没有产出、还回了轮次的调用也算），或同一任务连续 3 次调用都没产出 `-o` 文件（以进程组确认退出后的状态为准）→ 停止该任务、标 `blocked` 并报告负责人，其余任务照常推进。两项都从该任务运行目录里已结束调用的记录现算，在派发前计数时检查（代码仓库 `tools/ops/state.ts bump-attempt`，打开时退出 3）。不设每天的调用上限，也不按额度熔断（§1.3）。
- **模型容量错误**（`Selected model is at capacity`，退出码 1、无 `-o`，已实测出现过）：按退避重试，不计入 `attempts`，也不计入「连续 3 次无 `-o`」，但仍计入每任务 10 次的上限。
- **夜间漂移任务**（§5.5）：每晚最多建 5 个、每周最多 10 个；同一稳定键被驳回过一次就永久静音。

评审原为一个计数共 2 轮、超时与无 `-o` 也算一次、每任务上限 6 次；2026-10-02 负责人决定改为上面的按类型计数、无产出不算轮次、每任务上限 10 次（对应代码仓库 `ops/approvals.yaml` 第 13 条）；代码评审 2026-10-02 再由 2 轮提高到 3 轮（契约任务第 2 轮常还有新 S1，`ops/approvals.yaml` 第 17 条）。原有每天 40 次的全局上限和「连续 3 次无产出即停全部派工」，2026-10-02 随取消额度限制改为上面的按任务熔断（§1.3，`ops/approvals.yaml` 第 15 条）。

## 3. 评审与合并

### 3.1 发现分级

每条发现必须给出具体失败场景，并用稳定键（文件、函数、规则编号）去重。

| 级别 | 含义 |
| --- | --- |
| S0 | 算错钱、归属错、重复打款、越权、泄密 |
| S1 | 违反 BR 或契约、并发下进入非法状态、缺幂等 |
| S2 | 其他正确性问题 |
| S3 | 风格，不报 |

05 旧文里的「P0 / P1」评审级别作废，改用 S0–S3，避免与产品阶段 P1 / P2 重名。

### 3.2 合并条件

| 风险级 | 条件 |
| --- | --- |
| RV0 / RV1 | 必过检查全绿 + 评审无 S0 / S1 → Claude 直接合并 |
| RV2 | 另加：沙箱外验证是容器模式（§2.3 第 7 步）；规则测试已过审；两家评审均无未关闭的 S0 / S1；评审清单齐全（§3.3）；长跑属性测试在当前资金目录树哈希上通过；`evidence-check` 通过。合并后给负责人发中文摘要 |
| 命中保护路径（§4.4 第二、三类） | 不分收紧放宽，一律进 `ask`：负责人在对话里看中文前后对比后确认；`merge.sh` 没有 `couli-runs/approvals/<PR 号>` 记录就拒绝 |

- **证据文件**：每个 PR 带 `ops/evidence/<id>.json`，只记结论、哈希和测试 ID：`spec_commit`、红测试名、`runs[]`（每一次 verify 的提交、种子、退出码、`mode`：`container` 或 `host`）、两家评审结论、受保护代码目录的树哈希（`git rev-parse HEAD:<模块路径>`）。评审意见全文与 blocked 根因放私有库。
- **`evidence-check`**（CI，从 `origin/main` 检出 `tools/guard` 再检查 PR 的 diff）：证据齐全、`spec_commit` 是祖先、规则测试未被改动、树哈希一致。它防的是遗漏，不是恶意。
- **长跑结果绑定树哈希，不绑定提交号**：变基后资金目录树哈希不变即沿用；结果由 `merge.sh` 写成头提交的状态 `longrun-props`（`gh api repos/<owner>/<repo>/statuses/<sha>`）。纯函数包的长跑（每条属性 100 万次）实测在 20 秒内，评审通过后同步跑完再写状态。`longrun-props` 设为必过项，`merge.sh` 对每个 PR 的头提交都写这条状态：资金目录树哈希与 `origin/main` 相同时写 `success`，描述 `n/a tree=<哈希>`；否则写长跑结果。不写的话它会一直停在等待上报、合不了（文档结论，未实测）。
- **规则集与合并**（文档结论，未实测；建库当天实测 `current_user_can_bypass=never`、`gh pr merge --admin` 被拒、直推 main 被拒）：
  - 用 ruleset，导出的 JSON 存 `ops/branch-protection.json`；`bypass_actors` 留空即对管理员生效；`required_approving_review_count=0`（作者不能批准自己的 PR）。
  - Actions 来源的必过检查钉 `integration_id=15368`；本机写的 `longrun-props` 钉不了来源。
  - 不用 `gh pr merge --auto`（它只等必过项，合并时机不受 `merge.sh` 控制），仓库保持 `allow_auto_merge=false`。`merge.sh` 先 `gh pr checks --required --watch --fail-fast`，再 `gh pr merge --squash --match-head-commit <sha>`。
  - merge queue 与规则集里的「必过工作流」个人账号用不了。
  - CI 里按路径才跑的检查一律写成「工作流不设 `paths` + job 级 `if` + `if: always()` 的汇总 job」，只把汇总 job（如 `money-gate`）设为必过：被工作流级 `paths` 跳过的检查会一直停在 Pending。
- **不许重跑到绿**：资金与归属路径下，必过检查的 `run_attempt` 大于 1 即 `evidence-check` 失败。红过一次，必须有代码改动，或登记带复现种子的 `flake` 任务。
- **批准记录**：合并 RV2、改分支保护、应用依赖策略前，guard 读 `ops/approvals.yaml`，对应条目不是 `granted` 就拒绝（§7.3）。

### 3.3 分歧裁决与评审质量

- **裁决只认可执行证据**（全部风险级）：
  - 评审方把场景写成失败测试（资金与归属用真实 PG）→ 必须修，测试留作回归。
  - 两家各试一次都复现不了，且有一条测试断言该场景被约束挡住（唯一键冲突、CAS 影响 0 行等）→ 降为 S2，记入证据后继续。
  - 文字说明「不可能发生」不算；两者都拿不出，RV2 标 `blocked`，RV0 / RV1 驳回并记录。
- **评审范围只到任务的 refs**（2026-10-02 负责人决定）：规则测试评审只对照任务 `refs` 列出的 BR 条款，一跳引用的规则只作理解用；关于 refs 以外规则的问题写进评审产出的 `out_of_scope` 列表（`review.schema.json` 字段，严格 schema），不计入结论。资金评审同样以 refs 为范围，仓库硬规则与七项清单始终在范围内。规则测试评审另以任务 `paths` 加规则测试目录为界（2026-10-02 负责人决定，代码仓库 `ops/approvals.yaml` 第 14 条）：只有在这些路径内可测的行为才计入结论；refs 里某条 BR 落在 `paths` 以外的部分（库表、契约、别的模块、前端、CI 规则等）写进 `out_of_scope`。引用 `paths` 以外文件或模块、或评审方标了 `[out-of-scope]` 的发现由校验脚本移进 `out_of_scope` 并记警告，结论只按范围内的 S0 / S1 重算；范围外条目追加到运行目录的 `out-of-scope.md`，留作后续任务的规则测试。资金评审不变。
- **第二轮只看增量**：上一轮未关闭的发现 + 修复产生的增量 diff；全量新发现记入后续任务，不阻断本 PR，S0 除外。
- **资金评审清单必填**：`review.schema.json` 的 `checklist[]` 含舍入、正负号、幂等、并发、部分退款、时钟、`app_id` 七项，每项带 `file:line`；守卫核对引用行确实在 diff 里。空结论不等于通过。
- **埋雷抽查**（RV2 每次评审）：在临时 worktree 给同一 diff 打入固定变异清单中的一项，交给同一评审方的另一个新会话；没报出 S0 / S1，本轮真实评审作废重做。命中率记 `ops/metrics/review-canary.csv`，近 10 次低于 80% 时暂停 RV2 队列并上报。
- **上报时改写成业务问题**：不把锁和事务细节交给负责人。

### 3.4 规模与并行

- 单个 PR ≤400 行（不含生成物与 fixture）；一任务一分支 `task/<id>`，一任务一 worktree。
- 在途任务从 2 个起步，稳定后不超过 4 个；`paths` 相交不派发。
- 契约、迁移、`deps` 任务各自串行（全局同时只 1 个）；资金任务每模块 1 个、全局 ≤2 个。
- `deps` 任务先合并进 main，实现任务再以它为基线。
- RV2 在合并槽排队期间，暂停合并会碰同一包的其他 PR。
- 验收记录一条一个文件（或 `.gitattributes` 设 `merge=union`），避免并行 PR 互相冲突。

### 4.2 资金与归属专项

- **不变量以 08 为准**：BR-FUND-19 的 ①–⑧ 与 BR-CALC-21 的分账属性，不写「七条」。守卫检查每条都有对应测试且实际运行过。10 §5.3 的列举已随同步任务改为引用。
- **属性测试次数**（纯函数包，如 `packages/money`；2026-10-01 在 M2 Max 用试验包实测：4 条属性各 10 万次 2.3 秒、各 100 万次 18.5 秒，4 个文件各 1000 万次并行 19.5 秒）：

### 4.3 测试是否有牙齿

- **固定变异清单**（从 10-04 试跑起就是硬门槛）：floor 改 round、正负号翻转、去掉幂等判断、去掉账户行锁、扣回上限差一。清单由评审方维护；规则测试必须全部杀死（§2.3 第 4 步）。Stryker 不会为 bigint 除法生成 floor 改 round 这类变异（已实测），所以这份清单不能省。
- **变异测试**（Stryker 10.0.0 + Vitest 5.0.x，2026-10-01 已实测）：能装能跑、退出码 0，但套了 `describe` 的测试在变异阶段全部被跳过，得分静默变成 0%（上游 issue #6210，修复未发布）。现阶段：
  - 资金包规则测试一律写顶层 `it`，不套 `describe`（实测得分与 Vitest 4.1.11 一致）。同一文件混用两种写法没测过，按不允许处理。
  - 变异得分只报告，不作合并门。变异任务用 `PROP_RUNS=1000`、固定种子，不得 ≥10 万次（实测会出现超时变异体）。
  - 报告任务带自检：`mutation.json` 中任一有覆盖的变异体 `testsCompleted == 0`，或日志出现 `Ran 0.00 tests per mutant`，任务直接失败。
  - 转硬门槛的条件：上游修复发布并升级；连续 10 次得分与逐变异体结论一致；自检通过。届时资金包改动文件得分 ≥80%（`thresholds.break=80`；实测低于阈值返回退出码 1，不设阈值时 0% 也是退出码 0）。
  - 时间预算：PR 只变异改动文件 ≤3 分钟，每晚资金包全量 ≤20 分钟。这是按 37 个变异体 5 秒（带类型检查 24 秒）外推的，没在真实包上测过。
- **规则测试里禁止 mock `packages/money` 和 ledger。**

### 4.5 验收记录与真实录制

- **验收记录只由脚本生成**：`tools/ops/records-from-junit.ts` 用 `gh run download` 取 JUnit，核对该运行的 `head_sha` 是 main 上的合并提交、结论为 success、`run_attempt=1`、该用例至少 1 条通过且 0 条跳过，并写入报告文件的 sha256。CI 的 `records-check` 重跑脚本，手改的行对不上即失败。@auto 用例的验收人填 `ci:<运行号>`（§7.3 第 7 项）；@manual 与 waived 仍由负责人。
- **GitHub 侧只留 90 天**（文档结论）：运行记录、JUnit 产物、检查与提交状态最多留 90 天（2026-10-01 起检查与状态也按这个期限删）。`records-from-junit.ts` 生成记录的同时，把 JUnit 原件与运行元数据（`run_id`、`head_sha`、`run_attempt`、`conclusion`）存入 `rebate-private/ci-evidence/<run_id>/`；`records-check` 对超过 80 天的记录改为对照归档件的 sha256，不再调 `gh run download`。
- 资金、归属套件跳过数大于 0 即失败；已执行的测试 ID 集合与入库的 `test-manifest.json` 比对，少一条即失败。
- 10 里 Then 含多个圈号的用例，测试标题写成 `[AC-S2-26#1]`、`#2`、`#3`；脚本从 10 解析圈号个数，要求齐全。
- **录制来源**：每个录制目录带 `provenance.json`：`source`（probe / doc-derived / synthetic）、CAP 编号、探测运行号、抓取时间、脱敏前原文 sha256、脱敏器版本。
  - `source=probe` 只能由负责人在终端运行的 `tools/probe/run.sh` 写出，同时向 `rebate-private/probe-runs.log` 追加一行；守卫核对每份 probe 录制都有对应记录。
  - 回放框架记录本次加载了哪些录制；遇到非 probe 来源，验收记录一律不写 pass。
  - 守卫检查 `modules/union/<平台>/mapper*` 引用的每个平台字段都出现在某份 probe 录制里（09 README §0.2 硬规则 3）。
- **没有真实录制时**：用领域层的 `DemoUnionAdapter` 造数据，不伪造联盟报文格式，显式标注，不计入 AC-LINK / AC-ORD 验收；任务只能记「代码已提交」，不能记「已验收」（00 §10）。

### 5.2 开场必读

每个编排会话开场、以及上下文压缩后，按顺序读，控制在约 1.5 万 token 内：

1. 根 `AGENTS.md`。
2. `pnpm ops:status` 的输出（在途任务、未合并 PR、CI、失败熔断、超时未答的问题）。
3. `rebate-private/ops-state/NOTES.md` 与最近一份交接。
4. 当前任务的任务书。

### 5.3 规格版本与任务书

- **`SPEC_REF` 必须在规划仓库的 main 上**：guard 检查 `git merge-base --is-ancestor $SPEC_REF origin/main`。`ops:brief` 与索引生成器只用 `git show $SPEC_REF:<路径>` 读，不读工作区。契约 tag 里带上它对应的 `SPEC_REF`。
- **条目哈希** = 规范化后的（BR 表格行的正文列 + 该编号的「细则」小节）。状态列单独存为字段：只有正文哈希变才把相关任务标 `stale`；状态从默认假设变已确认只更新索引。解析表格要处理单元格里的转义竖线，生成器对已知会切错的行有测试。
- **任务书内容**：每个 `refs` 编号输出表格行（去掉「受影响的表 / 接口」一列）+ 细则 + 一跳引用到的 BR 表格行；`paths` 命中的各级 `AGENTS.md` 全文；允许路径、保护路径、验收命令、固定句。上限 24KB，超限说明任务该拆。
- **契约任务的任务书**（`type: contract`，2026-10-02 负责人决定，代码仓库 `ops/approvals.yaml` 第 17 条）：不带 BR 原文与一跳引用，`refs` 只列编号与标题；改为逐字带台账 `contract_sections` 点名的 04 各节。实测 04 §2 加 §7 就约 25KB，这样的任务照样超限，要么拆小，要么另定预算。
- **`SPEC_REF` 的推进**：每晚在新旧两个提交上各生成一次索引，按条目哈希比对（不按文件名）。没有受影响编号就自动推进；有则把相关任务标 `stale` 并先开同步任务。凡要列文件名的地方一律 `git -c core.quotepath=false diff -z`（中文路径否则被转义，匹配不到）。

### 5.6 教训回流（试行）

2026-10-05 补。项目已有把教训改进规则和工具的例子（骨架占位断言进 §4.4、路径守卫按 `spec_commit` 分段、契约任务书带 04 节选、评审轮次按类型分开），会话任务书也会点名教训文件；缺的是跨会话认出同一个坑。10-02 到 10-04 的教训里有四处重复出现，出处见 `docs/research/20261005-文章方法对照.md` §4。

## 8. 风险与保护

| 风险 | 保护 |
| --- | --- |
| 公开仓库泄密 | 推送只经 `tools/ops/push.sh`：先 `gitleaks detect --log-opts origin/main..HEAD`，再做私有指纹比对（对 `rebate-private` 文件按行取哈希，暂存内容命中即拒绝）；只暂存 `paths` 内文件；只提交 `.env.example`；建库当天打开 secret scanning 的 push protection；提交钩子 `.githooks/pre-commit` 真正建出来（规划仓库的已于 2026-10-01 恢复）。GitHub 的通用模式与自定义模式在个人公开仓库不可用，联盟平台密钥不在它的支持清单里（文档结论），所以 gitleaks 加自定义规则仍是主防线；推送保护可以被有写权限的人填理由绕过，绕过入口由 PreToolUse 钩子拦（具体地址与接口名待查证） |

**#6 的配方要点**（已端到端跑通；脚本入库后以 `tools/ops/verify-container.sh` 为准）：

- 不能直接挂宿主的 `node_modules`：里面是 darwin 的原生绑定，vitest 启动报错，turbo 垫片会联网重装而挂死。
- 依赖走离线 store：锁文件哈希变了才联网 `pnpm fetch` 一次（只挂锁文件和 `pnpm-workspace.yaml`），verify 里 `pnpm install --offline --frozen-lockfile`；store 只读挂载时要给 `/store/v10/projects` 盖一层 tmpfs。
- 镜像内 pnpm 版本须与 `packageManager` 完全一致，并设 `manage-package-manager-versions=false`，否则断网时挂死；镜像不依赖 corepack。
- `--internal` 网实测只通同网容器，外网与 `host.docker.internal` 都不通。
- PG 必须只接 internal 网：同时接普通网且测试用超级用户时，可经 `COPY FROM PROGRAM` 出网（已实测）。所以不与开发栈共用。
- 容器内 Testcontainers 不可用（没挂也不该挂 Docker 套接字），测试库入口读环境变量。
- 容器以非 root 运行，根文件系统只读，`/work` 与 `/tmp` 用带 `exec` 的 tmpfs；macOS 挂载无权限问题。
- 实验里的 PG 用的是 `postgres:18-alpine`（启动到可查询 1.4 秒）；换成 ADR-0001 的 pgvector 镜像后的耗时未测。slim 镜像没有 git，配方也不复制 `.git`。
