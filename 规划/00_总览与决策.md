## 2. 一页纸

**产品**：带 AI 找货助手的返利 App。用户粘贴链接/口令、搜索关键词或直接问 AI，拿到带返利的商品卡，一点跳到淘宝/京东/拼多多下单；订单自动跟单，付款即记预估收益，跟随联盟月结、账单日出账并经后台确认后批量入账（BR-FUND-04；用户侧显示预计结算月份，BR-TEXT-04），可提现到支付宝或本人银行卡（BR-WDR-02、BR-WDR-32）。

**产品方向**：面向没用过返利产品和已有返利经验的用户，改善找商品、查优惠、购买、跟单与提现的体验。自主开发使产品可按用户反馈持续演进；Agent 是核心创新方向，贯穿找货、解释优惠与订单服务，其竞争优势通过真实使用效果持续验证（D25）。

**MVP 边界**：推荐、转链、跳转、跟单、入账、提现。**不代下单、不代支付、不自动领券**；所有外跳都由用户点击触发。

**名称**：凑狸（06 Q-A1，2026-09-30）；AI 助手叫「凑狸 AI 助手」（拍板第二批 AI-22）。

**已确认形态（D28）**：保留 iOS / Android / 鸿蒙三端原生壳，由原生接入系统能力与客户端 SDK，并提供 WebView + JSBridge 承载三端共用的 H5；三端同步交付（D4）。

**当前实现方案（D27）**：核心交易与 Agent 页采用原生 UI，高频变化页采用 H5；一个 NestJS 后端（模块化单体）；Refine 管理后台。前端语言、页面框架、WebView 与后台的对应关系见 [03 前端架构 §1.2](03_前端架构.md#12-前端技术总览)；逐页实现方式统一记录在 01 §4.2。

**节奏**（2026-10-01 按拍板第二批重排：维持 W5 白名单内测、W8 公开上架，D3；鸿蒙与 iOS / Android 同步，D4；逐周安排以 05 §1 为准）：

```
W0 接口草案与外部申请 → W1–W2 交易链路（录制回放）→ W3 资金线 + Agent（go/no-go）
→ W4 后台（月结账单、调账、工单）+ 首页配置 + 三端钱包/Agent 页 → W5 iOS/Android/鸿蒙三端白名单内测（≤500 人，自动到账总开关默认关）
→ W6 双11 值守、注销/分享/华为账号登录 → W7 各商店提审 → W8 公开上架（AI 登记号填好即对所有人开放 Agent）
各平台首个月结批次在该平台 08b 月结对账验证通过后执行（BR-FUND-04）
```

- **资金与状态流转变更**（入账、扣回、补差、提现、订单状态机、账户与流水）：影响评估须附验证证据（属性测试、录制回放、对账结果）与迁移、兼容、恢复说明（存量数据如何迁移；新旧客户端与接口版本如何共存；出错时如何回滚或用开关止损）。
- **只细化近期要开发的内容**：当前阶段与下一阶段写到开发不用猜；更远的内容只保留目标、依赖、未知项（如 §4.1）。
- 不相关的未决事项不阻塞其他工作；会影响实现的关键问题在开工前解决（08 §14.4 列出最需要先拍板的项）。
- 重要架构决定写 `docs/adr/`（背景、选择、影响）；改变时新增一篇取代旧篇，保留历史。

## 9. AI 决策边界

编码代理（Codex、Claude Code）在开发中能自己决定什么。产品内 Agent 能对用户做什么另见 BR-AI-01。

| 代理可自定 | 必须负责人决定 | 禁止 |
| --- | --- | --- |
| 代码结构、命名、模块内实现、测试写法；不改变外部行为的重构 | **金额口径**：返利比例、分佣基数、舍入、入账时点、手续费与税（BR-CALC、BR-FUND、BR-WDR） | 自行推翻已确认决定，或把未验证的平台能力当成事实 |
| 08 标「代理可自定」的事项（如错误码按 08 §13.11 的分配规则在号段内取号、配置项命名、接口路径统一，08 §14.3 C-14、C-19、C-20、C-29） | **订单归属**：归因参数、点击证据、找回判定、改派（BR-ATTR） | 执行资金操作：真实打款、冲正、补差入账、余额调整 |
| 契约已定义范围内的 UI 布局与交互细节（文案取自 BR-TEXT 字典） | **用户授权**：隐私与 AI 同意、身份等级、剪贴板、推送与通知权限（BR-ID） | 读写生产数据库、使用生产用户数据测试；在日志、fixture 中写明文个人信息 |
| fixture、mock、录制回放、调试脚本与探测 App | **本期范围**：§4 阶段、砍项、预埋、§3 决策 | 把 09 未通过的能力写成对用户的承诺或默认打开平台开关 |
| 不改变规则外显行为的性能与缓存优化；依赖补丁版本升级 | **对外承诺**：用户可见的时限与金额承诺、营销文案、商店审核说明、客服口径 | 放宽 CI 必过检查、CODEOWNERS、AGENTS.md / CLAUDE.md 与 guard 脚本 |
| 待决策条目按 08 默认值实现，并做成配置或开关（08 §0.3） | **资金操作与生产数据**：打款批次、补差审批、迁移、修复、导出、删除；新增供应商、模型或第三方 SDK（BR-AI-14） | 在代码中写死平台开关或绕过 `convert.enabled.<platform>` |

- **规格缺失或矛盾时**：明确的同步错误直接修正；可逆实现由代理选用合理方案并说明。涉及业务取舍时集中列出问题与建议，只暂停依赖该决定的部分；复杂问题才另建记录。尚未提供的开发资料不由代理臆造。
- 仓库规则写在 AGENTS.md（工具中立）；任一代理账号停用时，另一代理按同一规则继续。
- 开发流程里的分工、合并规则、测试标准与「何时停下问负责人」见 `规划/11`（§7.1 七类、§7.3 批准栏）；本节表格是其依据，规划/11 不放宽本节，放宽须负责人在对话里确认并写入批准栏。批准栏第 0–9 项已确认（负责人 2026-10-01 确认；第 10 项为 2026-10-02 新增，待确认，未生效）；改到本节的有：建仓库与首次推送由 Claude 执行（规划/11 §7.3 第 1 项）；新依赖按自动策略，付费或新供应商仍由负责人决定（第 3 项）；单账号下 CODEOWNERS 不起作用，AGENTS.md / CLAUDE.md、guard、CI 门禁的改动改为命中保护路径一律先问负责人（第 4 项）。

## 10. 任务与验收状态

每个开发任务关联：需求编号（F- / AC- / BR-）、依赖、负责人、验收条件、验证证据（05 任务表）。状态分三种，分别记录，互不代替：

| 状态 | 定义 | 记录位置 |
| --- | --- | --- |
| 代码已提交 | PR 已合并（必过检查全绿） | `evidence/acceptance/records.csv` 的「提交 PR」列 |
| 已验收 | 验收人、验收日期、结果（pass 或负责人签字的 waived）、证据路径齐全 | 同表对应列；证据放 `evidence/acceptance/<阶段>/<用例>/<平台>/<端>/` |
| 已上线 | 上线版本、上线日期齐全，且该平台开关已对真实用户打开 | 同表对应列 |

- 记录粒度：一条用例 × 一个平台 × 一个端一行；模板、取值与阶段证据清单见 10 §5.1、§5.2。
- 阶段出门按平台判定（10 §0.6、§1）；05 周计划只记代码进度，不能代替验收记录。
