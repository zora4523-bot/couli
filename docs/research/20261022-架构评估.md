- 公开版说明：按 规划/11 §5「评审全文、blocked 根因放私有库」，具体的未修复缺口、代码位置、权限与风控判断、逐条代码证据和评审全文只在私有库 `rebate-private` 的评估全文里；本文只写质量场景、结论、风险主题、方向与门槛。编号（QS、R、N、S、T、RA）两边一致。

## 1. 业务驱动与架构方法

**业务驱动**（00 §2、§5，01 §7–§8）

| 驱动 | 内容 |
| --- | --- |
| 时间 | W5 白名单内测（M3，11-08，≤500 人，跑在 prod，每平台 ≥20 笔真实订单；三端内测包同时发放），W8 公开上架 |
| 资金 | 日终余额 = 分录之和、差异 0；重复打款 0；退款扣回正确率 100% |
| 归因 | 跟单成功率每平台 ≥95%（BR-ATTR-23）；转链归因正确 100% |
| 体验 | 点击购买到唤起平台 App P95 ≤1.5 秒；Agent 链接到首卡 P95 ≤2.5 秒；付款到入库 P95 ≤5 分钟 |
| 可用性 | API 月可用性 ≥99.9%；RPO ≤5 分钟、RTO ≤1 小时（01 §7.2） |
| 合规 | 三端隐私检测与同意前抓包 0 违规；Agent 注入、越权、禁售拦截 100%（01 §8.1） |
| 约束 | 开发由 AI 代理完成、负责人一人决策；成本敏感（2026-10-07 精简为 3 台 ECS）；淘宝链接 API 是邀请制；代码与规划仓库公开 |

**已有的架构方法**（02 §1、§2、§4）

| 编号 | 方法 |
| --- | --- |
| A1 | NestJS 模块化单体，同一镜像按 api、stream、admin、worker、payout 五个入口部署 |
| A2 | PostgreSQL 是唯一事实源，任务队列（pg-boss）也在库里；Redis 做缓存、限流、防重放 |
| A3 | 资金单写者：settlement 产出记账指令，ledger 唯一改余额，payout 只对外转账；复式记账、分录只插入、唯一业务键 |
| A4 | 外部依赖一律经 Adapter 与治理层（超时、重试预算、熔断、配额、录制回放） |
| A5 | 契约先行：`contracts/` 生成 Swift、Kotlin、ArkTS、TS 四端代码 |
| A6 | 三端原生壳 + 共用 H5；可信 / 第三方两类 WebView；JSBridge 三级权限 |
| A7 | 服务端 Agent：确定性路径交代码，模型只做意图与条件抽取；卡片数字由代码填 |
| A8 | 配置即数据：首页、开关、文案、规则带版本，可灰度、可回滚 |
| A9 | 领域事件与业务写入同事务入队，消费端去重；资金不依赖事件 |
| A10 | 部署：应用机 1 台（api、stream、worker、admin 同机）、payout 机 1 台、数据库机 1 台（PG + Redis + 监控同机） |

## 2. 效用树（质量场景）

## 3. 对照结果

「结果」分四种：**满足**（设计成立，主干已有对应实现）；**设计满足 · 未实现**；**待验证 / 部分**（依赖未验证的前提、只实现一部分，或本次没有核对到能下结论的程度）；**有风险**（与场景要求有冲突，见 §4）。逐条的代码证据在私有评估全文。

| 结果 | 场景 |
| --- | --- |
| 满足（3） | QS-07、QS-19、QS-20 |
| 设计满足 · 未实现（2） | QS-02、QS-03 |
| 待验证 / 部分（12） | QS-04、QS-08、QS-09、QS-13、QS-14、QS-16、QS-22、QS-25、QS-26、QS-27、QS-28、QS-29 |
| 有风险（12） | QS-01、QS-05、QS-06、QS-10、QS-11、QS-12、QS-15、QS-17、QS-18、QS-21、QS-23、QS-24 |

有风险的场景里，多数是实现还没跟上设计（可观测、服务隔离、配额计量、资金链路、备份与演练），另一些来自设计取舍、规划与 ADR 之间的不一致或未验证的平台能力。

## 4. 风险主题

「谁定」按 00 §8、§9 与 CLAUDE.md：同步修正与实现方案由代理直接做；原需负责人选择的待确认取值经 TypeSafe Jev 判断后回写、事后报告；改变已确认决定、资金与归属与授权边界、ADR 取舍、花钱、对外动作与需专业确认的仍由负责人定。

| 编号 | 主题 | 场景 | 严重度 | 方向 | 谁定 |
| --- | --- | --- | --- | --- | --- |
| R-01 | 告警与可观测性的建设落后于规划 | QS-24、QS-13 | 高 | 按 02 §13 的现行告警表与资金类规则补齐最小一套，不提高口径；ADR-0002 §6 的告警外发与心跳在 prod 承接第一笔真实订单前落地；资金类告警放在数据库节点以外 | 代理；外购监控服务由负责人 |
| R-02 | 可用性目标（01 §7.2）与单节点部署（ADR-0002 §3）口径矛盾；备份与恢复演练尚未落地 | QS-10、QS-11、QS-05 | 高 | 让需求与决定一致（改分阶段口径或撤回单节点），写死扩容触发条件；按 ADR-0002 §3 时点表完成备份、恢复演练与整机重建 runbook；02 §3.1 标题「双可用区」改正 | 口径与扩容：负责人；其余：代理准备、prod 命令由负责人执行 |
| R-03 | 资金链路的防线要在真实订单与资金开关之前补齐 | QS-01～QS-03 | 高 | 真实订单接入前完成资金链路完整性与持续校验的验收；资金最小闭环与属性测试优先，次要功能后放；资金开关按时点表逐项打开 | 代理；砍项涉及对外承诺的由负责人 |
| R-04 | 防重放与依赖失效时的可用性策略需要统一 | QS-12 | 中高 | 准备影响评估，按 00 §8、§9 分类后裁定，不用实现反推规划；裁定前把 Redis 按关键依赖准备（告警、持久化、重启与重建 runbook）；任何方案都要同时保证防重放连续，不做「故障时换存储」 | 影响评估：代理；裁定：按 00 §8（涉及已写明的可用性行为） |
| R-05 | 淘宝归因与跨端外跳建立在未验证的平台能力上（CAP-TB-11，另有 CAP-X-03、CAP-X-04） | QS-06 | 高 | CAP-TB-11 真机验证排在淘宝适配器开发之前，写好失败预案；建「平台 × 端 × 购买或分享入口」能力与降级矩阵，各入口放量前验完 | 验证：代理与负责人配合；范围调整：负责人 |
| R-06 | 联盟配额与熔断需要全局共享计量；配额口径未定 | QS-17 | 中高 | 配额与熔断状态按 02 §6.2 共享，共享存储不可用时退回保守的静态分摊；上线前拿到三家配额口径写进 09；压测加「配额耗尽」 | 实现：代理；配额申请与账号安排：负责人 |
| R-07 | 同机负载下的服务隔离与容量需要验收；发布方式与 02 §3.3 不一致 | QS-11、QS-15、QS-16 | 中高 | 明确各服务的资源配额、依赖健康检查与重任务并发，并在压测中验证隔离；写明拆分或加机器的触发指标；prod 发布链路内测前建好，pg-boss 升级保留 ADR-0001 §4.2 第 14 项的「先迁移、再重启全部进程」；QA-06 加同机组合场景 | 代理；加机器由负责人 |
| R-08 | 打款进程失陷时，兜底主要在应用之外；队列权限的隔离取舍值得重评 | QS-18 | 中高 | 通道侧设单日上限（能力待 BR-WDR-22）；企业支付宝余额按提现需要存放；余额变化比对只作辅助告警（自动查余额待验证），发现盗转仍靠按交易明细的对账；重评 ADR-0001 §4.2 第 14 项的队列授权，先在 staging 验证再按 ADR 流程修改 | 通道与余额：负责人；告警：代理；改 ADR：按 00 §8 |
| R-09 | 订单侧的平台差异散在领域代码里 | QS-21 | 中 | 收拢成每平台一份的规则表，领域代码只查表；lint 规则只作用于订单领域目录 | 代理 |
| R-10 | 三端交付进度落差 | QS-23 | 中高 | 三端按已确认范围与已验证降级做功能等价验收，作为 M3 发包前的门槛；按进度差补人力 | 编排；改变 D4 由负责人 |
| R-11 | 规划与代码、台账之间的漂移 | 全部 | 中 | 逐项分类处理：同步修正直接改；涉及发布方式、Redis 降级的随 R-07、R-04 定；能机器检查的放 CI（§9） | 按项 |
| R-12 | 08 内部的转链缓存键口径不一致（BR-AI-04 细则 vs BR-PROD-07、BR-ATTR-05 细则） | QS-06、QS-07 的前提 | 中 | 三处统一为一句并互相引用：键带推广位与归因参数版本；无返利结果是否缓存按 08 原意裁定 | 编排判断类别：只统一写法的属同步修正，要在两种行为间取舍的报负责人 |

R-11 已知的漂移：02 §3.1 标题「双可用区」；02 §3.3 写蓝绿，实际发布方式不同；02 §4.1 模块表里 identity 与 notification 互列依赖（代码里两边都没有互相引用）；02 §11 的事件清单（评估基线时 24 个，2026-10-22 主干已增至 25 个）多于代码已注册的数量（测试允许待注册项缺席）；02 §7.1 写按平台的死信队列，代码是共享的；02 §14 的 Redis 一行（见 R-04）；工程台账有多个已合并任务仍标 todo。方向是维护规划、实现与验收证据三者一致。

## 5. 非风险（设计已经站得住的地方）

| 编号 | 决定 | 场景 | 为什么站得住 |
| --- | --- | --- | --- |
| N-01 | 资金单写者 + 复式只插入 + 唯一业务键 | QS-01、QS-03 | 重放与崩溃重跑都落在唯一索引上，错误只能变成「写不进」而不是「写两次」；更正只能红冲 |

## 7. 与 REA 反编译分析的对照（公开版）

**材料**：负责人用 REA 做的静态分析笔记中尚未被规划吸收的部分：超级转链对比、省团团素材栏、淘宝联盟 9.15.6 分析集、优券汇 1.0.9 分析集，另有一份我方自拟的「自动查券 → 分享」任务书（我方新设计，不当作竞品证据）。笔记只做静态分析，没有运行对方 App、没有请求对方服务器。剪贴板三篇、「问一问」、优券汇第三、四轮复核已在此前吸收（规划落点已登记，不代表对应代码与真机验收已完成）。

**边界**：只写「这种做法」与我方结论，不写对方的类名、接口、字段与弱点；逐条证据与样本信息只在私有库。对方做法不等于平台规则，涉及平台能力的仍以 09 实测为准。

| 编号 | 做法（公开版） | 我方现状 | 结论 | 落点 |
| --- | --- | --- | --- | --- |
| RA-01 | 服务端代用户访问外部链接（如展开短链）时，限定协议与网段、每一跳重新校验、限制跳数与超时，拒绝内网地址 | 规划没写；主干暂无跟随跳转的代码 | 采纳（预防性） | 在服务端加短链展开之前写进 02 §12 与 BR-PROD-03 |
| RA-02 | 列表与搜索只接受当前查询的最新响应；缓存、网络、错误按单次请求交付；空结果替换旧内容 | 迟到丢弃已写在剪贴板、购买、Agent 流与提现估算（BR-WDR-04 细则）；列表与搜索没有统一约束 | 采纳 | 03 §3.2 页面内模式 |
| RA-03 | 桥的每次调用恰好结算一次：参数错误、发起权限申请后、不同宿主页面都一样 | 03 §5.3 有错误码、去重与页面会话作废，没有「恰好一个终态」 | 采纳 | 03 §5.3；§5.5 一致性用例加「响应计数」「授权后与拒绝后」「不同宿主」三类 |
| RA-04 | 转链缓存键带推广位与归因参数版本，授权一变即失效 | 08 内三处写法不一致（R-12） | 采纳 | 统一 BR-AI-04、BR-PROD-07、BR-ATTR-05 |
| RA-05 | 多图保存与分享逐张记状态，全部完成再提示；单图与批次限制大小、类型、解码、超时，可取消并清理临时文件；分享用临时缓存，点保存才写相册 | 桥结果只有一个「是否已保存」，表达不了部分成功，与 F-SHARE-12「保存张数与提示一致」的验收冲突 | 采纳 | 先开契约任务（`bridge.schema.json` 的结果形状、兼容处理、生成物、三端与桥 SDK）；再改 04 §9 与分享页 |

| RA-11 | 批量转链逐项返回、部分失败保留其余 | 已定全成全败（F-SHARE-06） | 不采纳；只吸收「逐条给出失败原因」 | F-SHARE-06 |
| RA-12 | 某些商品点卡片直接进入购买、不经详情页 | 所有购买都经受控的 open 与 TradeJump；Agent 卡片本来就直接进购买流程 | 交互选择，不作结论（跳过详情页不等于绕过 open 复核） | — |
| RA-13 | 多套渲染容器并存、运行期热修补 | 一套原生 UI + 一类可信 H5 容器，不做脚本热更新 | 不采纳 | — |
| RA-14 | 短动作也走「建任务 + 客户端轮询」 | 购买同步 + 同键重试，慢任务（海报）才返回进行中 | 不采纳（购买要低延迟） | — |

**对照后确认已有的**：桥只开固定方法并校验来源、证书错误不降级、不下发脚本（03 §5、§4.8）；外跳目标只来自服务端计划、取消后迟到的响应不外跳（03 §4.5）；登录或授权后只恢复用户发起的那次操作，SDK 回调只是过程信号（BR-ID-10、BR-PAY-04）；购买与分享分契约、商品上下文用不透明引用（BR-PROD-11）；只下发客户端声明支持的组件、未知组件跳过（03 §6）；商品请求不带位置（03 §3.5）；所有错误通道收敛到页面终态（03 §4.2）。

**一条提醒**：`share.open` 返回「已分享」的判定里包含「已调用系统分享」。直达微信的渠道应以微信 SDK 的返回值判定，不能以「调用没抛异常」判定。
