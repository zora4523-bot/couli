## 1. 后台新账号首次绑定身份验证器

**内容**（负责人 2026-10-05 确认，按建议执行）：

1. 新建的后台账号首次登录时，账号密码通过后由本人绑定身份验证器（动态码）；绑定成功才算登录完成。
2. 绑定时输入的动态码错误：不绑定、不登录；错误次数计入现有的后台登录失败锁定（BR-ID-34 正文，取值不在此复述）。
3. 账号没有任何权限点时，登录后落到「暂无权限」页：只能看登录即可见的内容，提示联系超管。

**代理补全的默认，待负责人确认**（06 新节第 5 项）：绑定前的中间状态只能用来完成绑定，离开或超时后下次登录重新生成密钥；重置流程定下前，后台不提供自助改绑。

**仍未定**（06 新节第 1～3 项）：初始密码怎样发放；首次是否强制改密；验证器丢失后怎样重置。

**涉及 BR / F**：BR-ID-34（正文加一句、细则新增「首次绑定身份验证器」）；只作引用：BR-ID-33。01 F-ADM-24。

**受影响的页面与接口**：后台登录页（新增绑定步骤）、「暂无权限」页；04 §3.2 `admin_users`（TOTP 绑定状态：密钥加密存储、绑定时间为空即未绑定，列名代理自定）；04 §6.6 `auth`（绑定步骤，路径、字段与错误码待契约线定，06 新节第 4 项）；05 F1-06。

**验收**（05 F1-06 验收列）：新账号首次登录先出绑定步骤，绑定前调其他后台接口被拒；动态码错误不绑定、不登录并计入登录失败锁定；没有权限点的账号落到「暂无权限」页。10 AC-S2-59 讲的是权限点授权，本次没有改它；如需单列用例，建议在 10 §3.7 新增一条。

## 2. 封禁账号不能作改归属目标，冻结账号可以

**内容**（负责人 2026-10-05 确认，按建议执行）：后台改归属（未归因订单的管理员变更与已归属订单改归属）时，目标用户是封禁账号的拒绝，不做任何修改；冻结账号可以作为目标，之后能否提现仍按封禁与冻结规则处理。目标用户的风控状态在改归属事务的复查步骤里一起重读。

**代理补全的默认，待负责人确认**（06 新节第 5 项）：「申诉中」的账号按冻结处理，可以作为目标。

## 3. 调账红冲只允许按原单金额整笔冲回

**内容**（负责人 2026-10-05 确认，按建议执行）：已执行的调账单只能整笔红冲，金额由系统按原单带出、不能修改；不支持部分红冲；要改金额须先整笔红冲，再另开新调账单。同一张原调账单只能被红冲一次（凭证唯一键已保证）。

**代理补全的默认**：后台调账页在已执行的单上提供【红冲】、金额只读、已红冲的单显示「已红冲」并链接红冲单（界面做法）。

**涉及 BR / F**：BR-FUND-24（⑥ 加一句、细则新增「红冲只按原单整笔」）；只作引用：BR-FUND-16。01 F-ADM-08。

**受影响的页面与接口**：后台调账页；04 §3.2 `admin_adjustments`（红冲单关联原单的字段，一张原单只能被红冲一次；列名代理自定）；04 §6.6 `adjustments`（请求只带原调账单号，重复红冲的拒绝码待契约线定）；05 F1-08。现有例子「误调 +500 → 红冲 −500 → 重记 +50」本来就是整笔红冲，不变。

**验收**（05 F1-08 验收列）：红冲金额只读、等于原单；同一原单第二次红冲被拒；改金额走「整笔红冲 + 新调账单」。

**恢复方式**：删去 BR-FUND-24 ⑥ 新加的一句与细则「红冲只按原单整笔」，04 `admin_adjustments` 与 `adjustments` 的本次句子，01 F-ADM-08、05 F1-08 的本次句子。

## 4. 字号、折叠屏、横屏的支持范围

**内容**（负责人 2026-10-05 确认「根据官方规范文档来执行」）：

1. 三端跟随系统字号；正文与主要操作在 200% 下不截断、不重叠。
2. 超过 200%（目前只有 iOS 的更大辅助字号档位）：正文继续跟随；导航栏标题、底部标签栏、密集表格类控件封顶在约 200%，用系统大内容查看器承接。
3. 手机锁定竖屏，不做横屏。
4. 折叠屏外屏按普通手机；折叠屏内屏与平板（最小宽度 ≥ 600dp）不做专门的双栏布局，内容区限制最大宽度并居中、可滚动，折叠 / 展开 / 窗口变化时不丢已填内容与滚动位置。
5. 鸿蒙同上；折叠态 / 展开态切换保持连续，悬停态不做专门布局。鸿蒙系统字号最大倍数未在官方页面核实，登记为 09 CAP-X-18（未开始），验证前按 200% 设计，不写成对用户的承诺。
6. App 内 H5 跟随 App 字号到 200%；管理后台支持浏览器缩放 200%。

**依据的官方文档**（由编排会话 2026-10-05 查得；本次回写没有再逐页打开核对）：

- Apple「Larger Text evaluation criteria」：至少 200% 或平台最大字号；底部标签栏、返回等重复出现的导航元素可以不等比放大并用 Large Content Viewer 承接。<https://developer.apple.com/help/app-store-connect/manage-app-accessibility/larger-text-evaluation-criteria/>
- Android 14 起系统字号最大 200%、非线性缩放。<https://developer.android.com/about/versions/14/features>
- Android 16 起面向 API 36 的应用在最小宽度 ≥ 600dp 的屏幕上，方向、可调整大小、宽高比限制被系统忽略；可用 `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` 临时豁免，面向 API 37 起取消豁免。<https://developer.android.com/develop/adaptive-apps/guides/app-orientation-aspect-ratio-resizability>
- 华为「阔折叠 / 阔直板应用开发」最佳实践。<https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-purax-guide>
- WCAG 2.2 成功标准 1.4.4（Resize Text）、1.4.10（Reflow）。
