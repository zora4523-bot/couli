### 0.1 分类与保守原则

每一节先说矛盾在哪，再用带数字的算例说明各种读法各记多少钱，然后判断归类：

### 0.4 贯穿各节的口径

下面七条是各节草案共用的定义。前两条是已确认规则的原意，后五条是为了让等式能核对而补的表达，分别在 §1、§3、§6.2 给出依据。

1. **有效联盟佣金 N**：结算佣金非空取结算佣金，否则取预估佣金；为负按 0（BR-CALC-02 取值阶段，已确认）。
2. **分佣基数 B**：由 N 按 BR-CALC-02 用快照里的预留比例换算。联盟给的数（新佣金、应扣佣金、结算额）都是 N；凡是「新基数」「基数归零」「与已入账基数比大小」，说的都是换算后的 B。
3. **已入账基数与已入账联盟佣金**：`booked_base_fen` 是最近一次记账所用的 B；拟新增 `booked_n_fen`，记同一次记账所依据的 N（正数部分）。两个字段成对更新。
4. **受益人净额**：该受益人在该子订单上各张凭证的代数和（入账、补差、扣回、恢复、改派）。改记平台坏账的扣回算进净额；归平台的正差不算进净额。
5. **应得**：按 `booked_base_fen` 与快照比例重拆出的份额。已被剥夺（forfeited）的受益人应得为 0，经申诉恢复的除外（BR-CALC-09；盲算核对后补，见 §7.6）；封禁或已注销的受益人，应得不超过其已有净额。
6. **待补记额**：应得 − 净额。只有暂缓（held）或正差被延后的受益人为正，其余为 0。
7. **平台净额**：`booked_n_fen` − Σ 未被剥夺受益人的应得。于是该子订单对应收联盟的净额 = `booked_n_fen` − Σ 待补记额。

### 1.2 各种读法的资金结果

**E-01 扣回，联盟回传新佣金**（BR-FUND-08 ①）。P0 入账后部分退款，联盟回传新的结算佣金 600。

| | 读法 A：把 600 直接当新基数（BR-FUND-08 字面） | 读法 B：先换算（BR-CALC-02） |
| --- | --- | --- |
| 新基数 | 600 | floor(600 × 8000 / 10000) = 480；预留 120 |
| U1 新应得 / 扣回 | 300 / 扣 100 | 240 / 扣 160 |
| P1 新应得 / 扣回 | 60 / 扣 20 | 48 / 扣 32 |
| 平台 | 留存 320 → 240，冲回 80；预留 200 不动 | 留存 192 + 预留 120 = 312，冲回 520 − 312 = 208 |
| 应收联盟变化 | −200（100 + 20 + 80） | −400（160 + 32 + 208） |
| 扣回后净额 | U1 300、P1 60、平台账面 440，应收联盟 800 | U1 240、P1 48、平台 312，应收联盟 600 |
| 订单状态 | CREDITED，booked_base_fen = 600 | CREDITED，booked_base_fen = 480，booked_n_fen = 600 |

核对：读法 B 的 240 + 48 + 312 = 600，等于联盟的新佣金；读法 A 的 300 + 60 + 440 = 800，比联盟实际会付的 600 多 200。读法 A 下 U1 多留 60、P1 多留 12；平台账面 440 里只有 600 − 300 − 60 = 240 是真的。

读法 A 的平台一侧，BR-FUND-08 有两句字面：上表按净影响式（「对 UNION_RECEIVABLE 的净影响必须 = −(booked_base_fen − B_new)」，预留不动），平台冲回 80、应收联盟 −200；按平台差额式（「平台留存差额 = 平台已入账净额 − 按 B_new 的新留存」= 520 − 240），平台冲回 280、应收联盟 −400、净额 600。预留不为 0 时这两句互相矛盾，读法 A 本身算不出唯一结果；§1.4 把两句都改成含预留的写法（盲算核对后补注，见 §11）。

**E-02 扣回，带取整**。另一单：N = 1452，reserve_bp = 1300，比例同 P0。入账：floor(1452 × 8700 / 10000) = 1263，预留 189；U1 = floor(631.5) = 631；P1 = floor(126.3) = 126；留存 1263 − 757 = 506；平台合计 695；631 + 126 + 695 = 1452。部分退款后联盟新佣金 1001。

| | 读法 A（1001 当基数） | 读法 B（先换算） |
| --- | --- | --- |
| 新基数 | 1001 | floor(1001 × 8700 / 10000) = floor(870.87) = 870；预留 131 |
| U1 | 新应得 500，扣 131 | 新应得 435，扣 196 |
| P1 | 新应得 100，扣 26 | 新应得 87，扣 39 |
| 平台 | 留存 506 → 401，冲回 105 | 留存 348 + 预留 131 = 479，冲回 695 − 479 = 216 |
| 应收联盟变化 | −262 | −451 |

核对：读法 B 的 196 + 39 + 216 = 451 = 1452 − 1001；扣回后 435 + 87 + 479 = 1001。读法 A 少扣 U1 65、P1 13。按 BR-FUND-08 平台差额式，读法 A 平台冲回 695 − 401 = 294、应收联盟 −451，与上表的净影响式不同，理由同 E-01（盲算核对后补注，见 §11）。

**E-03 扣回，只有应扣佣金**（BR-FUND-08 ②）。P0 入账后部分维权成功，联盟的维权记录给出应扣佣金 250，订单同步没有带新佣金。

| | 读法 A：B_new = 800 − 250 = 550（字面，拿 B 减 N） | 读法 B：N_new = 1000 − 250 = 750，再换算 |
| --- | --- | --- |
| 新基数 | 550 | floor(750 × 0.8) = 600；预留 150 |
| U1 | 新应得 275，扣 125 | 新应得 300，扣 100 |
| P1 | 新应得 55，扣 25 | 新应得 60，扣 20 |
| 平台 | 留存 320 → 220，冲回 100；预留 200 不动 | 留存 240 + 预留 150 = 390，冲回 130 |
| 应收联盟变化 | −250 | −250 |
| 扣回后净额 | U1 275、P1 55、平台 420 | U1 300、P1 60、平台 390 |

核对：两种读法的应收联盟都减 250，等于联盟要扣的佣金，所以字面读法在对账上看不出错；错在分摊：它让 U1 多扣 25、P1 多扣 5，平台多留 30。E-01 的字面读法少扣用户，本例的字面读法多扣用户，方向相反，说明两处都得改。

**E-04 结算额下调**（BR-FUND-09）。P0 入账后联盟把结算佣金从 1000 改成 900（新的结算记录）。

| | 读法 A：拿 900 与 booked_base_fen = 800 比（字面） | 读法 B：先换算，floor(900 × 0.8) = 720 与 800 比 |
| --- | --- | --- |
| 判定 | 900 大于 800，判成「正差」：不立即扣，生成补差候选 | 720 小于 800，负差，同一事务立即扣 |
| 记账 | 候选获批并把 900 当基数重拆：U1 450（+50）、P1 90（+10）、留存 360（+40） | U1 360（−40）、P1 72（−8）；平台 288 + 180 = 468（−52） |
| 应收联盟变化 | +100 | −100 |
| 订单状态 | CREDITED，booked_base_fen = 900 | CREDITED，booked_base_fen = 720，booked_n_fen = 900 |

核对：读法 B 的 40 + 8 + 52 = 100 = 1000 − 900。读法 A 把联盟的下调当成上调：该扣的 40、8 没扣，批准后反而多给 50、10，U1 比应得多 90，P1 多 18。

读法 A 的「批准」一步，上表按 BR-FUND-09 字面（「按当前 settle_commission_fen 与快照重拆的应得份额」）用 900 重拆。若比较时用 900、批准时又换算成 720 重拆，批准的「正差候选」写出来是 U1 −40、P1 −8、平台 −52，而 booked_base_fen 按该条末句写成 900，基数字段与凭证对不上。两种做法都说明比较与重拆必须用同一个换算后的基数（盲算核对后补注，见 §11）。

**E-05 结算额没变**。P0 入账后联盟数据不变（结算佣金仍是 1000），月结账单日运行补差比对。

- 读法 A（字面）：1000 大于 800，这一单生成正差候选。预留比例不为 0 的每一单每个月都会生成一条。若批准并把 1000 当基数：U1 500、P1 100、留存 400，加上原预留 200，账面合计 1200，超过联盟佣金 1000。若批准时改按换算后的 800 重拆，各方差额为 0、不写分录，但 booked_base_fen 被写成 1000（盲算核对后补注，见 §11）。
- 读法 B：换算后 800 等于 800，不生成候选，不记账。

### 2.2 各种读法的资金结果

**E-06 入账后只有预估变小**。P0 入账后，订单同步回传预估佣金 900；结算佣金仍是 1000，没有新的结算记录，退款数量没变，没有维权记录。

| --- | --- | --- | --- |
| 新基数 | 不重算 | floor(900 × 0.8) = 720 | 不重算 |
| 记账 | 无 | U1 −40、P1 −8、平台 −52 | 无 |
| 记账后 | U1 400、P1 80、平台 520，应收联盟 1000；另有 1 张差错单 | U1 360、P1 72、平台 468，应收联盟 900，booked_base_fen = 720 | U1 400、P1 80、平台 520，应收联盟 1000 |
| 下一个账单日的补差比对 | 结算基数 800 = 已入账 800，无动作 | 结算基数 800 大于 720，生成正差候选 +40 / +8 / +52；批准就回到原数，不批准则用户少 40、8 而联盟仍按 1000 付 | 同读法 A |

核对：读法 B 的 40 + 8 + 52 = 100 = 1000 − 900。读法 B 之所以来回，是因为它用预估扣、而补差比对用结算佣金补；要让读法 B 自洽，得同时规定入账后有效来源改回预估，这又推翻 BR-CALC-02。三种读法与 §2.3 的选项 A、B、C 一一对应。

**E-07 预估变成 0**。P0 入账后，订单同步回传预估佣金 0；结算佣金仍是 1000，平台状态没变，没有维权或处罚记录。

- BR-FUND-08 ① 字面（取本次更新的字段）：新基数 0，走迁移 R8：U1 −400、P1 −80、平台 −520，订单变 CLAWED_BACK，应收联盟 0。联盟仍按 1000 结算，之后出「结算有、我方 CLAWED_BACK」差错单；用户被全额扣回，已提现的会变成负余额。
- BR-CALC-02：预估只存档，订单保持 CREDITED，谁的钱都不动。
- 入账前同理：订单还在 WAITING、结算佣金 1000 已到，这时预估变 0。BR-FUND-07 字面（B_est 取预估）会把订单作废，这一单永远不入账，U1 少得 400、P1 少得 80；按 BR-CALC-02 则不动，照常随批次入账。

**E-08 结算佣金归零**。P0 入账后联盟新的结算记录把结算佣金改为 0，平台状态没变，没有维权记录。

- 迁移 R8 与 R10 都符合。金额相同：U1 −400、P1 −80、平台 −520，订单变 CLAWED_BACK，应收联盟 0。核对：400 + 80 + 520 = 1000。
- 不同的只是凭证：R8 写 CLAWBACK（键含 `C{commission_version}`），用户流水显示「订单扣回」；R10 写 SETTLE_ADJUST（键含 seq），显示「结算补差」。
- 结算佣金变成负数同理（追加算例 X-02：预留 0、本人 5000、无上级，已入账基数 1000，U1 500、平台 500，新的结算记录为 −100）。有效 N 按 0（BR-CALC-02），金额同上：U1 −500、平台 −500，应收联盟 0，扣 1000 不扣 1100。终态有三种读法：R8 → CLAWED_BACK；R10 守卫字面是「结算佣金=0」，−100 不满足，订单停在 CREDITED，BR-FUND-09 末句还会把 booked_base_fen 写成 −100；BR-CALC-02 细则写明负 N 入账后走 R8 → CLAWED_BACK（盲算核对后补，见 §11）。

**E-09 同一次更新同时命中两条迁移（R-27）**。P0 入账后，一次订单同步同时带来：2 件退 1 件（refunded_quantity 增加）和新的结算记录 500。新基数 floor(500 × 0.8) = 400，预留 100；U1 应得 200、P1 40、平台 160 + 100 = 260。

- 按当前净额重算（BR-FUND-08「已入账净额 − 新应得」、BR-FUND-09「diff≠0 才写」）：后算的一条差额为 0，不写。合计只扣一次 −200 / −40 / −260，应收联盟 500。核对：200 + 40 + 260 = 500 = 1000 − 500。先算哪一条决定凭证类型，现行规则没有定。

### 2.3 已确认的决定能不能直接定夺

分四件事。

1. **用哪个数算基数**：能，归类**同步**。BR-CALC-02 已确认，结算佣金非空后只取结算佣金；BR-FUND-08（待决策）、BR-FUND-03、BR-FUND-07（默认假设）要服从它。所以 E-07 里预估变 0 不触发扣回，也不触发入账前作废。已入账订单的整单失效另有平台失效状态、维权或处罚记录触发，不靠佣金字段。
2. **归零走哪种凭证**（E-08）：能，归类**同步**。两种写法金额相同，属凭证映射。BR-FUND-08 正文、BR-CALC-02 细则、BR-CALC-15 都把「基数由正变零」归到迁移 R8 写 CLAWBACK，BR-FUND-08 还专门写了京东实际佣金归零按全额扣回；只有 R10 一行另写了一种。统一为：有效基数由正变零走 R8，R10 只处理新基数大于 0 的结算差额。BR-CALC-02 细则本来就写负 N 入账后走 R8；BR-CALC-23 (a) 的「始终保持 CREDITED」随之限定为新基数大于 0（盲算核对后补，见 §11）。
3. **同一次更新的先后**（E-09，R-27）：能，归类**同步**。金额由「按当前净额重算」保证只扣一次，要补的是先后：逆向事件优先。
4. **入账后只有预估变，要不要立刻扣**（E-06）：不能，归类**负责人 / 财务选择**。两边都是已确认规则。FUND-11 的原话是「联盟最终结算比已入账的少了立即扣，多了批准再补」，说的是结算额；只有预估变小算不算「结算少了」，负责人没有说过。月结口径（FUND-01）确认之后，R9b 在已入账订单上已经没有可用的基数来源。

第 4 件事的选项：

| 选项 | 做法 | 资金结果（E-06） |
| --- | --- | --- |
| A（保守默认） | 预估只存档，不记账；系统生成差错单「入账后预估佣金变化」并告警，人工去联盟后台核对。联盟的结算记录真的变小时，按迁移 R10 立即扣（现有规则） | 用户余额不变；差错单 1 张 |
| B | 按预估立即扣（R9b 字面），并规定入账后有效来源改回预估 | U1 −40、P1 −8；要改 BR-CALC-02 |
| C | 预估只存档，不提示 | 用户余额不变；没人知道 |

选 A 的理由：月结口径下入账的依据是联盟结算额（D11）；只变预估是拿不准的信号，按原则挂起由人工处理；不自动动用户已到手的钱；不改已确认的 BR-CALC-02。A 的代价：联盟随后真的下调结算、而用户已经提现时，会形成负余额，按 BR-FUND-10、BR-FUND-12 处理。

大白话：**返利已经按联盟的结算数入了用户的账。之后联盟只把这一单的「预估佣金」改小了，「结算佣金」没有动。要不要马上按改小的预估数把用户多拿的钱扣回来？**

## 3. 日终核对等式（F-13 后半、F-14 后半；Codex 第三轮 R08；含 R-26）

### 3.1 矛盾在哪

| 位置 | 原文要点 |
| --- | --- |
| BR-FUND-19 ⑤（默认假设） | 「每个 CREDITED 或 CLAWED_BACK 子订单：该单订单类凭证（CREDIT、CLAWBACK、SETTLE_ADJUST、ADMIN_ADJUST RESTORE）对 UNION_RECEIVABLE 的净额 = booked_base_fen」；②③④⑤ 属全局差异，会自动把 `settle.auto.enabled` 关掉并冻结涉及用户的提现 |
| BR-FUND-05 细则、BR-CALC-02、BR-CALC-04（已确认） | 平台合计 = 留存 + 预留；入账时平台凭证含预留。于是该单对应收联盟的净额是联盟佣金 N，而 booked_base_fen 是扣过预留的 B |
| BR-CALC-13（已确认，FUND-17）、BR-FUND-04 ⑩ | 受益人冻结或账户申诉中时份额暂缓，不写凭证；其他受益人照常入账，订单变 CREDITED |

⑤ 的等式在三种正常业务下不成立：预留比例不为 0、有暂缓的受益人、有正差被延后的受益人。④ 在「扣回 → 恢复 → 再扣回」和「改派 → 扣回」两种合法序列下不成立。照现行文字实现，这些订单每天都会触发全局差异，自动停掉批次并冻结用户提现。

### 3.2 各种读法的资金结果

**E-10 预留与暂缓**。四步。

| 步骤 | 记账 | 应收联盟净额 | booked_base_fen / booked_n_fen | ⑤ 字面（净额 = booked_base_fen） | 修正式（净额 = booked_n_fen − Σ 待补记额） |
| --- | --- | --- | --- | --- | --- |
| ① P0 入账，没有暂缓 | U1 +400、P1 +80、平台 +520 | 1000 | 800 / 1000 | 1000 ≠ 800，报全局差异 | 1000 − 0 = 1000，通过 |
| ② 另一单，入账时 U1 被风控冻结（暂缓），其余同 P0 | P1 +80、平台 +520；U1 的 400 不写凭证 | 600 | 800 / 1000 | 600 ≠ 800，报全局差异 | 1000 − 400 = 600，通过 |
| ③ 接 ②，暂缓期间联盟把结算佣金改为 900 | P1 −8、平台 −52；U1 应得变 360，仍不写凭证 | 540 | 720 / 900 | 540 ≠ 720，报全局差异 | 900 − 360 = 540，通过 |
| ④ 接 ③，U1 解冻，后续批次补入账 | U1 +360 | 900 | 720 / 900 | 900 ≠ 720，报全局差异 | 900 − 0 = 900，通过 |

核对：④ 之后 U1 360 + P1 72 + 平台 468 = 900。若 ④ 改为 U1 转封禁，360 记平台收入，应收联盟同样是 900。

要让字面的 ⑤ 成立，只有两种做法，都会把账做错：

- 平台凭证不记预留（P0 只记留存 320）：应收联盟 800 = booked_base_fen，等式成立；但联盟回款 1000 时应收联盟被贷记 1000，每单倒挂 200，预留 200 没进任何收入科目。
- 暂缓份额先记给平台（② 里平台记 920）：等式在预留为 0 时成立；但解除时按 BR-FUND-05 的模板「借 应收联盟 / 贷 用户余额」补入账 400，应收联盟变成 1400，超过联盟佣金。

**E-11 恢复后再次扣回（R-26）**。P0 入账后全额维权成功：CLAWBACK U1 400、P1 80，平台冲回 520，订单变 CLAWED_BACK。之后联盟恢复佣金 1000，差错单经人工处理走迁移 R13：ADMIN_ADJUST（RESTORE）U1 +400、P1 +80、平台 +520，订单回到 CREDITED。之后再次全额维权成功：CLAWBACK U1 400、P1 80，平台冲回 520。

- ④ 字面：U1 的 Σ CLAWBACK = 800，CREDIT 400 + 正向 SETTLE_ADJUST 0 = 400，800 大于 400，报全局差异。
- 修正式（净额不为负）：U1 净额 = 400 − 400 + 400 − 400 = 0，通过。
- 核对：应收联盟 1000 − 1000 + 1000 − 1000 = 0；两次扣回都只扣了当时确实在账上的钱。
- 上面两行的第二次扣回都按计入恢复的净额算（U1 扣 400）。若按 BR-FUND-08 正文的净额式（CREDIT + Σ SETTLE_ADJUST − Σ CLAWBACK，不计 RESTORE），第二次扣回时 U1、P1 的净额都是 0，不扣；平台冲回 520 后应收联盟停在 480，U1、P1 留着恢复的 400、80，订单却是 CLAWED_BACK。这时 ④ 反而通过（Σ CLAWBACK 400 ≤ 400），⑤ 报差异。BR-FUND-19 ④ 是日终核对，只发现、不拦截写入；扣回多少由 BR-FUND-08 的公式决定，这一处缺口见 §7.6（R-28）（盲算核对后补注，见 §11）。

### 3.3 已确认的决定能不能直接定夺

能，归类**同步**。⑤ 与 ④ 是核对公式（BR-FUND-19 是默认假设），被它们否定的做法都是已确认规则：预留归平台（BR-CALC-02）、暂缓不入账（BR-CALC-13）、人工恢复（BR-FUND-22）、改派（BR-ATTR-20）。公式跟着业务改，不改变任何一笔钱。

## 4. 锁顺序与受益人状态的串行化（F-03；Codex 第三轮 R03）

### 4.1 矛盾在哪

| 位置 | 原文要点 |
| --- | --- |
| BR-WDR-07 正文（默认假设） | 「凡是会修改一个会员余额行或其提现冻结的写操作（包括 BR-FUND 扣回、BR-WDR-05 冻结），都必须先锁 users 行，再锁余额行」 |
| BR-FUND-16 正文（已确认）、BR-FUND-05、02 §18 | 只写「account_balances 在同一事务内 SELECT … FOR UPDATE，多账户按 account_id 升序」，没有 users 行 |
| BR-FUND-16 细则「分工」 | 「锁顺序、缓存策略等实现细节代理可自定」 |
| BR-ID-28（默认假设，资金部分 FUND-09 已定） | 「自进入 processing 起，以该 user_id 为受益人的订单在入账时不写该用户流水」 |
| BR-CALC-13（已确认） | 入账执行时逐受益人判定：封禁、注销、已识别未成年的推广份额归平台；冻结或申诉中暂缓 |

两个缺口。一是多受益人入账时 users 行按什么顺序锁没有定，两个订单的受益人交叉时可能互相等待。二是规则只说「入账时判定受益人状态」，没有说判定要在取得锁之后：先读状态、后加锁，中间状态变了，就会按旧状态记账。

### 4.2 各种读法的资金结果

**E-12 入账与注销同时发生**。订单 O8：归属 U7（无上级），联盟结算佣金 750，其余同 P0。B = floor(750 × 0.8) = 600，预留 150；U7 应得 300，留存 300，平台合计 450。U7 余额 800，已申请注销、冷静期刚满。时间线：① 批次事务读到 U7 状态正常；② 注销任务锁 U7、置为注销处理中，把余额 800 以 ACCOUNT_CLOSED 转平台收入并提交；③ 批次事务取得余额锁，记账。

| | 读法 A：先读状态、后加锁，按读到的状态记账 | 读法 B：取得锁之后重读状态再记账 |
| --- | --- | --- |
| U7 | 余额 0 → +300 = 300 | 余额 0，不写流水 |
| 平台 | 订单凭证 450；另有注销转入 800 | 订单凭证 450 + 没收 300 = 750；另有注销转入 800 |
| 应收联盟 | 750 | 750 |
| 结果 | 300 挂在一个已不能登录、不能提现的账号上，既到不了用户手里，也没进平台收入，违反 BR-ID-28 | 符合 BR-ID-28、BR-CALC-13 |

核对：两种读法订单凭证合计都是 750（300 + 450）。

同样的窗口在封禁时也有：读到正常 → 封禁提交 → 把 300 入给已封禁用户。按 BR-CALC-13「已入账的份额不因事后封禁而扣回」，这 300 留在封禁用户余额里，平台少收 300。

死锁的例子不涉及金额：订单 X 的受益人是（U1 本人、U2 上级），订单 Y 是（U2 本人、U1 上级）。两个事务各按角色顺序锁 users 行，X 持有 U1 等 U2，Y 持有 U2 等 U1。按 user_id 升序加锁就不会发生。

### 4.3 已确认的决定能不能直接定夺

能，归类**同步**（实现做法）。BR-WDR-07 已要求所有余额写操作先锁 users 行；BR-ID-28、BR-CALC-13 已规定按入账那一刻的受益人状态处理；BR-FUND-16 细则写明锁顺序属实现细节、代理可定。要补的是一个统一顺序，和「锁后重读」这一句。金额规则不变。

### 4.4 拟写入 08 的条文草案

状态：已确认（BR-FUND-16 原状态；内容属其细则授权的实现细节）。

**BR-FUND-16 细则「加锁流程」** 改为：

> 订单相关的记账事务（迁移 R5、R5a、R8、R9、R10、R13、R14）按固定顺序加锁：
> ① `pg_advisory_xact_lock(order_key)`（BR-FUND-01）；

> ③ 这些用户的 account_balances 行按 account_id 升序 `FOR UPDATE`；

**BR-FUND-05 正文**「用户账户按 account_id 升序 SELECT … FOR UPDATE」改为「加锁顺序与锁后重读见 BR-FUND-16 细则」。**BR-CALC-13 正文**「入账…执行时逐受益人判定」补「判定在 BR-FUND-16 的锁内进行」。

### 6.5 F-12 哪些已经定了，哪些还等财务

### 6.11 S-08 已失效的订单能不能被找回

**矛盾在哪**。迁移 R3b 写「VOID 且 user_id 为空｜CLAIM_APPROVED / ADMIN_REASSIGN｜VOID 不变，只写 user_id、user_basis、locked」，BR-CALC-10、BR-ATTR-20 ③（已确认）同样写法。但 BR-ATTR-17 ④c（默认假设）在提交找回时遇到 VOID 订单直接返回 30202；BR-ATTR-18 在审核时遇到 VOID 由系统自动驳回。所以 R3b 的 CLAIM_APPROVED 走不到。另有两个缺口：未归因且已 VOID 的订单被同步重新归因成功时，R3a 只从 UNATTRIBUTED 出发，没有迁移可走；未归因的 VOID 订单经 R12 恢复时该回到 UNATTRIBUTED，R12 只写了 ESTIMATED 或 WAITING。

**各种读法的资金结果（E-26）**。一笔未归因订单，金额同 P0，买家退款后失效（VOID）。U1 提交找回。之后买家撤销退款，平台恢复有效，联盟结算 1000。

### 6.12 W-01 02 的打款步骤顺序与 08 相反

**矛盾在哪**。02 §5.3 的时序先「再校验开关、会员阻断、单笔上限、单日总额；不过 → 回 APPROVED」，后「已有 transfer 记录只查询不转账」。BR-WDR-13（默认假设）的顺序是：① 状态与 execute_seq；② 已有任何转账尝试 → 不转账，转入查询；③ 复核，不过走 W9。

### 6.13 W-03 提现单怎么换批次

**矛盾在哪**。BR-WDR-11（已确认）：一张 APPROVED 单同一时刻只能属于一个未完成的批次，批次内还有 APPROVED 单即为未完成。BR-WDR-13：W9 退回时保留 batch_id。BR-WDR-30（已确认）：判为自动后执行受阻的单留在 APPROVED，「进入人工批次」。合起来：受阻的单让原批次永远未完成，它自己又不能进别的批次，怎么转没有写。

**各种读法的资金结果（E-28）**。提现单 amount 28000（net 28000）判为自动，系统审核通过并建了自动批次；执行时水位不足，留在 APPROVED。

- 读法 A（字面）：这张单属于未完成的自动批次，不能加入人工批次；自动批次没有人工重新执行的入口。28000 一直冻结，直到有人驳回（退回余额）或线下打款补录。
- 读法 B（换批次）：人工勾选这张单组建人工批次时，把它从自动批次移到新批次，水位补足后执行，打款 28000 一次。BR-WDR-18 的水位检查对人工批次同样适用，水位仍不足时整批拒绝，单据留在 APPROVED，转账 0 次（盲算核对后补注，见 §11）。
- 两种读法都不会打两次款（执行要求状态为 APPROVED 且没有任何转账尝试），差别是钱能不能按时付出去。

**能不能直接定夺**。能，归类**同步**。转人工已由 BR-WDR-30 决定；要补的是换批次的做法，不改审核结果与转账次数。

**条文草案**（BR-WDR-11 已确认；BR-WDR-12 默认假设）：

- **BR-WDR-11**：「一张 APPROVED 单同一时刻只挂在一个批次上（withdrawals.batch_id）。批次的每个成员都有了执行结果（进入 PAYING、跳过、受阻、已移出）即为已完成。」
- **BR-WDR-12**：「人工组建批次时勾选的 APPROVED 单如果已挂在别的批次上（自动批次里执行受阻的单、经 W9 退回的单），在同一事务内以 CAS（status=APPROVED 且 batch_id=原批次）改挂到新批次，原批次的成员明细记『已移出』并保留。review_mode 不变，仍表示审核方式；执行方式看所在批次的 kind。」

**受影响位置与验收**。04 §3.2 `payout_batches` 补成员明细（批次、提现单、结果、原因、移入的批次；12 §9 W-07 已列为缺口）；12 §5.2、§5.3。10 拟新增 **AC-S2-拟13**：AC-S2-53 ③ 的那张单随后被勾进人工批次并执行成功，原自动批次显示已完成，全程只有 1 条转账尝试。

### 6.14 W-04 付款方侧失败的单，通道其实已成功时怎么收口

**矛盾在哪**。BR-WDR-17（默认假设）：转账返回付款方侧的码时走 W9 回到 APPROVED，不退回用户余额；这类单已有转账记录，不得再次执行，只能 W8 手动成功或 W3 驳回。BR-WDR-08 细则写「已有转账尝试的单不回到待审核」，与 W9 把它退回 APPROVED、列表显示「等待审核」不符。BR-WDR-23 ③ 与该主题未决问题第 9 条承认：通道账单显示成功而内部是这种 APPROVED 单时，没有迁移可走，只出差错单并冻结会员。

**各种读法的资金结果（E-29）**。提现单 amount 10000，手续费 0、税 0，net 10000。转账返回的码被判为付款方侧失败，单据经 W9 回到 APPROVED，冻结 10000 没动。实际上通道那边转账成功了（码表误判，或通道异常）。

- 做法 A（凭原通道的成功证据核销原单）：把原单记为 PAID_API：借 用户冻结 10000 / 贷 企业支付宝 10000。用户共收到 10000。
- 做法 B（财务按 W8 再线下打一次并补录）：用户共收到 20000，重复付 10000。
- 做法 C（财务按 W3 驳回）：冻结的 10000 退回可提现余额，用户再提现 10000，共收到 20000。之后对账发现，用 PAYOUT_RECOVERY 调减 10000，余额可能变负。
- 核对：做法 A 下冻结 10000 → 0，企业支付宝实际流出 10000，账实一致。

**能不能直接定夺**。展示措辞：能，**同步**。收口方式：不能，归类**负责人 / 财务选择**（要新增一条提现状态迁移）。

| 选项 | 做法 |
| --- | --- |
| A（保守默认） | 保持冻结。通道成功有证据（查询结果，或含该 out_biz_no 的账单行，金额等于 net_fen）时，由有权限者 step-up 把原单核销为 PAID_API。在此之前，这类单的 W3、W8 增加守卫：须先有一次查询结果为「订单不存在」或明确失败，否则拒绝 |
| B | 不加迁移，维持现状：差错单、冻结会员、事后调账追回 |

大白话：**一笔提现，系统以为没打出去（比如平台账户余额不足），其实支付宝已经打给用户了。这时财务如果再线下打一次，或者把钱退回用户余额，用户就拿了两份。要不要规定：先查清原来那笔到底成没成，成了就直接把原单记成已到账？** 保守默认：要。

**条文草案**（待决策，按 A）：

- **BR-WDR-08 迁移表**增 W11：「APPROVED 且 hold_reason=payer_side_after_transfer｜CHANNEL_SUCCESS_PROVEN｜该单唯一的转账尝试 result=fail；通道成功凭证（查询返回成功，或含该 out_biz_no 的账单行，金额 = net_fen）；有权限者 step-up｜PAID_API｜写成功分录（BR-WDR-09）；追加一条 kind=query、result=success 的尝试记录，不改原记录。」
- **BR-WDR-17**「只能走 W8 手动成功，或 W3 驳回」之后补：「执行 W3、W8 之前，该单最近一次查询的结果必须是『订单不存在』或清单内的明确失败；查询成功的走 W11；查询结果未知的不得处理。」
- **BR-WDR-08 细则**（同步）：「已有转账尝试的单不回到待审核」改为「已发出转账且结果为成功或未知的单不回到 APPROVED；付款方侧失败（结果为失败）的单经 W9 回到 APPROVED，列表显示『等待处理』与原因，不可再次执行」。

**受影响位置与验收**。04 §4 的 4.2 行（W1–W10 改 W1–W11）与 `withdrawal.yaml`；12 §5.4、§5.6、§5.8。10 拟新增 **AC-S2-拟14**：付款方侧失败的单，查询返回成功 → W11 记为 PAID_API，只出金一次；未查询就驳回或手动成功被拒；AC-S2-50 ③「支付宝成功、内部 APPROVED」的后续处理改为可走 W11。

### 6.15 W-08 对账能力没验证时要不要开自动出款

### 7.1 R-21 按应扣佣金扣回之后，月结补差会把扣掉的钱补回去

**矛盾在哪**。BR-FUND-08 ②（待决策）：联盟没有回传新佣金、只有维权记录给出应扣佣金时，按应扣佣金算新基数并扣回，booked_base_fen 随之变小。BR-FUND-09 ②（已确认）：补差比对对 CREDITED 子订单运行，结算佣金换算出的基数大于 booked_base_fen 就生成正差候选。按 ② 扣回之后，联盟订单上的结算佣金还停在旧值，下一次比对就会为这一单生成正差候选，金额正好等于刚扣掉的数。另一个没写清的点：如果扣回之前这一单已有一条待批准的正差候选，应扣佣金是从已入账的联盟佣金里减，还是从联盟最新的结算佣金里减。

**各种读法的资金结果（E-32）**。接 E-03 读法 B：按应扣佣金 250 扣回之后，U1 300、P1 60、平台 390，booked_base_fen = 600，booked_n_fen = 750。联盟订单上的结算佣金仍是 1000，没有新的结算记录。到了月结账单日：

- 读法 A（BR-FUND-09 ② 字面）：结算基数 800 大于 600，生成正差候选 U1 +100、P1 +20、平台 +130。批准后 U1 400、P1 80，刚扣的钱原样补了回去。联盟实际只付 750，平台实得 750 − 480 = 270，账面却是 520。
- 读法 B（保守）：这条结算记录早于最近一次扣回，不为它生成候选。等联盟的新结算记录：新记录是 750 → 与已入账相等，不补；新记录更高 → 正常生成候选，由批准人对着维权记录决定。
- 核对：读法 A 候选合计 100 + 20 + 130 = 250，等于刚扣回的合计。

基准的两种取法：这一单在扣回前还有一条没批准的正差候选（联盟结算 1200，已入账的联盟佣金仍是 1000）。从已入账的 1000 里减：1000 − 250 = 750，候选作废。从最新结算 1200 里减：1200 − 250 = 950，换算出的基数 760 小于 800，扣 U1 20（400 → 380）。前一种扣得多，等联盟出新记录后再按新记录补差。

**能不能直接定夺**。不能，归类**财务选择**。BR-FUND-08 是待决策条目，BR-FUND-09 ② 没有考虑扣回之后的情形；两种读法的资金结果不同。

| 选项 | 做法 |
| --- | --- |
| A（保守默认） | 应扣佣金从已入账的联盟佣金 booked_n_fen 里减（BR-FUND-08 ② 字面的口径）。扣回发生后，早于这次扣回的结算记录不再产生正差候选，已生成、未批准的作废。等联盟的新结算记录 |
| B | 不加限制。候选照常生成，由批准人把关 |

大白话：**联盟通过维权记录告诉我们这一单要扣 250 佣金，我们已经扣了用户的钱。但联盟订单上的结算金额还没改，系统月底一比对，会以为该给用户补 250。要不要让系统在这种情况下不提补钱？** 保守默认：不提，等联盟把结算金额更新了再比。

**条文草案**（待决策，按 A）。BR-FUND-09 ② 补：「同一条结算记录（seq）只在其写入时刻晚于该子订单最近一次扣回（CLAWBACK）时才生成正差候选；扣回发生时，该子订单未批准的正差候选全部作废。」BR-FUND-08 ② 的基准已在 §1.4 写为 booked_n_fen − 应扣佣金。

**受影响位置与验收**。04 §3.2 `settle_adjustments.status` 增「因扣回作废」（12 §9 F-09 已列为枚举缺口）；12 §4.5、§4.7。10 拟新增 **AC-S2-拟15**：E-32 读法 B；另一问：扣回前已有未批准的正差候选 → 扣回时作废，批准接口返回已作废。

### 7.2 R-22 从没入过用户账户的份额，扣回时被写成了坏账

**矛盾在哪**。BR-ID-28 细则最后一例：注销用户进入 processing 之后，其订单在月结批次入账时「不写该用户流水，记平台」；该单随后全额维权成功，「不写墓碑用户 CLAWBACK，记平台坏账（BR-FUND-08）」。BR-FUND-08 正文的公式是「受益人扣回金额 = 该受益人的已入账净额 − 新应得，≤0 不写」，改记坏账只是把本该写在用户账户上的扣回换一个借方科目。这位用户的份额从没入过他的账户，净额是 0，没有可扣的，也就没有可记坏账的。

**各种读法的资金结果（E-33）**。沿用 BR-FUND-05 细则的数：联盟结算佣金 1234，预留比例 0，本人 5000、直推 1000。归属用户 U 在入账前已进入注销处理，上级 P 正常。入账：U 的 617 记平台（没收）；P +123；平台 494 + 617 = 1111；应收联盟 1234。之后全额维权成功。

- 读法 A（BR-ID-28 细则例的字面）：借 平台坏账 617 / 贷 应收联盟 617；P −123。平台那一笔如果冲回 1111，应收联盟合计减 1851，变成 −617；如果只冲回 494，应收联盟归零，但平台收入里留着 617、同时多出 617 坏账，一笔从没付出去的钱被记成了坏账。
- 读法 B（BR-FUND-08 公式）：U 的净额 0、新应得 0，不写；P −123；平台冲回 1111。应收联盟 1234 − 1234 = 0，没有坏账。
- 核对：123 + 1111 = 1234。

**能不能直接定夺**。能，归类**同步**。BR-FUND-08 的公式已经给出答案；它自己的细则例（11-24 入账、12-01 才进入注销处理）才是该记坏账的情形：钱确实入过用户账户。BR-ID-28 的例子把两种情形写混了。

**条文草案**（默认假设，同 BR-ID-28）。BR-ID-28 细则末例改为：「…该用户的份额在 10-24 的月结批次中记平台（forfeit_reason=deleted）；该单 11-05 全额维权成功 → 该用户净额为 0，不写任何分录；平台冲回其已入账净额（含没收的份额）。」BR-FUND-08 正文的注销一句前加限定：「该受益人净额大于 0 时」。BR-ID-28 正文「已入账订单再被扣回时…改记平台坏账」的「已入账」注明「指份额入过该用户账户」。

### 7.3 R-23 基数为 0 而联盟佣金大于 0 时，平台预留漏记

**矛盾在哪**。BR-FUND-05 正文、迁移 R5：「B_credit=0 时不写凭证，只迁移状态」。这句写于没有平台预留的时候，那时基数为 0 就是联盟佣金为 0。BR-CALC-02（已确认）之后，预留比例可取 0–10000：比例够大，或联盟佣金小到扣完预留后取整为 0，都会出现「基数 0、联盟佣金大于 0、预留大于 0」。照字面不写凭证，预留这部分就没进账。

**各种读法的资金结果（E-34）**。某平台预留比例设为 10000（全部预留），联盟结算佣金 1000：基数 0，预留 1000。

1. §1 的换算（同-01）。预留比例一旦不为 0，旧写法会让每一次扣回少扣、每一次补差比对多出一条正差候选，方向都是多付，而且对账上不一定看得出来（E-01、E-04、E-05）。

3. 提现侧的重复付（决-08、决-11、同-21）。付款方侧失败的单、负余额后卡住的单，在现行规则下都有一条「先核销或退回、之后又付出去」的路径（E-29、E-31、E-35）。

### 11.1 方法

- **谁算**：Codex（另一家模型）独立计算，做法同规划/11 §4.2。只给它规划仓库 main 的 `规划/08_业务规则/` 和一份只含输入的算例文件，不给本文各节的答案。
- **输入**：本文 §0.3、§0.4、§9.3 原样（E-01～E-36），另加 5 个追加算例 X-01～X-05。追加算例取自 12 流程图收尾核对（Codex 第四轮 E1–E5）的反例，不用 P0：预留比例 0、本人 5000、没有上级。§0.4 第 3–7 条注明是本文补的表达，允许使用，但要求它在认为 08 不支持时写明。
- **输出**：每个「算例 × 读法 × 步」一行，共 180 行（E 算例 155 行，X 算例 25 行），另列它认为 08 原文本身矛盾的 16 条和一段「缺规则或需要限定条件」。输入文件与原始结果是本地运行记录，未入库。
- **符号**：Codex 按分录写，借为正、贷为负：受益人被扣记正数、入账记负数，平台收入减少记正数，应收联盟减少记负数。比对时换算成本文的写法（受益人余额、平台收入增加记 +）。
- **比对**：逐行逐列比各受益人、平台收入、平台坏账、应收联盟的变化与净额、订单终态、booked_base_fen；多步算例逐步比。本文没写的列不算不一致；本文没算、Codex 多算的行（多为对照读法的后续步），由本文独立复算。
- **分类**：(a) 一方算术错误，只有算式无歧义时才算；(b) 双方对同一读法、或对 08 某句的理解不同；(c) 一方标「算不出」或「08 不支持该读法」。(a) 错在本文的直接改数字。(b)(c) 不由本文裁决：08 原文明确支持一方的，写明依据、按同步项处理；原文支持不了任何一方的，列为待选择项。
